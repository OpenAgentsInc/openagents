# Streaming SHA-256 and tagged hashes

Queue task `crypto-sha256` (`#6784`), 2026-10-28.

[sha256.coax](../../lib/crypto/sha256.coax) provides streaming, one-shot and
BIP-340 tagged SHA-256 with checked Coax policy and caller-owned state/output.
The [runtime bridge](../../lib/crypto/sha256-memory.coax) observes overlapping
byte spans; it contains no hash, state-transition or admission policy.

## One compression implementation

The compression function, padding, initial hash words and the one-shot
`S_hash` are in [sha256-kernel.coax](../../lib/crypto/sha256-kernel.coax).
Both this module and the compiler's `coax/lib/proto/fingerprint.coax` load it.
Streaming code supplies complete blocks, including explicit final padding; it
does not reimplement the SHA round function or copy a second constants table.

Until Nostr book chapter 4 (2026-10-31), the kernel lived in
`fingerprint.coax` and this module loaded that file. The move was a compiler
input migration:

- `coax/provenance.sh` lists `coax/lib/crypto/sha256-kernel.coax` as a
  compiler input, and `coax/build.sh` copies it into its build snapshot.
- `coax/bootstrap-build.sh` and `coax/tests/run.sh` run `coax test` and
  `coax mutate` on the kernel.
- The embedded fingerprint source, and so a generated module's
  `fingerprint_sha256`, is the kernel followed by `fingerprint.coax`.

Every digest is unchanged: the kernel's binary vectors and this module's
checks are the same before and after the move. The combined fingerprint
source SHA-256 (kernel bytes, then `fingerprint.coax` bytes) is
`cbb06bc1439ca987d14de9addf60f6966bff9c291f80987c2b69f0bbe9db50a2`. The earlier `fingerprint.coax` pin,
`94142391e7e8122c4314443a878d65e61a1318cc5de2430f7d1ac826d620728a`, is the
value in the evidence files dated before the move.

## API and lifecycle

Load `sha256-memory.coax` for the public update/final/hash/tag operations. All
statuses are values: zero is success. The state is an opaque, caller-owned byte
view of exactly `sha256_state_size()` bytes (112 in this version).

| Procedure | Behavior |
| --- | --- |
| `sha256_init(state)` | Initializes every state byte; enables a new stream. |
| `sha256_update(state, input)` | Consumes the whole admitted chunk synchronously; retains no borrowed input. |
| `sha256_final(state, out)` | Writes the first 32 output bytes; repeated finalization returns the same digest. |
| `sha256_hash(input, out)` | One-shot wrapper over the streaming path. |
| `sha256_tagged(tag, input, out)` | `SHA256(SHA256(tag) || SHA256(tag) || input)`; tag is a counted byte string. |
| `sha256_bip340(tag_id, input, out)` | IDs 0, 1, 2 select `BIP0340/aux`, `BIP0340/nonce`, `BIP0340/challenge`; other IDs refuse. |
| `sha256_info(state)` | Returns `{error, phase, total, buffered}`; valid active/final phases are 1/2. |
| `sha256_update_limit(total, count)` | Pure counter/chunk preflight only; it does not authenticate a state/history. |

An update chunk or one-shot message is at most 1 MiB. Larger streams use
multiple bounded updates. The cumulative byte count is at most `2^61-1`, so
final multiplication by eight fits the 64-bit SHA length field. Generic tags
are at most 1,024 bytes, including the valid empty tag. BIP tags use the exact
ASCII names above; callers decide how arbitrary external text is encoded.
There is no fixed 32-byte message restriction on the general hash/tag API.

| Status | Meaning |
| --- | --- |
| 0 | Success |
| 1 | Wrong state count, magic/version, phase or inconsistent counter/buffer metadata |
| 2 | Negative or oversized input chunk count |
| 3 | Output capacity below 32, negative or above the local byte-helper budget |
| 4 | Update attempted after finalization |
| 5 | Overlapping state/input/output spans |
| 6 | Cumulative byte count would overflow the SHA byte-length bound |
| 7 | Invalid BIP tag ID or generic tag count |

Refusals leave state and output unchanged. Fixing output capacity permits retry;
updating a finalized stream requires explicit reinitialization. `sha256_info`
reports the original message byte count after finalization and zero buffered
bytes. Output capacity beyond 32 is left untouched. The byte state layout is a
private in-process representation, not a published protobuf or durable format.
Do not accept a saved state from an untrusted peer: valid shape is not evidence
that the claimed bytes were hashed. Caller code serializes access to each state.

Native callers lend valid pointers and truthful view counts. Whole borrowed
spans are conservatively checked for overlap, including unused output capacity.
The pure `_checked` procedures consume already observed alias metadata and are
not substitutes for the runtime wrappers. There is no allocation or input-sized
padding buffer in the Coax algorithm; its scratch is fixed arrays and state.
State and scratch may retain input or digest material. Ordinary initialization
is **not secure erasure**; keyed users need the separate cleanup contract.

## Verification

```sh
coax/bin/coax test coax/lib/crypto/sha256.coax
coax/bin/coax mutate coax/lib/crypto/sha256.coax
python3 coax/tests/nostr/sha256.py
python3 coax/tests/nostr/sha256.py --evidence /tmp/coax-sha256-evidence.json
```

The [vector adapter](sha256_adapter.coax) exports `vector_digest(input, out)`
for the shared native vector-runner SPI; it calls the actual new hash API.
It is distinct from the runner's earlier fingerprint-only fixture adapter.

- **39 combined Coax checks** cover this module and the shared byte and
  kernel checks. **693 mutants killed, zero survivors** across the
  combined graph. Surviving cases led to wide counter and actual one-shot
  digest assertions. A duplicate fast/slow buffer path and redundant validity
  checks were simplified instead of granting equivalent-mutation waivers.
- **Nine focused native/target tests** check all 129 pinned NIST ShortMsg and
  LongMsg rows against both their published digests and independent Python
  `hashlib`, plus chunk/padding boundaries, general and all three BIP tag hashes,
  idempotent finalization, phase errors and state/output preservation.
- Checked and wrapping generated C runs at `-O2`. A native ASan/UBSan harness
  covers malformed view counts, boundary splits and state/input/output alias.
- **Real wasm32-wasip1** executes in Node/V8/WASI in checked and wrapping builds:
  all 129 NIST rows, 36 boundary stream cases, 12 BIP tag cases and output guards.
  Both native and Wasm hash a 1 MiB payload split at **every size 1 through 129**.
  These are actual Wasm results, not native output labeled as browser evidence.
  No Safari/JavaScriptCore or physical iPhone run is claimed.

The shared legacy comparison checks stream-state composition; because it uses
the same compression kernel, it is not an independent cryptographic oracle.
The pinned NIST/hashlib results provide that independent check. Neither tests,
mutation nor throughput constitute a security audit or production-signing gate.

## Kernel measurements

[Raw evidence](data/sha256-2026-10-28.json) records source/vector/toolchain hashes,
CPU/platform, engine, optimization and seven raw samples. On this Apple M5 Max,
Apple clang 21.0.0 native C and Homebrew clang 23.1.4 Wasm, `coax0 0.15.0`:

| Target | Checked `-O2` median | Wrapping `-O2` median |
| --- | ---: | ---: |
| Native arm64 | 285.64 MB/s | 329.84 MB/s |
| wasm32, Node 26.12.1 / V8 14.6 | 192.86 MB/s | 271.40 MB/s |

MB means 1,000,000 bytes. These are warm kernel-only measurements after
conformance work, seven samples of 32 MiB native / 8 MiB Wasm per sample, each
using 1 MiB one-shot calls with a varying first byte and observable digest sink
to prevent dead-code elimination or loop hoisting. They exclude UI, relay traffic, cold start
and platform signing. The checked native point is below the provisional
300 MB/s target; the wrapping native and both Wasm points exceed their respective
provisional 300/150 MB/s figures on this machine. No universal or tail-latency
claim follows. Further optimization must preserve the same independent vectors
and explicit cost/evidence scope.
