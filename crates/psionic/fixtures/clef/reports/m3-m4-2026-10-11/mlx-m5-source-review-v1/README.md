# MLX source review for the next Clef M5 experiment

Status: source review only. No product changes, builds, model execution, GPU work, or weight reads. Public MLX sources are pinned to `06eb7483f03bca49a80e596f4089d02a507a2cf9`; `sources.json` records URLs, sizes, and SHA-256 values.

The strongest remaining opportunity is a faster full-K projection path. The earlier loaded 4k profile assigned about 3.4 of 4.4 device seconds to matrix multiplication and 0.27 seconds to Delta. Those are historical measurements, not a current phase profile or proof of a memory-bandwidth limit. The new diagonal Delta probe preserved the tested numerical bounds but was slower than production sequential scan for every timed shape. Further Delta tuning cannot be justified by that evidence.

## One small candidate: change tile dispatch order

MLX's regular NAX dispatcher chooses a threadgroup swizzle and adjusts the grid in [matmul.cpp, lines 291–326](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/matmul.cpp#L291-L326). Its shader maps physical groups to logical output tiles in [steel_gemm_fused_nax.h, lines 97–105](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/kernels/steel/gemm/kernels/steel_gemm_fused_nax.h#L97-L105). Several architecture branches use four adjacent row tiles per column tile.

Clef currently maps `tgid.x` directly to output columns and `tgid.y` to 64-token rows. A single fixed candidate can instead map `output_tile = physical_x / 4` and `token_tile = physical_y * 4 + physical_x % 4`. The corresponding grid is `(output_tiles * 4, ceil(token_tiles / 4), 1)`. Extra logical token tiles must return before tensor slicing. Keep the existing 64-by-64 or 64-by-128 tile, four SIMD groups, full dynamic K, transpose flags, strict precision, static interior slices, and residual accumulation unchanged.

This groups four token blocks using the same weight panel. Better cache reuse is a hypothesis; Metal does not promise a particular threadgroup execution order, and the tradeoff can reduce input reuse. The candidate adds no allocation, reduction, or dispatch. It differs from the already rejected larger tiles, transposed storage, fixed K, and serial K loops. Because it changes no per-element arithmetic or output ownership, require bitwise output equality before timing, including residual mode and odd token/output tails. Compare only baseline and this fixed swizzle with the existing actual Flash gate/up/down weights at 512, 1024, and 2048 tokens. Preserve paired GPU timestamps and reject integration unless the complete FFN combination improves materially. There is no evidence yet of any gain, let alone enough to meet M3.

## Other source findings and their limits

- MLX routes large K to parallel split-K when `K >= 3 * max(M, N)` [at lines 1050–1054](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/matmul.cpp#L1050-L1054). Flash down `(M=tokens, N=4096, K=12288)` and 27B down `(N=5120, K=17408)` meet that condition for our tested chunks. This is different from a serial K loop, but MLX allocates an f32 partial output for each partition and adds a reduction dispatch [at lines 741–749](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/matmul.cpp#L741-L749). Three Flash partitions cost 48 MiB at 1024 tokens or 96 MiB at 2048 tokens, before the final output. The changed reduction order needs fresh numerical validation. Existing grid parallelism is already substantial, so source routing alone does not justify prioritizing it over the smaller swizzle check.
- MLX's register-fragment matmul uses a persistent f32 accumulator and explicit K loops [in gemm_nax.h](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/kernels/steel/gemm/gemm_nax.h#L45-L98). Its 16-by-32-by-16 primitive enables relaxed precision [in nax.h, lines 401–411](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/kernels/steel/gemm/nax.h#L401-L411). The installed public MPP header describes that flag as allowing accuracy to be sacrificed for performance. Clef leaves it false. Porting this implementation would change several factors and cannot be assumed to preserve our f32 contract or outperform the current full-K operation.
- MLX's narrow-output NAX route explicitly excludes f32 output [at lines 994–999](https://github.com/ml-explore/mlx/blob/06eb7483f03bca49a80e596f4089d02a507a2cf9/mlx/backend/metal/matmul.cpp#L994-L999); it is not a drop-in path for Clef's half-input/f32-output projection. Its quantized kernels also use their own scales/biases format, which is not direct GGUF Q4_K compatibility.

The separate MPS grouped-LUT work is still the higher-impact representation hypothesis: exact half-valued decode during full-K multiplication could reduce persistent weight bytes without our rejected serial decode loop. Its tiny public-API capability check passing does not establish real-weight precision, throughput, or end-to-end acceptance. This review does not duplicate that experiment or infer a clock, thermal, QoS, or bandwidth cause from the existing timings.
