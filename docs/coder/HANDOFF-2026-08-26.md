# 2b. How to run both deploys — the whole procedure

Two different pipelines. They are not the same thing and neither is one
command.

## A. The backend deploy (`openagents.com`, Elixir → Cloud Run fleet)

**Authority: `docs/operations/production-deploy-runbook.md`.** Read it whole
before acting. Every other operations doc is reference; that one is the
checklist. Do not improvise a shortcut around a step.

```
push candidate to forge main
  → release gate (exact SHA)
  → immutable image build and publish
  → promote
  → migration job
  → rolling replacement (structural) or direct load (BEAM-only)
  → settle the target
  → verify production
```

**Two invariants govern everything:**
- **One exact Git SHA.** Gate receipt, image, promotion and rolling replacement
  all name the same full SHA. **If `main` advances, you have a new candidate
  and you start over at the gate.**
- **One immutable image digest.** Deployment identity is a `sha256:` digest,
  never a mutable tag.

The roll itself:

```sh
ops/deploy/release-to-production.sh <full-git-sha>
```

It is written to **refuse rather than guess** — a revision with no passing gate
receipt, an image whose embedded revision is not the Git SHA, or a node that
returns on the wrong revision each stop it where it stands. *"A half-rolled
fleet that reports success is worse than one that stops."* **If it refuses, do
not work around the refusal.** Report it.

Promotion has no button: there is no control on `/admin/forge` that does it.
The script drives the same operator API through `rpc` on a node, so the whole
release runs from a terminal.

**Workstation prerequisites (runbook §0 — check before starting, the gate fails
fast):** `jq`, `mix`, `npm`, `docker`, `git` ≥ 2.38 (the git-plane tests need
`git merge-tree --write-tree`), `terraform` >= 1.11 < 2.0, `npm ci --prefix
assets` (the relup stage runs `mix assets.deploy` and needs
`assets/node_modules`), and a local PostgreSQL with the `vector` extension plus
a disposable database the gate may trash.

For any `gcloud`, prefix
`CLOUDSDK_CONFIG=/Users/christopherdavid/work/.secrets/gcloud-sa-config` — the
pre-authenticated automation service account. **Never** attempt interactive
`gcloud auth login`; never run `/usr/bin/security` or any Keychain probe (each
probe opens a blocking dialog and makes unattended work impossible).

**Do the work in the canonical checkout, not a worktree** — the gate builds
assets and needs the repo's `assets/node_modules`.

## B. The CLI binary release (`openagents` monorepo → release bucket)

Entirely separate from A. Ships a native binary; touches no server.

```sh
ops/release-cli.sh --version <X.Y.Z> [--targets "..."] [--publish] [--channel NAME]
```

The installer contract it fills, under `https://openagents.com/releases`:

```
<base>/<channel>                       a bare version string
<base>/openagents-<version>-<platform> the executable, no extension
<base>/SHA256SUMS-<version>            "<sha256>  <name>" per line
```

**All seven platforms:**

| platform | rust target | builder |
| --- | --- | --- |
| `macos-aarch64` | `aarch64-apple-darwin` | cargo |
| `macos-x86_64` | `x86_64-apple-darwin` | cargo |
| `linux-x86_64` | `x86_64-unknown-linux-gnu` | zigbuild |
| `linux-x86_64-musl` | `x86_64-unknown-linux-musl` | zigbuild |
| `linux-aarch64` | `aarch64-unknown-linux-gnu` | zigbuild |
| `linux-aarch64-musl` | `aarch64-unknown-linux-musl` | zigbuild |
| `windows-x86_64` | `x86_64-pc-windows-gnu` | zigbuild |

The two Linux libc flavors are **separate platforms, not variants**: the gnu
build is dynamically linked and names a glibc loader a musl system does not
have; the musl build is static-pie and names no interpreter. Each artifact is
read back and matched against an expected `file` signature before staging —
the anti-forgery check, because cross-compilation fails in ways that still
leave a runnable binary at the output path (a stale artifact from a previous
target, or a host build that silently ignored the requested triple).

**Single-target (the current owner instruction, ~82 seconds, still signed and
notarized):**

```sh
ops/release-cli.sh --version 0.0.4 --targets "macos-aarch64" --publish --allow-partial
```

**Seven-target (owner: at 0.1.0), ~15 minutes, and the only shape that may move
`stable`:**

```sh
ops/release-cli.sh --version 0.1.0 --publish --channel stable
```

**Flags and their guards:**
- `--allow-partial` — publish with platforms missing. Required for any
  single-target build; the script refuses otherwise (`release-cli.sh:363`).
- `--channel NAME` — point a channel at this version *after* publishing.
  **The script refuses `--channel` alongside a partial build** (`:380`), which
  is exactly why 0.0.4 cannot move `stable`: pointing the channel at an
  Apple-Silicon-only build hands every other platform a bare download failure.
- `--allow-prerelease-channel` — let a version with a `-suffix` claim a
  channel. A version containing `-` is treated as a prerelease (`:104`).
- `--skip-notarization` — macOS artifacts without Apple notarization. Do not
  use for anything published.

**`stable` currently resolves to 0.0.2 while 0.0.3 is published**, so the
installer hands out a build behind what is being tested. That is deliberate
and stays true through 0.0.4.

Signing and notarization details: `apps/oa-updates/docs/release-signing-runbook.md`
(ed25519 release key, Apple Developer ID `HQWSG26L43`).

**If Flash cannot resolve its id, it must refuse loudly.** Removing `Auto` did
not remove the problem `Auto` avoided — it moved the whole load onto catalog
resolution. A Flash that silently falls back to a compiled-in id reintroduces
