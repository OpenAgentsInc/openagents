# The chat router's CLI route on a labeled set

Issue [#9926](https://github.com/OpenAgentsInc/openagents/issues/9926)
implements route 7 of the [chat router design](../design/2026-09-28-chat-router.md),
"The CLI route: descending the command tree", behind the router's
`CliRoute` seam (`crates/coder/src/router/seams.rs`). This page records how
the route did on a labeled set of 62 requests, what it costs in time, and
what is not yet wired.

## What was built

- `crates/coder/src/cli_route/tree.rs` and `usage.rs`: the `CommandTree`,
  read from the `openagents` command's own help text. `openagents-cli`
  (`src/tree.rs`) hands over the top-level table and every group's `USAGE`
  with the effect and phone placement each module declares beside its
  `USAGE`, and a test fails when the bundled `tree.json` differs from what
  the live help builds. The tree holds 29 groups and 183 commands (`xp` is
  listed once, as `verse xp`).
- `descend.rs`: one Jev Choice per level over exactly that node's commands
  plus `none`. The level-0 description of each group lists its commands with
  the first words of their summaries, so the judge reads what a group can do
  (`CommandRoute::groups` hands the same descriptions to the router's
  `cli_group` question).
- `params.rs`: hosts, workspace labels, and usage-line enums are selected by
  Jev among candidates; free text is written by the chat model as a JSON
  object whose keys come from the usage line; the command must then pass
  `coder::argv::Args`, the parser `openagents` itself runs (moved from
  `openagents-cli` so both use one copy), and the usage's required values,
  known options, numbers, and enums.
- `gate.rs`: the router's effect gate, plus the owner's phone list: only
  `computer list`, `show`, and `workspaces`; `verse who`, `quests`, `board`,
  and `xp`; `kb search`; `cap`, `prg`, and `ext list`; and `session list`.

## How it was measured

```sh
set -a; . ~/work/.secrets/coder-local-door.env; set +a   # the gateway door
cargo run -p coder --example cli_route_eval
```

`crates/coder/examples/cli_route_eval.rs` runs every row of
`crates/coder/src/cli_route/labeled-v1.json`: it asks the level-0 group
question alone (as the router's `cli_group` would), descends from the group
at p ≥ 0.60, and scores the outcome. Jev is `jev-latest` through the decision
profile; free text is written by `google/gemini-3.8-flash` through the Vercel
AI Gateway, the chat worker's own door. Phone rows have no computers (the
worker never learns them); desktop and terminal rows have two.

The set: 36 rows that expect a command (25 phone, 11 desktop or terminal), 2
that expect the route to ask which computer, and 24 that must get no offer:
money, secrets, grants, publishing, read-only commands off the phone list,
and messages that are no command at all.

## Results

Three runs on 2026-09-28, on the final code:

| Metric | Run 1 | Run 2 | Run 3 | Target |
| --- | --- | --- | --- | --- |
| Proposal validity (a proposal that parses, with required values, for rows that expect one) | 34/36 (94.4 %) | 33/36 (91.7 %) | 33/36 (91.7 %) | ≥ 90 % |
| Proposal correct (the labeled command and values) | 94.4 % | 91.7 % | 91.7 % | reported |
| Asked for the missing computer | 1/2 | 1/2 | 2/2 | reported |
| No offer where none is labeled | 24/24 | 24/24 | 24/24 | reported |
| `spends` or `secret` offers | 0 | 0 | 0 | 0 |
| Phone offers off the owner's list | 0 | 0 | 0 | 0 |
| Group correct (level 0) | 94.7 % | 94.7 % | 94.7 % | ≥ 95 % (design) |

Every proposal that came back was valid; the misses are all no proposal at
all. The misses, and why:

- "which of my computers are online?" goes to `reach presence` (the host's
  presence sample), a fair reading that is off the phone list, so nothing is
  offered.
- "show me the details of my Mac Studio" picks `computer show` at p ≈ 0.45,
  under the level's 0.50 floor, in some runs.
- "what extensions are listed on the relay?" sometimes picks the `relay`
  group, whose commands do not list extension records.
- "show me my studio", in the terminal, is judged no command.

The first version, with bare group summaries and a premise that the user
names the program, reached 55.6 % validity: the level-0 question missed
"who is in the plaza?", "what level am I?", and every request that did not
sound like a command. Listing each group's commands in its description is
what moved it. The labels were not tuned between runs, except to accept
`verse board` for "what level am I?", since the help says the board shows
"this identity's level".

## Time

From the start of the descent to the outcome, on a development Mac:

| Rows (all three runs) | p50 | p95 |
| --- | --- | --- |
| No model call: 165 rows whose outcome needed no typed text | 341 ms | 520 ms |
| A model fill: 21 proposals of `kb search`, `verse say`, or `computer tail` | 2.9 s | 5.4 s, one at 10.5 s |

The router bounds the seam at `CLI_BUDGET` (3 s), so a slow fill falls back
to the model's reply. A proposal that needs typed text will often miss that
budget on the gateway's Gemini Flash lane; a faster fill model or a larger
budget for `kb search` is a follow-up measurement, not a change here.

## Running a proposal: what exists and what does not

`cli_route::execution` names the path for each place, and all of them
exist today:

- `computer list`, `show`, and `workspaces` on the phone: the phone's own
  `coder_computers::live` client, which `openagents computer` also uses.
- Every other phone command: `openagents --json ARGV` on the user's
  computer through NIP-HOST `terminal.open` and NIP-TERM, the path
  `openagents computer exec HOST -- …` takes. The grant needs the
  `terminal` right.
- The desktop and the terminal: `openagents --json ARGV` as a child
  process, as `openagents mcp serve` runs each tool call.

Not built here: the phone's tap handler for a `cli` offer
(`crates/openagents-mobile` is outside this change), the worker's wiring of
`CommandRoute` into its `Seams` (the router's integration step), and a way
for the phone to hand its computers to the route. The `context` the phone
sends carries no host names, so on the phone a command that needs a `HOST`
is answered "which computer" instead of a proposal.
