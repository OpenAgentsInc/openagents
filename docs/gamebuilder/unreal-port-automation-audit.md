# Unreal to GameBuilder: import and port automation audit

2026-11-17. Audited GameBuilder `f17e5ec` and its OpenAgents pin `3109f42ed9`. The [original SPLICEBOTS port notes](splice-bots-port.md) are the history of the native integration. This audit asks what another project's ZIP could produce without someone writing a new port.

Milestone 1 now has a local command. See [Unreal shipping ZIP previews](unreal-preview.md) for its input contract, report fields and replay instructions. The findings below describe the baseline before the command was added.

## Finding

**We have a reproducible Unreal level asset converter and a bespoke SPLICEBOTS port. We do not have a ZIP-to-GameBuilder port system.** The native game's world pack was made from a source project opened in Unreal Editor. The characters were built from separate source art. Its gameplay combines an earlier Coax game, source rules translated into Coax, and integration written specifically for SPLICEBOTS. The shipped ZIP contributed useful cooked-content evidence and unusually rich loose data, but it did not generate the game that Play runs.

The closest deliverable is one command that inventories a ZIP and makes a **reported scene preview** from a supported Unreal export. An **editable GameBuilder project** is a separate milestone. It requires a shared scene and asset path into the editor and Play. A **verified game port** needs a source export that carries gameplay semantics, a compiler for a defined subset of those semantics, compatible runtime systems, and tests for the game's actual flow. A command can accept any ZIP for inspection and give a precise answer about coverage. Full conversion can only be promised against an explicit input and runtime contract.

### What this audit verified

- **Editor bundle to native world pack.** Ran the pinned level converter twice against the existing editor bundle, pinned plan, and `--two-tone Lit=Shade --shade-auto ShadeAuto:ShadeShare:ShadeTint`. Both outputs matched the existing native world resource byte for byte. The result is 61,017,116 bytes, with 10 maps, 5,026 packed placement rows from 5,084 bundle placements, and 2,487 colliders. It reports 58 skipped placement rows, 21 skipped lights, 14 refused textures and 889 producer skip records. These are several layers of counts. The smaller number seen in native Play reflects its chosen route and filtering. This replay starts at the exported bundle and does not establish whether repeated Unreal Editor exports produce identical bundles.
- **Cooked bundle to preview pack.** Converted the existing cooked bundle at the pin. It passed pack readback with 8 maps, 4,901 packed placement rows from 4,961 bundle placements, and 2,929 colliders. The bundle has 87 static mesh rows, 15 textures, no skeletal mesh, animation or audio rows, and 1,147 skip records. The converter carried 10 textures. The historical comparison reports 4,511 matching placements out of 4,861 in its comparison scope. Those comparison counts and the whole-bundle totals use different scopes. They measure scene recovery, not gameplay or release parity. [Jam comparison][jam-plan]
- **Original shipping ZIP to preview pack.** In a fresh private directory, unpacked all 178 files with path normalization after Info-ZIP warned about Windows separators and returned nonzero. Ran the local UE 5.9 `UnrealPak` on the game container, then the pinned cooked reader with the generated engine schemas and an explicit empty project argument. It read 1,012 packages, yielded eight maps and 4,475 placements, and recorded 996 skip rows. The level converter read back a 33,954,360-byte pack with 4,415 placements and 2,443 colliders. This used no SPLICEBOTS source project and no model calls in the conversion steps. It recovered 486 fewer placements and colliders than the previous cooked bundle produced. That comparison is evidence of the lower-coverage route that works from the ZIP plus the engine toolchain. It does not isolate the cause of every difference between the two runs. Pack readback is structural verification. No visual or gameplay parity was measured for the cooked output.
- **Automated checks.** The pinned Coax test entry points for `unreal-level-import`, `unreal-cooked-export`, `unreal-rig` and `bundle-diff` passed 316, 224, 364 and 173 checks respectively, including shared library checks in more than one entry point. The upstream `jam-run-check` passed on the existing private editor-derived world pack, with the character and table packs supplied. It exercised the adapted game's route, charge point, harvest, chest, boss, exit, jump course, jetpack, cast and table bindings. GameBuilder's `scripts/build.sh` also passed. This audit did not qualify an iOS or macOS gameplay journey or a public deployment.

The source-free cooked replay used these stages after unpacking into a fresh, private staging directory. `ENGINE_SOURCE` is the root of the matching built Unreal source tree. Run the Coax tools from the pinned OpenAgents tree. The last empty argument overrides the cooked reader's default project path. This sequence is a reproduction of the preview, with one known unencrypted IoStore container selected by hand.

```sh
"$UNREALPAK" IoStore "-FindAndExtract=$GAME_UTOC" '-PackageFilter=*' "-OutPath=$STAGE/extract"
coax/web/tool.sh metaverse-engine/tools/unreal-cooked-export.coax \
  "$STAGE/extract" "$STAGE/cooked.aimport" "$ENGINE_SOURCE" ''
coax/web/tool.sh metaverse-engine/tools/unreal-level-import.coax \
  "$STAGE/cooked.aimport" "$STAGE/pack"
```

The artifact details above describe private inputs already held on the workstation. Keep those inputs, derived art, private traces and the accompanying digests out of public fixtures and evidence.

## What each ZIP can promise

ZIP is a transport. The importer must inspect the files inside and declare what it has before picking a route.

| Input | Expected endpoint | Conditions |
| --- | --- | --- |
| **GameBuilder-compatible Unreal export ZIP**, generated by an editor commandlet on a supported version | Editable project and a verified port for a declared capability profile | Export maps and dependency closure, original or baked assets, game rules and bindings in supported portable forms, rights metadata and reference tests. Require the declared semantics to compile and every mandatory test to pass. |
| **Source project ZIP** with `.uproject`, source, assets, config and required plugins | Use the matched Unreal Editor export worker. A scene is feasible when the project loads. A verified port depends on behavior coverage. | Missing plugins or external assets are explicit dependencies. Build and load only in an isolated worker or run export on the creator's own machine. Arbitrary C++ and native plugin behavior need a supplied portable implementation or reviewed adapter. |
| **Cooked shipping ZIP** with Pak or IoStore containers, often a Windows executable and loose files | Best-effort recoverable scene, assets and typed data. A verified port is possible only when a compatible sidecar supplies the needed semantics and evidence. | Platform, engine build, container variant, codecs, generated schemas, chunk layout and input rights determine what is readable. Use official tooling and credentials the owner provides where needed. Epic's cooker optimizes for the target runtime and omits unused content. No unpacker can recover material or rules data absent from its input. [Epic packaging documentation](https://dev.epicgames.com/documentation/unreal-engine/packaging-your-project) |
| **Asset-only ZIP** containing interchange exports, or a loose data ZIP | Asset library and any scene described by supported layout data | glTF/GLB/FBX, textures and audio can carry content, while object roles, animation state, map flow and interaction need their own declarations. |

Return one of four outcomes with evidence, `verified-port`, `editable-import`, `preview` or `blocked`. A verified port may contain explicitly accepted differences. It may never hide an unresolved required feature behind a placeholder, dropped row, stock character or exit code 0. A port profile states supported feature families, targets and parity tolerances. Its report lists source objects and dependencies as exact, converted, approximated, substituted, intentionally excluded or unresolved. Each material change needs a source ID, reason and test or other evidence. Keep the distinction between a project-specific policy choice and an engine limitation.

## Systems to build

Implement shared Unreal conversion and runtime primitives in OpenAgents. Put the GameBuilder command, project admission, editor integration and user-facing import report here. Reuse the existing formats, renderer, physics and script host. Make any additions to shared formats upstream, then pin them here. The reverse-direction `metaverse-engine/tools/unreal-import.coax` is Aethyr **into Unreal** and is not an existing route into GameBuilder. Its export-and-test orchestration is useful precedent. These systems have different completion criteria. A better cooked mesh reader advances scene coverage. It cannot close the editor, gameplay, or parity gaps by itself.

## When AI is allowed

The default import must run offline with respect to model services, with zero model calls. A synthetic fixture should prove it runs with no model credentials. Deterministic stages should classify missing input, resolve references, match supported nodes and named roles, convert assets, enforce constraints and run checks. A missing codec, unsupported class, absent source or ambiguous map selection first gets a concrete typed diagnostic. None is a reason to ask a model to invent missing information.

After deterministic inspection, an opt-in assistant may propose a narrowly scoped mapping when intent is genuinely ambiguous, or draft a reviewed adapter when a reachable behavior has no supported lowering. Give it the smallest authorized input and keep source code, raw assets and secrets out of remote model calls by default. A proposal carries the exact source IDs and evidence, a typed diff or adapter, unresolved questions and a replay test. Never allow model output to directly execute, admit an archive, publish a project, change rights metadata or declare parity. Compile, validate and apply only the approved result. Save it as reusable code or declarative data. Replaying a completed import uses the approved artifacts and makes zero calls.

Track deterministic coverage separately from verified parity. Count required behaviors supported and exercised, blocking exceptions by category, AI calls per import, manual interventions, tool and target costs, and the fraction of repeated imports that reuse existing adapters. Report counts against an explicit inventory so dropping a feature cannot improve the score.

## Delivery sequence and exit gates

1. **One command for a scene preview.** Wire archive classification, a supported cooked ZIP route, existing `.aimport` conversion and private output reporting. Reuse the reader as it exists before adding codecs or trying game translation. Gate on a synthetic ZIP and the original SPLICEBOTS shipping ZIP from a fresh location. Record the independently supplied engine tools, any separate schema dependency, all missing rows and the pack digest. Repeated runs with the same normalized input and pin must reproduce the pack and canonical report. Invalid and unsupported fixtures must get specific reasons. This is the nearest milestone. The parsing stages exist, while orchestration, classification, quality gates and generic delivery do not.
2. **One command for an editable project.** Start with a small source export profile covering static geometry, material, lights, starts, blocking collision and a supported character. Import into normal GameBuilder storage, open the project through game selection, edit an imported entity, save, undo and reopen, then run Play on the edited scene. Run it on an unrelated fixture with no SPLICEBOTS code, plus the private editor pack. Prove reimport preserves creator edits or reports conflicts. This needs product and runtime work beyond the converter.
3. **One command for a verified game in a narrow profile.** Export a reference game such as a traversal and pickup course with a checkpoint, a HUD and a win event. Ship the behavior graph, declare the nodes and tests in the export, and lower them with zero AI and zero project-specific code changes. Compare the Unreal and GameBuilder traces on all claimed targets, then make a deliberately unsupported mandatory node fail admission as a verified port. Repeat on an independently authored game in the same profile so the result is evidence of a general capability.
4. **Expand by measured game features.** Bring in animation graphs, inventory, world transitions, combat and other feature families as separate extensions. Qualify SPLICEBOTS through the same path, migrating existing hand-authored rules and adaptations into declared compatible inputs where necessary. Its gate covers the source reference's agreed objectives and supported route, inventory, Digger, vehicles, interaction, progression, audiovisual tolerances, save/reentry and target inputs. Specify which mechanics come from the shipped Unreal baseline versus later source and which intentionally differ. A second unrelated game must exercise each advertised profile. A SPLICEBOTS-specific adapter can be a legitimate input, but using it cannot prove general C++ or Blueprint portability.

A future job could look like `gamebuilder import unreal GAME.zip --profile PROFILE --target macos --out OUTPUT`. That command is a proposed interface. Its output should be a loadable project revision when the selected profile succeeds, plus a reproducible manifest, conversion report and verification evidence. For a lesser result, the report tells the creator what came through, which baseline it was compared against, which tests ran, and the smallest missing input or system that would move it to the next outcome.
