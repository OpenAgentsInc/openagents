# Glossary

This glossary defines the terms used across OpenAgents: Coder and its research
harnesses, decision models and services, measurement, evidence, plugins and
the programs and extension packages they ship as, Nostr protocols, markets,
and world interfaces. It starts with the [one vocabulary](#one-vocabulary-what-you-can-add)
for what people add: plugins. It also explains
historical names that still appear in the retained transcripts.

Implementation status is checked against this repository as of **2026-09-29**.
The linked owning contract or source file supplies the detailed rules.
Cloud computer and repository environment entries were reviewed on
**2026-10-08** against the [managed computer plan](cloud/managed-computers.md).

| Status | Meaning |
| --- | --- |
| **Implemented** | Code provides the specific behavior described. This does not imply deployment, universal compatibility, or demonstrated benefit on every workload. |
| **Partial** | Code provides part of the contract; the definition identifies the important remaining boundary. |
| **Designed** | A repository specification describes the intended behavior, but the complete named feature is not implemented. |
| **Defined** | An analytical or architectural concept used in the repository. It is not itself a claim that a runtime feature shipped. |
| **Historical** | A product name, implementation, or idea from the retained archive. Its presence here does not establish a current implementation in this workspace. |
| **Retired** | A previous implementation is no longer in this repository; the entry identifies its replacement or disposition. |

A model confidence, signed event, receipt, process exit, test verdict, accepted
artifact, and confirmed payment establish different things. Each needs its own
scope and evidence. A specification or passing parser fixture establishes less
than an operating service.

## One vocabulary: what you can add

**A plugin is anything you add to OpenAgents.** It is the one word for it in
the apps, the chat, the `openagents plugin` command, and the
[how-to docs](plugins/README.md), decided 2026-10-01
([#10087](https://github.com/OpenAgentsInc/openagents/issues/10087)). You
write a plugin, and a plugin can contain:

- **skills**: instructions the agent reads;
- **workflows**: typed, step-by-step programs a host runs;
- **knowledge**: cited reference entries;
- **Wasm**: sandboxed WebAssembly code that performs a bounded operation,
  the only executable code a plugin can carry (native executables stay
  host-owned, per [NIP-EXT](../nips/openagents/NIP-EXT.md));
- **tests**: the test set that shows whether the plugin helps.

Project map is a plugin: a workflow that runs one piece of Wasm, with its
tests. Coder and the engines (Codex, Claude Code, Grok Build, OpenCode, and
Devin) are not plugins; they are the agents plugins plug into.

The specifications keep precise terms beneath the one word. Read the table
from the word people use down to the term a specification or the code
uses:

| People say | Specifications and code say | What the precise term adds |
| --- | --- | --- |
| Plugin | The contribution, shipped in an **extension package**: a [NIP-EXT](../nips/openagents/NIP-EXT.md) release, signed by its publisher. Each part in it is a **component**. | The package is the container, never the thing; a component is NIP-EXT's word for one entry in a package, with a `kind`. |
| Workflow | A **program** ([NIP-PRG](../nips/openagents/NIP-PRG.md)), carried as a `program` component | A typed workflow of named steps that names its sources, operations, and children by pinned identity and grants nothing. The default part to write; a context-construction policy is one. |
| Wasm | A **Wasm guest** that `crates/plugin` runs, carried as a `plugin` component | The wire component kind `plugin`, the `crates/plugin-*` guest crates, and *plugin host* and *plugin packet* name this part only, never the whole plugin. |
| Skill | A `skill` or `guidance` component; from chat, `CODER_GUIDANCE` and its digest | Guidance with no authority and no code. |
| Knowledge | A **knowledge entry** ([NIP-KB](../nips/openagents/NIP-KB.md)): a `3190` version with a `30190` head | Published beside a package, not inside one. |
| Tests | An **eval suite** of cases and graders, released as an `eval-suite` component | The phone says **test set** and **test**. |
| Test result ("passed 5 of 6 with it, 2 of 6 without") | A **capability claim**: a with-and-without measurement, published as a [NIP-EVAL](../nips/openagents/NIP-EVAL.md) `3189` result | The claim's key, evidence, and verdict policy ([test-time capabilities](#test-time-capabilities)). |

**Capability** names a measured effect, never a thing people add. A plugin
is a *candidate* until a test result, a capability claim, says what
admitting it changed; a capability in the measured sense is what a claim
establishes, so the research question is "does this plugin add
capability?" ([the essay](essays/2026-09-29-test-time-capabilities.md)).
In the security sense the word is **grant** or **authority**, and what
[NIP-CAP](../nips/openagents/NIP-CAP.md) calls a capability definition is
an **operation description**, which grants nothing. *Tool* never names a
plugin or any part of one: in AI products a tool is something a model calls
by name, and a plugin's Wasm is chosen and run by workflows and typed
decisions. The word survives for a model's tool call in a transcript and
inside proper names. A Claude Code or Codex package under `plugins/` is a
*client plugin package*, always named in full.

| Part | What it is | How it ships | How it's measured | Example |
| --- | --- | --- | --- | --- |
| Workflow (program) | A typed workflow of named steps a host interprets ([NIP-PRG](../nips/openagents/NIP-PRG.md)); it names sources, operations, and children by pinned identity and grants nothing. | A `program` component in an extension package | A [plugin test](#extensions): the same tests with the plugin and without it | `programs/evidence-guests.json`, and the workflow that runs Project map |
| Wasm | A Wasm guest performing a bounded operation, run by `crates/plugin` under a profile, fuel, and memory limits | A `plugin` component in an extension package, with a build receipt | The plugin test of the workflow that runs it | Project map's Wasm, `crates/plugin-repo-map` |
| Skill | Guidance an agent reads before a task: a `SKILL.md` guide, or the plain-language instructions a plugin made in chat is | A `skill` or `guidance` component in an extension package; from chat, `CODER_GUIDANCE` and its digest | A plugin test | The instructions a person drafts in chat |
| Knowledge | A versioned, cited Markdown reference: a method, edge case, slip, environment note, or how a command is used ([NIP-KB](../nips/openagents/NIP-KB.md)) | A NIP-KB `3190` version with a `30190` head, not a package | The same with-and-without report, on the entry (`microcoder kb evidence`) | An entry under `knowledge/` |
| Tests | Cases (`prompt.md`, graders, fixtures) under the plugin's `evals/` | An `eval-suite` component in a NIP-EXT release | They are the measurement; a second test set someone else wrote validates a result | `crates/plugin-repo-map/evals/` |

Delegates ([test-time delegation](#test-time-capabilities)) and typed
judgment ([Jev](#decision-models-and-runtimes)) are measured too, but the
system supplies them; nobody adds one as a plugin yet.

## Terms that are easy to confuse

| Distinction | How this glossary uses it |
| --- | --- |
| Coder, Coder One, Microluna, Microcoder | Coder is the product/runtime; the others are configurable agent components or research harnesses with different execution and recording paths. |
| OpenAgents chat, Coder | Chat with OpenAgents is the hosted assistant that speaks as "we" and needs no computer; Coder is the coding agent it dispatches to a connected computer, only on a tap. |
| Chat, project, computer, execution environment | A chat retains the conversation; a project scopes authorized repository work; a computer executes it; an execution environment specifies and records its runtime and materialization. Selecting a source or runtime grants no execution authority. |
| Account workspace, checkout, workspace resource namespace | An account workspace owns membership and service access. A checkout is working source on a computer. A workspace resource namespace is the designed identity for coordinated artifacts and checkpoints. These are separate scopes. |
| Decision model, generator, executor | A decision model answers typed questions; a generator produces open-ended output; an executor performs admitted work. Selecting one does not automatically authorize the others. |
| Decision gateway, Vercel AI Gateway, Pro inference door | The decision gateway (`crates/gateway`, [its guide](decision-models/service/gateway.md)) admits `POST /v1/systemone`. The Vercel AI Gateway (`ai-gateway.vercel.sh`) is a Jev and chat upstream. The [Pro inference door](gateway/README.md) serves three GPT-5.6 chat models at `pro.openagents.com`. Its Stripe LLM proxy catalog is larger than that allowlist. The Metronome token-billing price table is neither list. |
| Plugin, capability, program, Wasm, skill, knowledge entry, extension package | A plugin is what a person adds: its skills (guidance), workflows (programs, which compose work), knowledge (cited references), Wasm (a guest performing one bounded operation, the wire component kind `plugin`), and tests. A capability is what a test result, a capability claim, establishes a plugin adds; it is never the name of the thing. An extension package is the container a plugin ships in, and a component is an entry in it. Voyager's skill is executable Lua; a client plugin package is a Claude Code or Codex package under `plugins/`, always named in full. |
| Operation description, binding, grant | An operation description (NIP-CAP's capability definition) describes an interface, a binding connects it to a host, and a grant supplies authority, the security sense of *capability*. Discovery and installation grant nothing. |
| UI intent, activation, execution authority | An activation identifies a current control; the validated view supplies its typed application intent. The application must separately check authority before causing an effect. |
| Trace, evidence, receipt, journal | A trace records execution; evidence supports an assessment; a receipt attributes a call or effect; a journal records durable lifecycle state. None guarantees all the others exist. |
| Verification, integration, acceptance, settlement | Checking the result, adopting it, accepting contractual work, and confirming payment are separate decisions. |
| Knowledge, method, component | Knowledge supplies cited guidance; a method registry supplies executable definition-based checks; a component is a reusable part of agent behavior. A source task is not independent evidence for its own contribution. |
| Benchmark, plugin test (extension eval) | A benchmark (Terminal-Bench, CoderBench) measures Coder on a fixed task set; a plugin test, the extension eval in the specifications, measures one plugin's effect on Coder with and without it over a test set written for that plugin. The Gym's product loop runs plugin tests. |
| Signature | A cryptographic signature authenticates an event; a semantic AI signature defines an operation's meaning. An artifact signature identifies a particular served/trained artifact under its own contract. |
| Test-time compute, test-time capability | Test-time compute is extra computation spent while a model answers (longer reasoning, sampling, search); a test-time capability is an ability gained or lost by admitting a component to the run, stated as a capability claim: a key (which identified subject, admitted to which baseline agent, on which task distribution and sample, under which environment, grant, and measurement), the evidence records on it (each run's effect estimate with its uncertainty), and the written policy that turns them into a verdict. Reports are evidence; claims summarize effects; adoption is policy. See [the essay](essays/2026-09-29-test-time-capabilities.md). |

## Agent infrastructure

The [general agent architecture](agents/README.md) separates shared contracts, domain-specific behavior, and the host that enforces them.

| Term | Status | Definition |
| --- | --- | --- |
| OpenAgents | Partial | The open-source agent infrastructure in this repository: typed decision services, Coder, measurement, execution, extensions, and Nostr protocols. The broader interoperable product and commercial network remain under development. |
| General agent infrastructure | Partial | Shared identity, decision, workflow, evidence, authority, execution, coordination, and evaluation mechanisms. Coder is the coding specialization; another domain needs its own bindings and acceptance evidence. |
| Domain profile | Designed | An assembly of sources, resource semantics, operations, guidance, policy, and evaluation for a class of work, such as coding or research. It is not a new event kind or an execution grant. |
| Host | Defined | The process and operator-controlled configuration that own execution, credentials, admission, resource limits, and effects. A model or package proposes behavior within that boundary. |
| Operation | Partial | An action with typed inputs and outputs, declared effects, limits, and an execution binding. Native actions exist; the unified extensible operation registry is a [target contract](extensions/architecture.md). |
| Resource | Designed | An object or effect destination identified within its authoritative system and tenant/account scope, such as a repository file, document, dataset, or service record. Each domain defines its version and update semantics. |
| External observation | Designed | A versioned capture from a pinned source adapter, with explicit consistency and completeness limits. Captured bytes do not establish an atomic live snapshot; see [shared contracts](../nips/openagents/contracts.md#external-observations). |
| Effect | Partial | An operation’s consequence: reading, writing, disclosure/network access, subprocess creation, delegation, or spending. Local [program authority](coder/guides/program-authority.md) uses these categories; a granted category alone does not enforce isolation or a monetary ceiling. |
| Integration | Defined | Authorized adoption of a result into its intended destination, with fresh base/state checks. Producing an artifact, verifying it, and integrating it are separate stages. |
| Reconciliation | Partial | Determining what actually happened after interrupted or ambiguous execution before deciding whether work may resume or retry. Local [reconciliation rules](../crates/coder/src/reconcile.rs) exist; external systems must supply their own effect-confirmation guarantees. |
| Pro inference door | Partial | The chat service at `pro.openagents.com`. It admits `gpt-5.6-sol`, `gpt-5.6-terra`, and `gpt-5.6-luna` and forwards them to Stripe's LLM proxy. The proxy's own catalog, `GET https://llm.stripe.com/v1/models` with `stripe_ai_gateway_support`, is larger than that allowlist. The running service is deployed. The `pro-gateway` crate is still in the private `pro` repository, not in this workspace. See [the door guide](gateway/README.md). |

## The Coder product suite

The [product-suite plan](coder/design/typesafe-product-suite.md) treats these as interfaces and execution locations around one task owner. Historical demonstrations do not establish current availability.

| Term | Status | Definition |
| --- | --- | --- |
| Coder suite | Partial | One coding product spanning terminal/headless operation, inspection, owned or managed workers, and proposed mobile, web, and computer-control views. Coder One, Microluna, and Microcoder are implementation and research components, not separate customer brands. |
| Coder Cloud | Partial | Native admitted operator jobs, Boat/GCE placement, original output, reviewed controls, and web observation exist. The [web specification](cloud/coder-cloud.md) and [managed computer plan](cloud/managed-computers.md) also require reusable environments and persistent computers. Operator admission and decision-service billing do not establish customer compute entitlement or retail launch. |
| Coder Mobile and Coder Web | Partial | Thin clients intended to observe, steer, approve, and cancel host-owned tasks. The [Rust mobile prototype](coder/design/rust-mobile-feasibility.md) has bounded simulator/emulator feasibility evidence, not a released task-control app. The [Coder iOS/Android reader](coder/guides/mobile-readonly.md) adds paired read-only Codex/Claude history, an encrypted device cache, and foreground updates. Verse opens first; a world computer exposes QR pairing and the chat reader. Writing remains separate. The separate [OpenAgents app](#the-openagents-app-and-chat) is the current phone product: it chats with OpenAgents and starts Coder on a connected computer. Admitted Cloud web views exist; general host-task web delivery remains planned. Older web implementations are historical references. |
| CoderOS / Coder OS | Designed | The planned opinionated computer environment and admitted application/device controls around Coder. The historical Linux distribution is not retained as a current product here. |
| Task owner | Partial | The principal whose authority establishes a task. Product discussions also use the term for the implemented [local execution owner](coder/runtime/task-owner.md). [NIP-CTRL](../nips/openagents/NIP-CTRL.md#encoding-principals-and-limits) distinguishes the owner principal from its admitted controller; local execution does not establish distributed ownership. |
| Task controller | Partial | The admitted host that serializes a durable task’s state and control requests under the owner’s authority. The local task owner exists; [scoped Nostr control](../crates/coder-control/src/lib.rs) maps an exact task and controller generation to it. General execution transfer and full client products remain separate work. |
| Trusted-device pairing | Partial | An owner-authorized link between a client key and a task controller, with bounded observation, steering, and cancellation rights. [CTRL primitives](../crates/nostr/src/control.rs) and the [bounded host](../crates/coder-control/src/lib.rs) implement a scoped path. Pairing grants neither approval nor spending; native mobile delivery remains incomplete. |
| Execution transfer | Designed | Moving task execution to a newly admitted host with exact artifacts, reconciled effects, and fenced ownership. Reconnecting a client or copying a transcript is insufficient. |
| Provider neutrality | Defined | Keeping product control and reusable contracts independent of one model or executor supplier. Supported adapters can be interchangeable without having equal behavior, quality, cost, or permissions. |

## The OpenAgents app and chat

The [OpenAgents iOS app](../bins/openagents-ios/README.md) and its
[Android build](../bins/openagents-android/README.md) share one Rust core,
`crates/openagents-mobile`. The [app wireframe](product/2026-09-28-app-wireframe.md)
specifies the intended screens; this section names what the code ships.

| Term | Status | Definition |
| --- | --- | --- |
| OpenAgents app | Implemented | The phone app (`com.openagents.app`) with four tabs: **Chat**, **Verse** (the Grid), **Wallet**, and **Account**. Rust builds each screen and thin SwiftUI and Android hosts render it, reusing Coder's Rust Native renderer. It is distinct from the older Coder iOS/Android reader in `bins/coder-ios` and `bins/coder-android`. See [OpenAgents for iOS](../bins/openagents-ios/README.md). |
| Chat tab | Implemented | The app's first tab (the message icon). From build 21 it opens on the [main menu](#the-gym-in-chat); **CHAT WITH OPENAGENTS** there opens a new chat, ready to type, with the composer **Message OpenAgents**. Every chat goes to OpenAgents; there is no target selector (removed in build 29). Above the field sit only questions to send, never previous chats, which sit behind the menu button. It replaced the earlier Coder tab. See [OpenAgents for iOS](../bins/openagents-ios/README.md). |
| Chat with OpenAgents | Implemented | The chat every new conversation goes to by default, even with a computer ready. It needs no computer or sign-in: each message is a NIP-CJ conversation job the device key signs and NIP-44-encrypts to the chat worker. The assistant speaks as OpenAgents in the plural ("we"), answers from the chat router, and dispatches Coder only when a message needs a computer. It was called the *basic Coder* until 2026-09-28; measurements taken before then keep that name. See [the chat worker](deployment/chat-worker.md) and [the chat router](coder/design/2026-09-28-chat-router.md). |
| Thread | Partial | One conversation with OpenAgents: what the chat list shows as one entry, on the phone, the desktop, and the `openagents` CLI (`--thread ID`). A thread keeps its turns in order, including the router's answers, knowledge answers, and any Coder work it delegated. Each native thread maps to one ATIF trajectory (`ATIF-v1.8`, `session_id` = the thread's ID), so a thread can be exported, replayed, and carried as [NIP-ATIF](../nips/openagents/NIP-ATIF.md). A thread's turns live in `openagents-chat`'s encrypted store (the host's, on a computer), and `openagents_chat::thread` renders any thread as its ATIF document: one step per turn, the router's judgment as a decision call, the served knowledge entry, and a link to Coder work it delegated. `openagents chat export --thread ID` prints it ([#10031](https://github.com/OpenAgentsInc/openagents/issues/10031), [guide](cli/chat.md)). A computer's threads (the desktop's and `openagents chat`'s) reach a paired phone over NIP-HOST `thread.list`, `thread.read`, and `thread.send` ([#10035](https://github.com/OpenAgentsInc/openagents/issues/10035)); the phone lists them beside its own, labelled with the computer, and a follow-up sent there appends to the host's thread. `thread.read` includes the router's offers, cards, and follow-up chips on each turn, inside the same 48 KiB page, dropping the oldest turns' extras first. The typed judgment stays on the host. `thread.run` (`operate`) asks that computer to start Coder for the thread through the host's handoff ([#10040](https://github.com/OpenAgentsInc/openagents/issues/10040)). The code and older notes say *chat* or *conversation* for the same thing. The visitor-owned web `/chat/{uuid}` surface currently uses a separate durable server record with frozen selections and native work references; a portable ATIF export for those real web conversations remains unimplemented. |
| OpenAgents Terminal | Implemented | The full-screen chat with OpenAgents in a terminal, opened by `openagents terminal` or bare `openagents` on a terminal ([guide](terminal/README.md)). It is a screen over the same chat client as `openagents chat` (`openagents_chat::client`), sends turns as the `terminal` surface with the client word `openagents-terminal`, and shares the desktop app's threads when this computer's host runs. A coding reply runs Coder on this computer and streams its steps inline; Esc stops a reply or a run, and quitting leaves the run going. Its only parse of typed text is a closed list of slash commands. The library is `crates/openagents-terminal`, drawn with `crates/coder-terminal` in white on near-black. Not Coder Terminal, the older `coder` shell. |
| Chat worker | Implemented | The hosted service that answers Chat with OpenAgents. It runs the `coder-worker` binary on the Coder worker VM, with its own release separate from the executor worker. It receives messages through the relay at `wss://relay.openagents.com`. The app identifies the worker by its public key, which is compiled into the app as `basic_coder::WORKER`. It accepts conversation jobs from any caller key with no usage limits by default and records every job in the usage log. Space Bunny Alpha through OpenRouter answers first; if it fails before sending its first answer text, the worker automatically retries the same turn with Gemini 3.8 Flash through the Vercel AI Gateway. Jev judges the chat router's questions alongside the model call. The worker retains a 96 KiB request-size bound. Optional emergency quotas are off in the shipped configuration. See [the chat worker](deployment/chat-worker.md). |
| Coder chat | Implemented | A chat that runs Coder on a connected computer: tapping **Run Coder on** a computer, a chip under a reply the chat router placed on a computer, sends a NIP-HOST `task.create` with the conversation, and the host's auto-start policy runs it. A computer whose presence says it starts Coder at once (`coder-start-at-once`: its `coder.start` is `at_once` and auto-start is on) gets that `task.create` with no tap, and the reply shows the start with **Open Coder** and **Stop** ([#10101](https://github.com/OpenAgentsInc/openagents/issues/10101)). Images attached to the chat's draft go with it as their exact bytes (`artifact.put` chunks, then `task.create` naming them by digest; PNG or JPEG, at most 8 MiB each and 4 a task), and Codex and Claude Code receive them as native image input; the hosted chat itself never carries images ([#10066](https://github.com/OpenAgentsInc/openagents/issues/10066)). Attachments are off everywhere as of 2026-10-01: the phone's chat ([#10093](https://github.com/OpenAgentsInc/openagents/issues/10093)) and the desktop's ([#10095](https://github.com/OpenAgentsInc/openagents/issues/10095)) are text only, behind one switch (`coder_tab::ATTACHMENTS_ENABLED`); the image pipeline is kept for when it is turned back on. The reply streams into the chat from the task's transcript. The phone lists only chats with OpenAgents and Coder chats; the separate Claude Code, Codex, OpenCode, and Devin history lists and their host mirrors were removed. See [OpenAgents for iOS](../bins/openagents-ios/README.md) and [the chat load benchmark](coder/runtime/chat-load-benchmark.md). |
| Delegate session | Implemented | The OpenCode or Devin session a Coder task delegated to on an `opencode` or `devin` route, copied after each turn into the task directory as `<task>.delegate.<agent>.<session>.jsonl` and listed by the Coder catalog as that task's subagent. A device shows it inside the Coder chat, not as a separate chat. See [delegate sessions](../crates/coder-history/README.md#delegate-sessions). |
| Coder-only host | Implemented | `coder host` serves and watches only a grant's Coder task roots (`Host::coder_only`): an older grant that also names Codex, Claude, OpenCode, or Devin history lists only its Coder chats. The standalone `coder-connect` observer still reads Codex and Claude history for the Coder reader. See [saved harness history](../crates/coder-history/README.md). |
| Catalog index | Implemented | `coder-history`'s private file of each source's first-record reads (`catalog-index.json` in the host's observer directory), used only while a file keeps the identity and length it was read at, so a restarted host lists chats without reading every source again. See [saved harness history](../crates/coder-history/README.md#read-a-history). |
| Relay link and `Client::warm` | Implemented | A `coder-connect` client's standing relay link: one authenticated socket that subscribes once to the host's replies, publishes up to eight requests at once, and takes new reads for 105 seconds of its 120-second lease. `Client::warm` opens the link, and the direct connection when the host has one, before the first read; the app calls it on foreground. See [the reusable client API](../crates/coder-connect/README.md#reusable-client-api). |
| Change nudge (push, not poll) | Implemented | A host-to-phone signal that a watched chat or the chat list changed. One process-wide filesystem watcher (FSEvents or inotify) wakes a direct connection, which nudges the catalog or the open source; on the phone, Rust signals the native host when a screen's data changes instead of the host polling every 250 ms or second. A 5-second look (3 seconds on the phone) remains a fallback. Nudges carry no transcript content. See [the chat load benchmark](coder/runtime/chat-load-benchmark.md) and [NIP-SESS](../nips/openagents/NIP-SESS.md). |
| Relay admission pipelining | Implemented | The relay's admission path sends its policy reads, locks, and checks as one Postgres pipeline and the insert, tags, head update, and notification as a second, still in one transaction with `OK` after commit; an event this process committed is delivered from memory when sequence order allows. A standing host subscription also survives connection renewals. These are latency changes, not new delivery guarantees. See [the database guide](deployment/database.md) and [the chat load benchmark](coder/runtime/chat-load-benchmark.md). |
| Chat load benchmark | Implemented | `crates/chat-load-bench`, which times opening the Chat tab, Send to first words and to done, and listing and opening Coder chats over the relay and a direct connection, phase by phase, with synthetic transcripts by default. | Hosted decision service | Implemented | The `decision-worker` (`crates/gateway`) that answers Jev for a computer with no TypeSafe key: a NIP-CJ decision job (kind `25910`) on `wss://relay.openagents.com`, signed by the computer's decision key (`~/.openagents/decision.key`) and forwarded to `https://api.typesafe.ai` under the worker's own key. ## Context and working state

These are target concepts in the [TypeSafe analysis](coder/design/typesafe-agent-analysis.md), [suite plan](coder/design/typesafe-product-suite.md), and [NIP-CTX](../nips/openagents/NIP-CTX.md). Existing traces and local claim ledgers do not constitute the complete shared context system.

| Term | Status | Definition |
| --- | --- | --- |
| Evidence item | Designed | An addressable observation or derived artifact with source, version, scope, capture limits, and provenance. Summaries retain references to their sources. |
| Evidence snapshot | Designed | An immutable set of evidence versions read by a task or decision. Sharing it does not assume that the current working tree or external service remains unchanged. |
| Evidence representation | Designed | A raw, abbreviated, summarized, or structured view of an evidence item, with its own identity and a path back to the source. A shorter representation retains the original capture’s completeness limits. |
| Task frame | Designed | The current objective, binding constraints, acceptance references, attempted approaches, and unresolved questions. It distinguishes observed user instructions from inferred subgoals. |
| Context request | Designed | A request for evidence tailored to one operation or recipient, under task, input-size, freshness, and disclosure constraints. |
| Context manifest | Designed | The exact evidence and representation versions included in one input, plus omissions, unresolved coverage, and selection identities. It records what was supplied, not whether a provider cached it. |
| Meta-attention | Designed | A separate selection process that decides which evidence and representation an operation needs. Its value depends on preserved constraints, sufficient evidence, and complete-task cost, not tokens removed alone. |
| Retrieval recall and selection recall | Defined | Retrieval recall asks whether candidate search found the needed evidence; selection recall asks whether the later selector retained it. Ranking cannot recover evidence missing from the candidate set. |
| History index | Designed | A scoped task/topic index with references from summaries to original records and bounded expansion. The plan makes no guarantee of logarithmic retrieval of semantically useful evidence. |
| Recursive language model (RLM) approach | Designed | Keeping source material and typed intermediate values outside a single prompt, with bounded investigation and expansion. Generated context-processing code still needs host admission and resource limits. |
| Background view | Designed | An optional explanation or finding derived from a pinned snapshot under a separate resource allowance. It becomes stale when relevant sources change. |
| Mandatory instructions and optional guidance | Defined | Binding user, host, and scoped repository rules are resolved by precedence and scope. Relevance selection may choose optional guidance; it cannot discard applicable mandatory instructions. |
| Cache-aware routing | Designed | Choosing reuse, trimming, rebuilding, or a model change using actual cached/uncached input observations and expected remaining work. Selection, summaries, expansion, failed detours, and cache rebuilding all contribute to the cost. |
| Learned preference | Designed | Proposed optional guidance derived from authorized evidence, with owner, lineage, scope, counterevidence, expiry, and separate permission to learn from the sources. A current task's read permission does not authorize private-history mining. See [POL learned preferences](../nips/openagents/NIP-POL.md#learned-preferences-and-governed-activation). |
| Preference activation | Designed | An owner-admitted controller's revision-checked decision to activate, replace, suspend, reject, or withdraw an exact candidate. Only one revision per lineage is active, and application rechecks current scope and expiry. It cannot grant tools, spend, publication, or approval authority. See [POL activation](../nips/openagents/NIP-POL.md#learned-preferences-and-governed-activation). |

## Capabilities and programs

Sources: [program guide](programs.md), [runtime](../crates/coder/src/runtime.rs), [composition](../crates/coder/src/child.rs), and [capability trust](../crates/capability/src/trust.rs). Portable specifications can be ahead of local readers.

| Term | Status | Definition |
| --- | --- | --- |
| Capability | Implemented | What a capability claim establishes a [plugin](#one-vocabulary-what-you-can-add) adds to an agent: an ability it gains or loses when the plugin is admitted to the run. It names a measured effect, never the thing a person adds, which is a plugin. Without a claim a plugin is a candidate; a [plugin test](#extensions) report is the claim, and the [test-time capability](#test-time-capabilities) rows define the measured sense. The security sense is a grant, below; NIP-CAP's object is an operation description, below. |
| Candidate capability | Implemented | A plugin before a capability claim exists: installed, described, or demonstrated, but not yet measured with and without. It has no verdict from the Gym's gate, can't be confirmed by a check, and can't be adopted into Coder's defaults. Every plugin made in chat starts here; a [plugin test](#extensions) or the [hosted eval runner](#extensions) turns one into a claim. |
| Operation description | Partial | What [NIP-CAP](../nips/openagents/NIP-CAP.md) calls a capability definition: a portable description of operations, interfaces, required effects, and enforcement support. A host binding implements it; a separate grant authorizes use; it grants nothing and measures nothing. NIP-EXT's `capability` component kind is one. Local manifests and probes exist, while the revised NIP-CAP runtime remains partial. |
| Grant | Partial | Authority: permission for a principal to use a binding within a scope and budget, supplied by host or operator policy and never by the component. This is the security sense of *capability*, and a claim's scope names the grant it was measured under. Local program grants (below) and executor settings are implemented; the portable NIP-CAP [grant](../nips/openagents/NIP-CAP.md#grants) object is specified. |
| Delegate | Implemented | Another agent that does a bounded task for this one under a prepared briefing: Microcoder or a CLI executor through the [delegate door](#coder-and-execution), an OpenCode or Devin [delegate session](#the-openagents-app-and-chat), or the executor of a NIP-PRG `delegate` step. Something the system supplies, measured as [test-time delegation](#test-time-capabilities); not a plugin a contributor adds yet. |
| Missing capability | Defined | An ability a task needed that no admitted capability supplied: a test that fails in both arms, or a task the agent still fails after an adoption. It is what the next candidate is for; the [capability flywheel](#test-time-capabilities) turns when adoption reveals one and someone adds it. See [the essay](essays/2026-09-29-test-time-capabilities.md#11-the-capability-flywheel). |
| Executor | Implemented | The built-in runner or approved external-agent binding that performs a bounded task. Its supported effects and limits determine admission; [delegation](coder/runtime/delegate.md) records its actual outcome. |
| Program | Partial | A workflow, the default part of a plugin a contributor writes: a reusable host-interpreted workflow of named steps with separate sources, question sets, and bounds; a context-construction policy is one. The local runtime supports six step kinds and child composition; native `invoke` admission and fetching programs from relays remain unbuilt. |
| Program selection | Implemented | The `openagents.program.v1` decision proposes which admissible workflow a request asks for, or `none`. Selection does not install a plugin or grant execution authority. See [the target entry path](extensions/programs.md#what-the-program-decision-decides). |

Unsupported semantics refuse rather than being skipped. |
| Bounds | Partial | Declared ceilings on work, time, resources, or access. The runtime checks supported enforcement before dispatch and narrows child limits; unsupported required bounds refuse instead of becoming prompt suggestions. |
| Module | Partial | A Wasm guest invoked by a `module` step under `pure` or `snapshot-read` limits. | Module announcement | Designed | An optional `30183` event saying where a module's bytes can be found and what it requires. A locator, not an authority: it cannot change what a program runs, because the program names a hash. |
| Capability manifest | Implemented | A document that says how to drive an executor: transport, detection, bounds it enforces, bounds it ignores, whether it sees the repository, and who pays. Read from `capabilities/` today and published as Nostr `kind:30180` later. |
| Capability probe | Implemented | Running a manifest's `detect` through `crates/capability` under a recorded approval that pins the manifest and executable identity. The probe is bounded; reading a registry does not execute it. |
| Presence | Implemented | Capability status: **present**, **absent**, **present and unavailable**, **unprobed**, or **unknown**. A missing approval leaves a capability unprobed; a failed or incomplete probe cannot manufacture availability. |
| Program registry | Implemented | The programs a host resolved, read from `programs/` in `crates/coder`'s `program` module. The read records the Nostr filter it would have sent beside the answer it got from disk. |
| Run-state store | Partial | The append-only [local journal](../crates/coder/src/runstate.rs) for pinned run, step, and task-attempt identities, worktree/result references, and terminal outcomes. | Task source | Implemented | Where a `query` step's work comes from, named in the program by slug and resolved from `sources/` in `crates/coder`'s `source` module. A program names a source and never a command, so a machine decides what the lookup reads. `request`, the work the request carried, is built in. |
| Selection | Implemented | What one `query` step looked up: the work that runs, the order it is in, what was dropped and why, and every path more than one selected item touches. A lookup answering with more than `max_results` truncates or refuses, as the step's `on_overflow` says, and the trace records which. |
| `cannot_enforce` | Implemented | A capability manifest’s explicit list of bounds its executor cannot enforce. Runtime admission refuses a required bound intersecting that list; the field reports a limitation rather than granting an exception. |
| Operator policy | Designed | The portable signed NIP-CAP `30181` document stating capability preferences, concurrency limits, and exclusions. Existing local program grants and executor settings implement narrower host controls; they are not this complete portable policy runtime. |
| Program grant | Implemented | Operator authorization for named program slugs and an effect ceiling. The [grant](coder/guides/program-authority.md) is separate from semantic program selection and from the ordinary shell permit. |
| Child program | Implemented | A resolved `program` step whose dependencies, typed bindings, outcome propagation, and narrowing limits pass [composition admission](../crates/coder/src/child.rs). Children share the parent’s budget and deadline. |
| Host binding | Partial | Local configuration connecting a portable definition to real paths, adapters, executors, or credentials. Current program and capability bindings exist; the full revised portable contract remains under migration. |
| Local package lock | Implemented | The verified digests and dependency identities resolved by [`coder::package`](../crates/coder/src/package.rs). Resolution pins local bytes and records trust; it does not install, execute, approve a probe, or grant access. |

## Plugins and skills

A *plugin* is anything a person adds ([one vocabulary](#one-vocabulary-what-you-can-add)); its Wasm part is a guest performing a bounded operation, which the code, the crate names (`crates/plugin`, `crates/plugin-*`), and the NIP-EXT component kind `plugin` still call a plugin. *Skill* means guidance, a `SKILL.md` guide or the instructions of a plugin made in chat; both skills and Wasm are parts of a plugin. A Claude Code or Codex package under `plugins/` is a *client plugin package*, always named in full. Voyager uses *skill* for banked Lua code. Sources: [plugin contract and implementation status](extensions/plugins.md), [client packages](../plugins/README.md), and [Voyager](voyager/README.md).

| Term | Status | Definition |
| --- | --- | --- |
| Plugin | Implemented | Anything a person adds to OpenAgents, with its skills, workflows, knowledge, Wasm, and tests ([one vocabulary](#one-vocabulary-what-you-can-add), [how-to](plugins/README.md)). The apps, the chat, and `openagents plugin` use the word; it ships as an [extension package](#extensions). |
| Wasm (a plugin's code) | Partial | A plugin's executable part, the code's *plugin* and *Wasm plugin*: an OpenAgents WebAssembly guest that `crates/plugin` runs to perform a bounded operation, with typed operations and bounded host imports. It can implement a program's `module` step or, once host roles exist, a supported host role; it is not an executor or a workflow, and no model calls it by name. The host core and the `module` step are built; the manifest, host roles, authoring commands, packaging, and a catalog are specified in [Wasm plugins](extensions/plugins.md) and not built. |
| Plugin host | Partial | The Wasm host: the trusted Rust boundary in `crates/plugin`, using a fresh Wasmtime instance per call with no ambient WASI. It enforces profiles, fuel, memory, read/output limits, and cancellation. Full plugin-manifest admission, automatic host roles, and invocation-receipt integration remain designed. |
| Plugin packet | Implemented | The `openagents.plugin-packet.v1` request and response a host and a guest exchange, defined in `crates/plugin-pdk`, whose `guest` feature is the guest side of the ABI. `crates/plugin-outline` is a diagnostic guest built against it. |

## Checks, components, and iteration

| Term | Status | Definition |
| --- | --- | --- |

| Pareto frontier / oracle portfolio | Implemented | The frontier marks configurations not dominated on success, cost, and time. An oracle portfolio chooses the best eligible configuration after seeing results; it is an upper bound for routing, not a deployed router. See [the matrix](../crates/gym/src/coder_matrix.rs). |
| Objective `J` | Implemented | The matrix's configured sum of mean cost, priced agent time, and a failure penalty. Its weights express an accounting choice, not a universal utility function or measured fallback bill. See [objective parameters](../crates/gym/src/coder_matrix.rs). |
| Failure precision / failure recall | Defined | Precision is correct failure detections divided by all failure calls; recall is detected failures divided by actual failures in the declared evaluation population. Abstentions do not establish passes; unknown coverage and denominators remain explicit. See [truthful-checks evaluation](terminal-bench/2026-09-25-candidate-review-validation.md). |
| False accept / false alarm | Defined | A false accept calls unsuccessful work successful; a false alarm calls successful work failed. “Success” must name its label source: official grading and a separate public-specification audit can disagree. See [candidate-review validation](terminal-bench/2026-09-25-candidate-review-validation.md). |
| Wilson interval / task-clustered uncertainty | Defined | Wilson intervals summarize uncertainty in observed binary proportions. Whole-task bootstrap comparisons preserve repeated attempts within each resampled task. Neither removes selection bias or proves unseen-task quality. See [the matrix](../crates/gym/src/coder_matrix.rs) and [paired uncertainty](terminal-bench/2026-09-25-truthful-checks-microluna.md). |
| Run card | Implemented | A deterministic characterization of one retained trial: identities, phases, session anatomy, evidence provenance, check lineage, claims, reversals, and costs. Missing records stay unknown or not recorded. See [run cards](gym/run-card.md). |
| Run analysis | Implemented | Gym's post-run account of grades, costs, timeline, check coverage, reversals, and anomalies. Arithmetic comes from retained records; optional Jev judgments map ambiguous acceptance/verifier test pairs and remain judgments. See [run analysis](gym/run-analysis.md). |
| Strategy fingerprint | Implemented | A derived phase sequence and timing summary of a trajectory, using command/tool rules and optionally cached Jev classifications. Differences between winners and losers suggest hypotheses; they do not prove an intervention helps. See [strategy fingerprints](terminal-bench/2026-09-24-strategy-fingerprints.md). |
| Learning order | Implemented | Gym's ranking of completed runs by cached Jev judgments about what merits inspection, including unusual failure patterns. It is a reading aid, not a verifier result or causal explanation. See [ranking runs](gym/terminal-bench-cli.md#rank-runs-by-whats-worth-learning-from). |
| Head-to-head replay | Implemented | Two retained transcripts aligned on elapsed time, with playback, seeking, separate scrolling, and optional whole-run assessments. Recorded and estimated timestamps are labeled; replay does not rerun either agent or establish matched experimental conditions. See [head-to-head](gym/head-to-head.md). |

| Term | Status | Definition |
| --- | --- | --- |
| System One | Implemented | The typed decision contract at `POST /v1/systemone`: one state and a map of questions produce structured answers. Code chooses what those answers cause. The native schema is `openagents.systemone.v1`; a valid answer shape does not establish that its judgment is correct. | NIP-DEC | Implemented | The decisions protocol: one state (a string or object) and typed `noul`, `choice`, and `score` questions, carried as the NIP-CJ decision family (`25910`/`26910`/`27010`, `openagents.systemone.v1`) and taken unchanged by `POST /v1/systemone`, TypeSafe's Jev API, and OpenRouter's Decisions API (`typesafe/jev-1.13`). It defines the bounds, model aliases, and the refusal-to-HTTP-status table. See [NIP-DEC](../nips/openagents/NIP-DEC.md). |
| EntryType | Implemented | A string, JSON object, JSON array, or null: the shape of a decision question's `instructions`, a `choice` option's description, a `score` level, and a `noul` question's `true` and `false`. Structure lets a question carry a shared `field`, a `what`/`not_for`/`examples` rubric, or a level's `summary` and `signals`. Entries nest at most 8 levels. See [NIP-DEC](../nips/openagents/NIP-DEC.md#entrytype); `jev::Entry` builds one. |
| State | Implemented | The document a request's questions judge. It can carry text or structured application data. Each question asks about that state; one question's answer is not another question's input. See [the question types](../crates/jev/src/questions.rs). |
| Question | Implemented | A named judgment with instructions, criteria, and one of three result types: `Noul`, `Choice`, or `Score`. Question wording is part of the measured instrument. See [questions](../crates/jev/src/questions.rs) and [question sets](../crates/gym/src/questions.rs). |
| `Noul` | Implemented | A yes-or-no judgment represented by the probability that the condition holds, from 0 to 1. It does not carry a separate confidence field. See [the caller guide](decision-models/guides/caller.md). |
| `Choice` | Implemented | A judgment among caller-supplied named options. Its answer carries a selected option, a probability distribution over the options, and confidence. See [the caller guide](decision-models/guides/caller.md). |
| `Score` | Implemented | A judgment on an ordered rubric, with a weighted position, a legend, and a distribution. Evaluators retain the explicit selected level when supplied; otherwise they use the distribution's argmax, with ties resolved to the last level. A calibrated distribution must not silently replace the original selection. See [the Score contract](decision-models/measurements/2026-09-20-score-contract.md) and [selection semantics](../crates/gym/src/calibrate.rs). |
| Confidence | Defined | A field whose meaning depends on the wire profile. The native System One guide describes distribution concentration. NIP-CJ specifies the selected option's probability for `Choice` and the largest level probability for `Score`. Neither meaning certifies calibration or authorizes an action; callers must pin the profile and measure their thresholds. See [the native contract](decision-models/api/decision-api.md) and [NIP-DEC answers](../nips/openagents/NIP-DEC.md#answers). |
| Door | Implemented | A serving interface to a decision model. The client chooses an origin through `base_url` and a model through `model`; a gateway can expose tenant-specific door names bound to particular artifacts. See [clients](decision-models/guides/clients.md) and [the gateway](decision-models/service/gateway.md). |
| Door identity | Implemented | The recorded model identity: door and version, relevant base or adapter identifiers, artifact content digest, and numerical execution settings when available. Estimator and seed configuration remain separate parts of a trial. A reported identity is not remote attestation. See [model identity](gym/model-identity.md). |
| Model card | Implemented | A model's discovery record returned by `GET /v1/models`. It can report identity, supported behavior, execution settings, and configured admission bounds. A gateway exposes authorized registry bindings; listing a model does not prove current backend health or measured quality. See [gateway discovery](decision-models/service/gateway.md) and [classification discovery](decision-models/api/classification-http.md). |
| Artifact signature | Implemented | A digest that identifies model content, distinct from a name, path, or base revision. For Kev, it covers the bytes actually loaded; execution settings are recorded separately. It identifies claimed content, not proof that a remote machine executed it. See [content identity](gym/model-identity.md). |
| Refusal code | Implemented | A typed reason a service or door declines a request. In decision evaluation, a coded door refusal is a retained outcome; a transport failure with no evaluable answer can leave a missing row that coverage must expose. See [typed errors](decision-models/guides/clients.md) and [measured records](gym/measured-records.md). |
| `uncalibrated` | Implemented | A refusal when a caller requires calibrated probabilities for a question family without a matching admitted map. A raw distribution is not silently promoted to a calibrated one. See [Lev calibration](lev/calibration.md). |

## Estimating a distribution

| Term | Status | Definition |
| --- | --- | --- |
| Estimator | Implemented | A method for deriving a selected answer and an observable uncertainty signal when the model runtime exposes no probabilities. Lev provides the L1, L2, and L3 methods. See [the estimator](../crates/lev/src/estimator.rs). |
| L1 | Implemented | Lev's single greedy draw, which returns a choice without a distribution. See [estimators](../crates/lev/src/estimator.rs). |
| L2 | Implemented | Lev's count of choices across `n` seeded draws. Its raw frequency resolution is `1/n`; that frequency is not an established probability of correctness. See [estimators](../crates/lev/src/estimator.rs). |
| L3 | Implemented | Lev's constrained self-reported certainty band alongside a selected answer. Whether the bands carry useful information depends on the checkpoint and measured workload. See [estimators](../crates/lev/src/estimator.rs). |
| Raw signal | Implemented | The observable estimator output before a fitted calibration map: for example, sample frequency or a certainty band. The type keeps that observation distinct from a calibrated probability of correctness. See [calibration observations](../crates/gym/src/calibrate.rs). |
| Seed block | Implemented | A non-overlapping range of L2 seeds. Block `b` with `n` draws uses the half-open range `[b*n, (b+1)*n)`. Reusing that block is not a fresh independent trial. See [seed construction](../crates/lev/src/estimator.rs). |
| Certainty band | Implemented | A coarse confidence category the model supplies under constrained output. A varying or monotone band must be demonstrated for the particular model; it is not guaranteed by the output type. See [banded observations](../crates/gym/src/calibrate.rs). |


## Calibration and decision metrics

| Term | Status | Definition |
| --- | --- | --- |
| Calibration | Defined | Agreement between reported probabilities and observed correctness over a specified population. Calibration evidence is tied to the workload, question wording, model identity, and evaluation procedure. See [calibration](lev/calibration.md). |
| Calibration map | Implemented | A fitted reliability table mapping a raw signal to the observed probability that the already-selected answer is correct. Serving checks its family and model identity. Redistributing the remaining probability mass is a display convention, not a newly fitted alternative prediction. See [the map contract](../crates/gym/src/calibrate.rs). |
| Band-conditioned map | Implemented | Reliability tables fitted separately within reported certainty bands. Whether conditioning improves held-out metrics is an empirical question. See [calibration](../crates/gym/src/calibrate.rs). |
| Calibration admission gate (admission gate) | Implemented | A digested Gym gate deciding whether a map's held-out evidence meets its declared accuracy, calibration, and other bounds. The rule is in `gym::gate`, not the removed `gym::calibrate::admit` function; thresholds belong to the named gate version. See [gates](gym/gate-digests.md). |
| Confident error | Defined | An incorrect selected answer assigned a high probability under a stated threshold. Its count depends on the threshold, population, and denominator; it is not interchangeable with total error. See [calibration scores](../crates/gym/src/calibrate.rs). |
| Calibration record | Implemented | The fitted map with its provenance, model identity, partition, estimator, metrics, and admission verdict. New records use `openagents.gym.calibration_record.v2`; historical v1 records remain readable, but incomplete identity cannot establish a new match. See [record versions](gym/model-identity.md) and [the owning schema](../crates/gym/src/calibrate.rs). |
| Expected calibration error (ECE) | Defined | A binned summary of the difference between confidence and empirical correctness. Its meaning depends on binning and which selected-answer probabilities are scored. It is one calibration measure, not a stand-alone guarantee. See [score calculations](../crates/gym/src/calibrate.rs). |
| Brier score | Defined | A squared-error score for reported probabilities against observed outcomes. Here, calibration evaluates the fixed selected answer's probability against whether that answer was correct. Lower is better for the same evaluation. See [score calculations](../crates/gym/src/calibrate.rs). |
| Log loss | Defined | A probability score that penalizes low probability on the observed outcome, especially confident mistakes. The Gym's calibration calculation scores correctness of the fixed selected answer. Lower is better for the same evaluation. See [score calculations](../crates/gym/src/calibrate.rs). |
| Selected answer | Implemented | The option or level actually returned by the model or estimator. Calibration preserves it even when rescaling moves the distribution's argmax. Rows retain this field so accuracy and probability metrics judge the same prediction. See [the selection contract](../crates/gym/src/calibrate.rs) and [row schema](../crates/gym/src/row.rs). |

## AI programming and optimization

These portable target contracts come from [NIP-OPT](../nips/openagents/NIP-OPT.md), the [architecture](optimization/architecture.md), and [experiment lifecycle](optimization/experiments.md). Local experiments are not evidence that the full optimizer or promotion service exists.

| Term | Status | Definition |
| --- | --- | --- |
| Semantic AI signature | Designed | Task meaning, semantic input/output schemas, abstention, and protected constraints. Distinct from a cryptographic event signature and an operation discovery descriptor. |
| AI implementation | Designed | An immutable realization of a signature through a decision function, program, or admitted operation, with its complete functional closure. |
| Inference strategy | Designed | A supported method for realizing AI behavior, potentially with multiple model or tool calls under host limits. |
| Compilation | Designed | Producing a concrete implementation from semantic structure and selected configuration; it does not necessarily mean machine-code compilation or weight training. |
| Optimization study | Designed | A frozen contract for bounded search, including task, baseline, allowed surfaces, data rights, partitions, objectives, protected evaluation, and budgets. |
| Candidate | Designed | In NIP-OPT, an exact proposed implementation and lock with study and parent lineage. Local benchmark studies also use the word for tested configurations; selection alone never establishes confirmed quality or adoption. |
| Materialization record | Designed | Host-attributed evidence of the functional assets, model target, configuration, and bindings actually loaded for a trial. It is not remote attestation. |
| Confirmation | Designed | In NIP-OPT, evaluation of a committed candidate under a protected, bounded allowance with recorded exposure. Local frozen benchmark confirmation studies implement specific research protocols, not the entire OPT runtime. |
| Promotion | Designed | Independent operator-policy adoption of an eligible exact implementation for a specified workload and model scope; separate from package publication and execution grants. |
| DSPy integration | Designed | A bounded authoring/optimization bridge from semantic contracts to supported complete implementation artifacts. No DSPy runtime is required by the wire protocol. |
| GEPA integration | Designed | An explicitly identified reflective search procedure using authorized feedback and the same candidate, measurement, and adoption contracts as other optimizers. |
| Replaceable AI operation | Designed | An operation whose semantic purpose, input/output meaning, authority, and acceptance requirements remain stable while its prompt, model, retrieval, examples, or bounded call strategy can change through measured adoption. |
| Protected constraint | Designed | A task, evidence, privacy, authority, or acceptance invariant that an optimizer is not allowed to change. A better score cannot waive it. |
| Optimizer | Defined | A procedure that searches explicitly allowed implementation choices using an objective and authorized feedback. It proposes candidates; it does not grant authority or deploy a winner. |
| Materialization | Designed | Resolving and loading the exact implementation closure that a trial will execute. A changed manifest without changed loaded behavior is not a new tested implementation. |
| Objective | Defined | The frozen success and efficiency criteria used to compare candidates, including protected error directions and budget constraints. Module scores and whole-task outcomes can differ. |
| Amortization | Defined | Accounting for whether repeated deployment savings repay the search, training, or compilation cost that produced a candidate. A cheaper individual call need not make the complete investment cheaper. |

## Nostr and shared protocols

The [NIP index](../nips/README.md) separates pinned official Nostr specifications,
pinned Block extensions, and OpenAgents drafts authored here. The OpenAgents
lane contains 30 NIPs and their shared contract. Event kinds are draft
assignments, not upstream registrations. Implementation status applies to the

## Test-time capabilities

[Test-Time Capabilities](essays/2026-09-29-test-time-capabilities.md)
proposes these terms. They keep the research word: in product words, the
candidate is a plugin, and a capability is what its test result shows it
adds. Each definition is the general, vendor-neutral
concept from the essay's [Part I](essays/2026-09-29-test-time-capabilities.md#part-i-the-concept); the "In
OpenAgents" clause is our implementation from
[Part II](essays/2026-09-29-test-time-capabilities.md#part-ii-our-implementation), and the status is that
implementation's.

| Term | Status | Definition |
| --- | --- | --- |
| Test-time compute | Defined | Computation spent when a model answers rather than when it's trained: longer reasoning, repeated sampling with a verifier, search, or brief test-time training. See [the essay](essays/2026-09-29-test-time-capabilities.md#what-test-time-compute-is). |
| Test-time capability (TTCap) | Implemented | A change in what outcomes an agent can achieve under stated resource constraints, at inference time, without a weight update, because a candidate (a program, plugin, skill, or knowledge entry a contributor added, or a delegate or typed judgment the system supplies) was admitted to the run. It is stated only as a **capability claim**: a key K = (A, B, D, S, E, G, M) (subject, locked baseline agent, task distribution, sampled suite, environment, grant, measurement), evidence records on it (each run's Δ with its uncertainty), and a policy P that turns them into a verdict; B is the whole locked agent, P is not part of the key, and observed cost and time are results, not scope. Nothing is a capability in general; having a component installed, described, or demonstrated makes no claim, and one without a claim is a [candidate capability](#capabilities-and-programs). See [the concept](essays/2026-09-29-test-time-capabilities.md#1-test-time-capability-ttcap) and [the five objects](essays/2026-09-29-test-time-capabilities.md#the-thesis-capability-is-something-you-can-acquire-at-test-time) (candidate, claim, reproduced claim, externally validated claim, adopted capability). In OpenAgents: a program, plugin, or skill shipped in an extension package, a knowledge entry, or a delegate admitted to a Coder turn; the claim is a NIP-EVAL report whose fields carry the scope; a candidate has no verdict from the Gym's gate, can't be confirmed by a check, and can't be adopted into Coder's defaults ([Part II](essays/2026-09-29-test-time-capabilities.md#what-is-a-capability-means-in-our-system)). Carried by [NIP-EXT](../nips/openagents/NIP-EXT.md) releases and [NIP-EVAL](../nips/openagents/NIP-EVAL.md#extension-evaluation-profile) reports ([protocol mapping](essays/2026-09-29-test-time-capabilities.md#how-the-protocol-carries-test-time-capabilities)). |
| Capability admission | Partial | The host's decision that an exact, locked component version may take part in a run; separate from discovery, installation, enablement, and grants. Evaluation admission (a sandboxed arena with a grant fixed by the evaluator, enough to measure a candidate) and operational admission (the grant real use gives it, decided on that evidence) are two decisions, and a grant is not the effective authority it confers, which runs through every component the candidate can reach. See [the concept](essays/2026-09-29-test-time-capabilities.md#2-capability-admission). In OpenAgents: separate decisions in the [extension architecture](#extensions), with the lock digest recorded in every eval report ([Part II](essays/2026-09-29-test-time-capabilities.md#capability-admission-in-openagents)). Carried by [NIP-EXT](../nips/openagents/NIP-EXT.md#listings-updates-and-installation) and [NIP-CAP](../nips/openagents/NIP-CAP.md#description-binding-and-grant); a run's lock is in [NIP-RUN](../nips/openagents/NIP-RUN.md#record-types). |
| Capability delta | Implemented | The estimated treatment effect of admitting the component: the difference between the with arm and the without arm on the same tests, with its uncertainty from repeats. A versioned written rule turns it into a verdict; that rule is an engineering gate, not the delta's definition. It holds only for the baseline it was measured against, and a negative delta is a finding. See [the concept](essays/2026-09-29-test-time-capabilities.md#3-capability-delta). In OpenAgents: `openagents ext eval` and the hosted runner, judged by the `ext-eval-v2` gate ([Part II](essays/2026-09-29-test-time-capabilities.md#capability-delta-in-openagents)). Carried by [NIP-EVAL](../nips/openagents/NIP-EVAL.md#reports) reports. |
| Reach and restraint | Implemented | Reach: how often the host exposes and the agent uses a candidate where its conditional delta is positive. Restraint: how often the host withholds it where that delta is negative or zero. Both belong to the agent, selector, and component together, not to the component alone. An installed capability the agent never invokes changes no outcome. See [the concept](essays/2026-09-29-test-time-capabilities.md#4-reach-and-restraint). In OpenAgents: every suite's should-fire and should-not-fire cases ([Part II](essays/2026-09-29-test-time-capabilities.md#reach-and-restraint-in-openagents)). Carried by [NIP-EVAL](../nips/openagents/NIP-EVAL.md#suites) case kinds `should-fire` and `should-not-fire`. |
| Judgment budget | Implemented | The time and cost spent deciding how to answer before answering, kept far below the work it can avoid. See [the concept](essays/2026-09-29-test-time-capabilities.md#5-judgment-budget). In OpenAgents: in chat, one Jev request (about 170 ms median) picks tier T0 to T4 ([Part II](essays/2026-09-29-test-time-capabilities.md#judgment-budget-in-openagents), [the chat router](#the-chat-router)). The judgment travels as [NIP-CJ](../nips/openagents/NIP-CJ.md#conversation-jobs) `judgment` feedback and decision jobs; its time and cost have no wire record yet. |
| Test-time delegation | Implemented | Acquiring another agent's capability for one task through a prepared briefing, recorded as part of the task. See [the concept](essays/2026-09-29-test-time-capabilities.md#6-test-time-delegation). In OpenAgents: Microcoder's provider failover, Claude Code or Codex CLI through the delegate door, and OpenCode or Devin delegate sessions ([Part II](essays/2026-09-29-test-time-capabilities.md#test-time-delegation-in-openagents)). Carried by [NIP-PRG](../nips/openagents/NIP-PRG.md#step-kinds) `delegate` steps, [NIP-SESS](../nips/openagents/NIP-SESS.md#steering-capability) delegate-engine rows, and [NIP-ATIF](../nips/openagents/NIP-ATIF.md#delegated-sub-agents) sub-agent links. |
| Reproduced capability claim | Implemented | A capability claim with a second evidence record from a different evaluator, the key K = (A, B, D, S, E, G, M) held fixed, whose effect estimate is compatible with the first (the same direction, within a stated tolerance); a verdict match is the lossy operational count. It shows reproducibility, not that the improvement holds beyond the author's tests, and it is only as independent as the reliance set (runner, provider, agent build, selector, grader, host) the rerun didn't share with the original. See [the concept](essays/2026-09-29-test-time-capabilities.md#7-reproduced-capability-claim). In OpenAgents: a **Better** result confirmed by an [eval check](#extensions) from a different trainer ([Part II](essays/2026-09-29-test-time-capabilities.md#reproduced-capability-claim-in-openagents)). Carried by [NIP-EVAL checks](../nips/openagents/NIP-EVAL.md#checks). |
| Externally validated capability claim | Defined | A reproduced claim whose improvement persists on new tasks from the same distribution, written independently of the author and revealed only after the subject was locked, on a suite that states its sampling frame. It belongs before adoption; changing the task distribution is transfer, a new claim. See [the concept](essays/2026-09-29-test-time-capabilities.md#8-externally-validated-capability-claim). In OpenAgents: the wire is built and no validation has been published: a `validates` result on a second suite, read for independence from the two releases' signers and creation times, and required by the candidate policy beside three confirming checks; the starter suites and catalog capabilities still share a signer ([Part II](essays/2026-09-29-test-time-capabilities.md#externally-validated-capability-claim-in-openagents)). No carrier yet; a second suite's report would be an ordinary NIP-EVAL `3189`. |
| Capability adoption | Partial | Making an externally validated claim's subject part of the agent everyone starts with, and keeping it there only while the claim still holds (a change in subject, baseline, environment, grant, or measurement reopens it for revalidation, quarantine, or revocation; a changed gate reinterprets the records; a changed distribution is a transfer; and the admission's lifetime follows the subject's identity strength, an unresolved subject never being adoptable), on its marginal effect against the current default set (current defaults plus the candidate against current defaults alone), not its standalone delta, and on the marginal effective authority the composition gains, not the candidate's grant alone. See [the concept](essays/2026-09-29-test-time-capabilities.md#9-capability-adoption). In OpenAgents: an `openagents.eval-admission.v1` decision and a [`coder-defaults`](#extensions) release; a candidate needs **Better**, three distinct confirming checks, and one externally validating result, and an admission that admits cites the validation. None has been made yet, and the runner has no baseline arm that holds the current defaults ([Part II](essays/2026-09-29-test-time-capabilities.md#capability-adoption-in-openagents)). Carried by [NIP-EVAL adoption](../nips/openagents/NIP-EVAL.md#adoption) and a [NIP-EXT](../nips/openagents/NIP-EXT.md) release. |
| Capability credit | Implemented | Recognition for the people whose work made a capability claim real: for adoption, and for verification work whichever way it came out, never for activity. The `eval-check` rule pays a protocol-following check whether it confirms or disputes; adoption still needs a confirming check. See [the concept](essays/2026-09-29-test-time-capabilities.md#10-capability-credit). In OpenAgents: [eval credit](#network-effects-and-contribution-value), XP and a name, never money ([Part II](essays/2026-09-29-test-time-capabilities.md#capability-credit-in-openagents)). Carried by [NIP-XP](../nips/openagents/NIP-XP.md#eval-check) `eval-check` and `eval-adopt`. |
| Capability flywheel | Defined | The hypothesized loop in which people add capabilities, tests produce claims, others reproduce them, independent tests validate them, and adoption hands them to every agent. Measured as incremental externally validated passes per adopted contribution. See [the concept](essays/2026-09-29-test-time-capabilities.md#11-the-capability-flywheel). In OpenAgents: chat, the Gym, and Verse; each part built, the loop not yet shown ([Part II](essays/2026-09-29-test-time-capabilities.md#the-capability-flywheel-in-openagents)). No single carrier; see the [protocol mapping](essays/2026-09-29-test-time-capabilities.md#how-the-protocol-carries-test-time-capabilities). |

## Maintaining the glossary

- Keep the [master roadmap](roadmap.md), [catalog](catalog.md), and owning domain
  index linked to the same current contract. Follow [documentation maintenance](documentation.md).
- Define a term from a repository contract or retained source, and link that
  source. Prefer an explicit scope over a claim that all implementations agree.
- Check runtime claims against code when a guide is older than its implementation.
  A validator, schema, fixture, or local prototype does not establish a complete
  network service.
- Keep overlapping meanings explicit: a trace is not a recovery journal; a
  capability definition is not a grant; a completed process is not a verified
  artifact or an accepted paid job.
- Keep thresholds, price tables, leaderboard positions, and experimental scores
  in their versioned specifications or result reports. The glossary explains
  how to interpret those records.
- Preserve important aliases and incoming section links. Check Markdown
  rendering, links, and implementation labels after an update.
