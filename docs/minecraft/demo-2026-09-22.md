# September 22 demo plan

Status: proposed recording plan for 2026-09-22, America/Chicago. No step below is
marked complete by this specification. The target is one visible causal chain:
guild request → mining → earned compute → code repair → verification → XP.

## The claim to demonstrate

Four agents inhabit a shared Minecraft world. They exchange signed guild
messages over Nostr. Jev interprets or selects useful work. A miner earns a
bounded compute allocation, and a teammate spends part of it on a real coding
attempt. Independent checks accept a patch, and the world reflects the result.

The stronger target adds CJ decision transport and recoverable execution, with
inspectable CAP/PRG/EXT definitions and CTX/POL/COORD/RUN records. Covering all
those contracts in design is possible now. Building and proving all roles in
one day is uncertain. Do not call the recording a complete implementation of
the new NIPs unless its evidence supports every advertised role.

## Critical path

These timeboxes are planning limits for implementation, not completed estimates.
At a failed gate, narrow the advertised demonstration and preserve the failure
record. Do not spend the recording day debugging a second graphics engine.

| Gate | Suggested timebox | Exit evidence | If blocked |
| --- | --- | --- | --- |
| D0: compatible environment | First 60–90 minutes | Pinned client/server/toolchain; one bot joins, walks, mines, reports inventory, stops, and exits | Record a protocol pilot separately; no claim of a live Minecraft agent |
| D1: attributable mining | Next 60–90 minutes | One deposit creates one durable credit award; repeated observation creates none | Show mining without earned-compute claims, or stop the economy segment |
| D2: real decisions and chat | Next 60–90 minutes | Two identities exchange kind `9` messages; an actual Jev answer changes a bounded task choice | Label a local HTTP decision honestly if CJ worker support is absent |
| D3: one coding quest | Next 90–120 minutes | Exact base, generated patch, independent checker result, integration record, reconciled cost | Show the failed attempt honestly; do not open the success gate |
| D4: two guilds | Next 60–90 minutes | Four agents, separate balances, a contested claim, no double grant | Keep one complete guild loop if four-agent operation is unstable |
| D5: rehearse and record | Reserve at least 60 minutes | Two complete retained rehearsals, one reconnect/duplicate check, readable recording | Use a clearly labeled replay of a successful recorded run |

These gates intentionally prioritize the complete loop. If the compatibility
spike requires a substantial new client or toolchain port, the full live target
is unlikely to fit this schedule. The first engineering decision should expose
that fact, not hide it behind a simulated world view.

Protocol validation and definitions can be prepared while building the arena,
but the implementation must not advertise untested roles to save time. A smaller
transport pilot is useful evidence and a different demonstration.

## Minimum playable configuration

- One controlled Minecraft server and one configured relay with NIP-29 enabled.
- Two guilds with two bot identities each; one neutral referee/verifier identity.
- One spectator client, a compact map, fixed weather/time if supported, and no
  combat or player placement in the reward area.
- The finite deposits and seed allowance from the frozen economy manifest.
- The bridge-planner quest, an isolated worktree per guild, and independent checks.
- One admitted Jev door and one generation door with configured real cost bounds.
- A companion terminal showing source-linked decisions, reservations, results,
  and protocol events. Reuse the terminal design system if adding a Rust view.
- A durable recording directory and an operator stop control that works without
  model calls and stops new dispatch immediately.

All credentials remain outside the map, agent-visible files, logs, and video.
Use public demonstration inputs. Existing relay or inference deployments must
not be assumed to have unused capacity or every draft extension enabled.

## Six-minute recording sequence

| Time | Scene | Evidence to show |
| --- | --- | --- |
| 0:00–0:40 | Establish the two guild camps, mines, forge, and closed gates | Live/replay indicator, identical starting allocations, quest objective |
| 0:40–1:30 | A guild request selects gathering work | Actual kind `9` exchange, Jev answer and the selected task |
| 1:30–2:20 | Miners pursue iron and the contested diamond | Physical actions, one claim winner, attributed award and balance change |
| 2:20–3:40 | A coder commits compute at the forge | Reservation, request identity, real patch, bounded progress |
| 3:40–4:40 | Verify the repair and open the gate | Independent checks, acceptance, settled/unknown usage shown accurately |
| 4:40–5:20 | Award and inspect reputation | XP entry, trusted NIP-32 label, contributor record |
| 5:20–6:00 | Reuse or a short failure/recovery segment | Actual loaded skill, or duplicate/reconnect with unchanged balances |

Do not slow the inference loop artificially to fit these timings. Cut between
real recorded states and label time compression. If generation takes longer,
explain the elapsed time rather than inserting a fabricated result. Keep a
short protocol inspector cut so the audience can see signed interactions without
having to read a wall of event JSON.

A useful closing observation is a question the run measured: did the guild that
reused a skill spend less compute for the same accepted result? Answer only from
the retained run. Do not prewrite the winner.

## Rehearsal acceptance

Before recording, establish the following with retained evidence:

1. The source manifest reproduces the map, roster, definitions, locks, and quest.
2. A real Jev result changes at least one permitted task or skill selection.
3. Guild messages are signed, received through the relay, and verified by the
   recipient. They are not local log lines styled as a conversation.
4. The mining attribution fixture passes. Duplicate delivery and a spectator
   reconnect do not change balances or XP.
5. A real generated patch passes the independent checks and receives a separate
   integration decision before the gate opens.
6. All calls fit both game and provider admission bounds, including repairs and
   review. Unknown usage remains visible and reserved.
7. Competing claims do not dispatch two actors under one exclusive permit.
8. Stop prevents new dispatch, terminates owned jobs through supervision, and
   leaves interrupted effects recoverable.
9. The recording contains no private credentials or protected artifacts and all
   public cards have working evidence references.

Runtime implementation requires the repository's pinned toolchain and
`./scripts/verify-rust.sh` under [verification scope](../verification.md), with a
separate Cargo target directory for the worktree. Documentation-only work does
not require that gate. Required checks remain manual; add no GitHub workflows.

## Fallbacks with honest labels

Use these in order of retained value:

1. A complete live single-guild loop if four agents cannot run reliably.
2. A replay of an actual completed episode, with original event identities,
   usage, elapsed time, and a visible replay label. Replaying never dispatches.
3. A live Nostr/Jev protocol pilot alongside a separately labeled Minecraft
   environment spike, with the missing connection explained.
4. A fixture visualization of the intended flow, explicitly called a prototype
   visualization with no autonomy, learning, or performance claim.

Stop the relevant segment on ambiguous mining attribution, unknown unbounded
liability, a checker integrity failure, private artifact leakage, or ineffective
worker fencing. Do not substitute a manual award while presenting it as an
autonomous verified outcome.
