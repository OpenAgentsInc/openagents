# Omega v0.2.0 All Work dogfooding plan

- Status: owner-directed screen and fixture plan
- Date: 2026-08-02
- Glossary reconciliation: 2026-08-03
- Parent program: [omega#208](https://github.com/OpenAgentsInc/omega/issues/208)
- Release issue: [omega#160](https://github.com/OpenAgentsInc/omega/issues/160)
- Target: Omega `v0.2.0`
- Scope: development and test Work screens, their planning data, and their

## 1. Decision

Omega will use its own `v0.2.0` launch as the first All Work dogfood project.
The development Work screens will stop showing generic sample work and will
instead show the live launch shape: its Release Planning Record, portfolio
hierarchy, all open `v0.2.0` and All Work issues in `omega` and `openagents`,
recently closed foundation issues, dependencies, accountable people, agent
delegates, coding sessions, review state, and release evidence.

The screen vocabulary will follow Linear's public GraphQL models with minimal
changes. `Organization`, `Team`, `Initiative`, `Project`, `ProjectMilestone`,
`Cycle`, `Issue`, `AgentSession`, `AgentActivity`, `PullRequest`, and `Diff`
keep their compatible structural meanings. The collision-prone Linear `User`
and `Release` resources become an OpenAgents User Projection and Release
Planning Record. OpenAgents adds only the repository, source, authority,
execution, evidence, receipt, and acceptance fields that Linear does not
model.

This document admits a screen-data plan, not a Public Claim. The first
implementation is an explicit development/test fixture. It does not become a
durable Work record, a live coding session, release evidence, or permission to
act merely because the UI renders it.

Implementation update, 2026-08-03: the canonical planning state, refresh,
Repository Work Claim, command-admission, signed Workroom, and one-writer
cutover boundaries are implemented without activating the cutover. The final
public strict-bug exception now has a typed, persistent untrusted-candidate
destination; see the
[strict bug candidate ingress boundary](./2026-08-03-strict-bug-candidate-ingress.md).
The production signature-verifying transport, installed two-client journey,
policy/tool refusal switch, and final build remain open gates.

## 3. The screen object graph

The initial fixture is one connected graph, not a list of unrelated cards:

```text
Organization: OpenAgentsInc
└── Team: Omega
    └── Initiative: Omega as the first-class All Work client
        ├── Project: Omega v0.2.0 dogfood
        │   ├── Release Planning Record: Omega 0.2.0
        │   ├── Cycle: v0.2.0 dogfood
        │   ├── ProjectMilestone: All Work foundation
        │   ├── ProjectMilestone: Agentic execution loop
        │   ├── ProjectMilestone: Planning, projections, and SDK
        │   └── ProjectMilestone: Candidate and launch proof
        └── Project: Forensics Security Work
            └── ProjectMilestone: Live evidence completion
```

Issues attach to the project, cycle, milestone, team, workflow state, labels,
and, only when the live release scope says so, the Release Planning Record
through a Release Scope Link. Dependencies use issue relations. `AgentSession`
attaches to the same Issue that the user selected. `AgentActivity` and `Diff`
attach to the session, and a `PullRequest` joins through the agent session.
Project updates summarize the program without replacing the issue rows.

Display names stay expressive while their coarse Linear lifecycle types stay
stable: `Ready` is `unstarted`; `In Progress`, `In Review`, and `Verification`
are `started`; `Done` is `completed`; and `Canceled` is `canceled`. `Blocked`
is derived from relations, not a new lifecycle type. Release-stage names use
the same pattern over `planned`, `started`, `completed`, and `canceled`.

Linear already encodes the separation that Omega needs for agentic work:

- `Issue.assignee` and `Issue.delegate` are separate `User` relations;
- `User.app` identifies an app-backed user, while
  `User.supportsAgentSessions` identifies agent-session capability;
- a User has separate assigned and delegated issue collections;
- `AgentSession` names the app user and the responsible human creator;
- an agent session attaches to an issue and carries plan, status, summary,
  activities, external links, and workspace changes;
- session statuses are `pending`, `active`, `awaitingInput`, `complete`,
  `error`, and `stale`;
- `AgentActivity` distinguishes action, elicitation, error, prompt, response,
  and thought content and defines continue, select, stop, and authentication
  signals;
- `Diff` is a first-class working-tree diff that can become reviewable through
  a linked `PullRequest`;
- Linear's `Release` resource already joins issues, documents, links, notes,
  pipeline stages, dates, commit SHA, history, and progress.

Those `User` facts decode into a User Projection. An app-backed User becomes an
Agent Delegate only after it resolves to an Agent Member with a Delegation
Grant. Linear's `Release` resource decodes into a Release Planning Record; a
planning stage, scope link, progress value, or commit SHA cannot create an
OpenAgents Release Candidate or Release.

Omega must never expose private chain-of-thought under an activity type named
`thought`. The safe projection is a concise progress summary, decision,
question, or evidence reference.

### Three layers stay distinct

1. The Linear-derived vocabulary in this document describes the target screen
   and fixture view models.
2. Omega currently consumes the OpenAgents-owned generated
   `all_work_boundary.v1`, whose first read-only `WorkSummary` and
   same-identity `IssueProjection` path currently projects Full Auto runs.
3. A future owned GitHub/release-plan source and the signed projections in
   openagents#9304 and generated API/SDK in openagents#9305 provide live data.

The broad view-model inventory in layer 1 does not claim that every field
already exists in layer 2. Layer 3 evolves the OpenAgents-owned contract; it
does not publish a renamed Linear wire schema.

## 4. Minimal OpenAgents extensions

The Linear models describe collaboration and planning. They do not define an
`Evidence`, `Receipt`, `Verification`, `Acceptance`, `Authority`, `Lease`,
`Repository Work Claim`, `Assurance`, or `Artifact` domain model. Omega
therefore keeps a small owned extension envelope rather than forcing these
meanings into comments or labels.

| Extension                              | Required data                                                 | Why it remains OpenAgents-owned                                       |
| -------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `Repository`                           | Stable repository identity, host, owner, name, default branch | Linear has no canonical first-class Repository model                  |
| `SourceCoordinate`                     | Repository, issue number, URL, source revision, fetched time  | Proves what fixture or live projection was read                       |
| `WorkIdentity`                         | Durable Work ID and same Issue projection ID                  | Preserves the All Work identity law                                   |
| `Effective Principal`                  | Principal, Organization, Team/Work scope, Membership facts    | Prevents display identity from implying authority                     |
| `Effective Authority Record`           | Allowed commands, grants, generation, and denial reasons      | Keeps read visibility separate from command authority                 |
| `Repository Work Claim Projection`     | Holder, scope, paths/contracts, heartbeat, source comment     | Makes collision ownership visible without inventing a Linear Assignee |
| `PlanProjection`                       | Typed steps, dependencies, acceptance, current step, revision | Does not reduce an executable plan to `AgentSession.plan` JSON        |
| `ExecutionRefs`                        | Thread, Session, Run, provider, Workspace, Lease refs         | Preserves the separation required by omega#214                        |
| `ExecutionControl`                     | Cancellation, revocation, fences, terminal reason             | A Linear stop signal and session status are not durable revocation    |
| `EffectProjection`                     | Intent, Block, effect status, Approval or owner-input refs    | Keeps execution effects under the durable OpenAgents contract         |
| `Evidence and Verification Projection` | Evidence, Receipt, Verification, reviewer, candidate digest   | Prevents an activity log or green check from becoming release proof   |
| `Owner Disposition`                    | Accepted, rejected, deferred, needs-owner, release decision   | Keeps owner authority explicit and typed                              |
| `Fixture Projection Provenance`        | Fixture version, digest, generated time, simulation flag      | Makes fixture state impossible to confuse with Canonical State        |

The initial fixture preserves unavailable optional fields as absent and emits
a Projection Issue when a required source field is unavailable. It must not
manufacture Repository Work Claims, Leases, Sessions, Receipts, Assignees, or
review decisions.

## 7. What the user sees

### 7.1 Work shell and navigation

The left rail opens on `My Work` with a visible `DEV MOCKS` and `v0.2.0 issue
snapshot` badge. The project switcher selects `Omega v0.2.0`. Navigation
offers Inbox, My Work, Initiatives, Projects, Cycles, Reviews, and Teams. Here,
Inbox is the Work/Attention Inbox projection rather than Work State. A
fixture-only route never persists as a production destination.

The header shows:

- the effective principal and `OpenAgentsInc` Organization;
- source freshness and a refresh action;
- project health, issue progress, current Release Stage planning value, and
  target version;
- saved views for critical path, unassigned, blocked, agent active, needs owner,
  in review, and verification.

### 7.2 Project overview

The project overview is backed by `Initiative`, `Project`, Release Planning
Record, `ProjectMilestone`, `ProjectUpdate`, and their Issue connections. It
shows:

- one launch summary and current health;
- the four milestone lanes and progress from closed/open issue state;
- the target candidate commit from the Release Planning Record, while an exact
  artifact appears only when a real Release Candidate record supplies it;
- recent project updates and decisions;
- the critical dependency path from omega#214 and openagents#9304 into
  omega#216;
- `Unassigned` as an explicit triage count rather than an invisible omission.

### 7.3 Issue list, board, and command menu

The same Issue collection supports table, board, and grouped-list layouts.
Columns include identifier, title, workflow state, blocked cue, milestone,
priority/severity, assignee, agent delegate, session status, review status,
updated time, and source repository. Grouping and filtering use model fields;
they do not fork the data into separate fixtures.

The command menu can navigate and filter immediately. Fixture mutations are
local simulations only. `Assign`, `Delegate`, `Start session`, `Steer`,
`Answer`, `Stop`, `Open review`, `Approve review`, and `Record owner
disposition` stay disabled until their exact capability is present, or run as
an unmistakably labelled local simulation in the debug/test fixture.

### 7.4 Issue detail and inspector

Selecting an issue opens one detail identity with these regions:

1. Issue title, description, state, labels, Project, Project Milestone, Release
   Planning Record, and source link.
2. Assignee and Agent Delegate as separate fields.
3. Dependency graph from issue relations.
4. Documents, Comments, Project Updates, and Repository Work Claim history.
5. Thread, Session, and Run references as separate links.
6. Agent session list with status, responsible creator, plan, summary, and
   safe activity stream.
7. Diff, pull request, checks, evidence, receipt, verification, and owner
   disposition sections.
8. An inspector that shows fixture provenance, durable identity, effective
   principal, capabilities, and denial reasons.

Missing data renders as `Not available from this source`, not as a plausible
placeholder.

### 7.5 Agent session and review surfaces

Delegating an Issue in simulation mode creates a local, non-canonical Agent
Session fixture projection, never a fake Repository Work Claim. The projection
starts `pending`, moves through `active` or `awaitingInput`, and ends
`complete`, `error`, or `stale`. Each transition records a public-safe
activity. The user can see which Person created the projection and which
app-backed User Projection resolves to the proposed Agent Member delegate.

The fixture should demonstrate all terminal and attention states through
separate deterministic scenes, not by pre-populating fake live work on the
default project. A review scene links a session Diff to a PullRequest and
check statuses. A green simulated check remains labelled simulation and never
creates Evidence, Verification, Owner Disposition, a Release Candidate, or a
Release.

## 8. Fixture and production boundary

Omega's current production-qualified Work Index admits four source entity
variants: Thread, Forensics Case, Forensics Run, and Effect Work. It validates
source identity and authority, binds each entity to owned lanes, and reveals
Inbox/My Work in production only when at least two real adapter lanes are
nonempty. Current detail mutation is title-only and Thread-backed; Forensics
and Effect rows are read-only.

The audited seams are the pinned
[Work Index model](https://github.com/OpenAgentsInc/omega/blob/989b5fe73078aa850ef64e466bcb15b100ee83e2/crates/omega_work_index/src/omega_work_index.rs),
[Work Index surface](https://github.com/OpenAgentsInc/omega/blob/989b5fe73078aa850ef64e466bcb15b100ee83e2/crates/agent_ui/src/omega_work_index_surface.rs),
[adapter/detail assembly](https://github.com/OpenAgentsInc/omega/blob/989b5fe73078aa850ef64e466bcb15b100ee83e2/crates/agent_ui/src/agent_panel.rs),
and accepted
[production navigation behavior](https://github.com/OpenAgentsInc/omega/blob/989b5fe73078aa850ef64e466bcb15b100ee83e2/docs/src/development/oaw-002-production-navigation-acceptance.md).
The owned contract boundary remains
[`all_work_boundary.v1`](https://github.com/OpenAgentsInc/openagents/blob/2b3ca74b051ad12f259aed573716d84540564ef6/packages/all-work-contract/README.md).

The `v0.2.0` fixture must not impersonate Effect Work, invent two real lanes,
or bypass that admission rule. The implementation should use this order:

1. Add a dedicated release-planning fixture adapter or preview projection that is
   compiled or enabled only for tests, test support, and debug builds.
2. Generalize the existing debug mock gate only if necessary. As with current
   Forensics fixtures, `OMEGA_UI_MOCKS=1` must require debug assertions, and a
   release or release-fast build must ignore it.
3. Mark the shell, rows, inspector, session simulation, and screenshots with
   `DEV MOCKS`, `Development mock data`, and the fixture digest/fetched time.
4. Exclude the adapter from production lane counts and durable command
   capability.
5. Normalize a persisted fixture-only selection to an admitted production
   destination when fixtures are unavailable.
6. Replace the adapter later with real owned projections from openagents#9304,
   openagents#9305, and omega#216 without changing the screen model.

If adding a fixture source variant would weaken Work Index validation, use a
preview-only view model outside the admitted Work Index instead. The preferred
result is faithful screen dogfooding; production admission remains fail-closed.

## 9. Fixture payload contract

The future checked-in payload should be deterministic and public-safe. At
minimum it contains:

```text
fixtureVersion
fixtureSha256
generatedAt
sourceRepositories[] { name, revision }
sourceSnapshotAt
organization
users[]
teams[]
initiatives[]
projects[]
projectStatuses[]
projectMilestones[]
cycles[]
releasePipelines[]
releaseStages[]
releases[]
workflowStates[]
labels[]
issues[]
issueRelations[]
documents[]
projectUpdates[]
customViews[]
agentSessions[]
agentActivities[]
pullRequests[]
diffs[]
openAgentsExtensions[]
```

The serialized names stay close to the Linear source for fixture traversal:
`users[]` decodes into User Projections, and `releases[]` decodes into Release
Planning Records plus Release Scope Links. Neither array creates canonical
Principals, Agent Members, Release Candidates, or Releases.

Stable logical IDs, normalized ordering, exact source URLs, and a digest make
visual and interaction scenes reproducible. Private prompts, credentials,
local paths, provider payloads, hidden reasoning, and customer data are never
fixture fields.

The initial snapshot has no agent sessions because the live open issues have
no public delegates or claims. Deterministic test scenes may layer explicitly
synthetic sessions over the source snapshot. User-created simulations live in
ephemeral local state and reset independently of the source issue data.
