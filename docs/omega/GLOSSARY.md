# Omega and OpenAgents glossary

- Status: canonical vocabulary
- Owner: OpenAgents
- Date: 2026-08-03
- Scope: current contracts and target All Work architecture

This document is the single vocabulary for Omega and the OpenAgents system that
Omega presents. It normalizes the current repository models and the target All
Work, collaboration, coding, execution, identity, sync, proof, outcome
economics, energy-aware placement, and interoperability models into
OpenAgents-owned terms.

The [App for All Work thesis](../allwork/README.md) owns the category direction.
The companion [All Work model](../allwork/model.md) owns the target core
vocabulary: Work, Session, Block, Host, Intent, Event, and Receipt. Development
planning is one domain profile over that model, not the root ontology.

The glossary is a naming authority, not an implementation-status authority.
Code, tests, ProductSpec, AssuranceSpec, the Omega roadmap, the Sol roadmap,
admitted work packets, and receipts remain authoritative for behavior and
delivery state.

## 1. Status marks

Each term has one or more status marks:

| Mark         | Meaning                                                                                                                                        |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Current**  | The term names a landed contract, data model, or supported product behavior. It does not claim that every intended surface is complete.        |
| **Target**   | The term is the chosen native name for an envisioned model or capability. It must not be presented as shipped without implementation evidence. |
| **Boundary** | The term states an authority, privacy, safety, or lifecycle distinction that current and target implementations must preserve.                 |
| **Interop**  | The term is an optional wire or federation concept. It does not replace OpenAgents command, work, receipt, or settlement authority.            |
| **Avoid**    | The term is ambiguous, misleading, or retired in this vocabulary. Use the named replacement.                                                   |

When a term is both **Current** and **Target**, its core meaning exists now and
its product reach is expected to grow.

## 2. Canonical model spine

The target All Work relationship is:

```text
Work
├── objective, owner, context, participants, state, policy, and outcome refs
├── Session ── runs on ──> Host
├── Block ── displays or controls part of the Work
└── history
      Actor ── submits ──> Intent
                              │
                          admission
                              │
                            effect
                           /      \
                       Event    Receipt

Verification, acceptance, release, and public claims remain separate.
```

One Work object can represent a repository task, CI job, deployment, incident,
service change, data job, research task, design review, or another bounded
outcome. A planning and portfolio profile can group Work without replacing it:

```text
Initiative → Project → Cycle / Project Milestone / Release Planning Record
                                                        │
                                                       Work
                                                        ├── Issue projection
                                                        ├── Work Relation
                                                        ├── Customer Need
                                                        ├── Document / Decision
                                                        └── Workroom / Thread
```

The Omega application relationship is also separate:

```text
App → Window → Workspace → Pane Group → Pane → Item
                              │
Selected Work ──> Block ──────┤
                              ├── Agent Panel / Thread View
                              ├── Project Panel / Editor / Terminal
                              └── Workroom / review / evidence views

IDE Project Graph → Work Context → Project Root → Worktree → Project File Ref
Session → Placement → Host → Agent Runtime / process / service
```

The separation is intentional. Work is not a Project, Session, process, or
thread. A development `Project` is not an IDE Project Graph; a Work object is
not a pane `Item`; a durable `Thread` is not a bounded `Session`; and a
filesystem `Worktree` is not an Omega `Workspace`.

## 3. Core naming rules

1. Use **Work** for the durable top-level object that holds an objective and its
   complete lifecycle. Do not make Project, Thread, Session, Run, or process the
   universal root.
2. Use **Session** for one live or resumable interaction with Work. A restarted
   process can create a new Session generation without creating new Work.
3. Use **Block** for a typed view or control surface inside Work. Visibility or
   interactivity never gives a Block authority.
4. Use **Host** for the identified placement where a Session or effect can run.
   Reachability and capability do not grant execution authority.
5. Use **Intent** for a typed request, **Event** for a durable admitted fact, and
   **Receipt** for an effect or observation bound to exact evidence. Keep all
   three distinct.
6. Use **Workspace** only for the Omega window/workbench container.
7. Use **Project**, **Initiative**, **Cycle**, **Project Milestone**, and
   **Release Planning Record** inside the optional planning and portfolio
   profile for any applicable Work Domain. These terms are not limited to
   software or product development. Use **IDE Project Graph** for the editor's
   capability graph over repositories and roots.
8. Use **Thread** for durable conversational or causal context. A Thread can be
   attached to Work, but it is not the Work object.
9. Use **Workroom** for a collaboration container whose membership, threads,
   Work, and agent participation are viewed together. A relay group can project
   a Workroom but does not define its OpenAgents authority.
10. Use **Assignee** for the accountable human or admitted organizational role
    shown on an Issue. Use **Agent Delegate** or **Delegate** for an agent
    assigned bounded Work. An agent is never the human accountable owner by
    implication.
11. Use **Evidence** for produced proof material, **Verification** for an
    admitted evaluation of evidence, and **Owner Disposition** for the owner's
    separate acceptance or waiver decision.
12. A **Capability** describes what an actor or runtime can do. A **Grant**
    describes what it may do in a named scope. Capability never implies grant.
13. Use **Release Planning Record** for pipeline, stage, scope, date, progress,
    and target-commit planning. Reserve **Release** for authorized publication
    or distribution after the applicable gates pass.

## 4. All Work and collaboration

### 4.1 Common work model

| Term                           | Status            | Definition                                                                                                                                                                                                                                                                                                       |
| ------------------------------ | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **All Work**                   | Target            | The OpenAgents category and system direction for interactive, automatic, remote, and production work across people, agents, processes, services, and machines. It is broader than any one planning domain.                                                                                                       |
| **Work**                       | Current, Target   | The durable top-level object for an objective and its complete lifecycle. The current generated boundary provides read-only summary and snapshot forms; target domain authorities bind the complete owner, context, participant, state, placement, policy, history, and outcome lifecycle.                       |
| **Work Domain**                | Current, Target   | A typed classification that adds domain-specific fields, Blocks, Intents, Events, and evidence rules to Work without replacing the common model. The generated boundary admits general, development, CI, deployment, operations, incident, research, security, design-review, service-delivery, and data values. |
| **Work Class**                 | Current, Target   | A versioned classification within a Work Domain that selects compatible routing, latency, interruption, privacy, evidence, verification, and cost policies. It never changes Work identity or grants execution by itself.                                                                                        |
| **Operational Work**           | Target            | The Work Domain for maintaining, changing, deploying, observing, or recovering a running system or organizational process. Operational access, urgency, and a successful command do not by themselves prove a safe outcome.                                                                                      |
| **Incident Work**              | Target            | The Work Domain for an abnormal condition from detection through triage, containment, recovery, investigation, corrective action, and after-action review. Incident resolution requires the admitted outcome and evidence, not merely a stopped alert or process.                                                |
| **Research Work**              | Target            | The Work Domain for a bounded question or hypothesis with sources, method, experiments, evidence, findings, limitations, and follow-on proposals. A persuasive narrative is not a verified research outcome.                                                                                                     |
| **Security Work**              | Target            | The authorized defensive Work Domain for assessment, scanning, finding triage, independent verification, remediation, regression, and controlled disclosure. Public source availability or technical capability does not grant target access, publication, or exploitation authority.                            |
| **Service Work**               | Target            | The Work Domain for fulfilling a bounded request or promised outcome for an internal, customer, or public recipient. Intake, commitment, execution, evidence, handoff, and acceptance remain separate records.                                                                                                   |
| **Objective**                  | Current, Target   | The bounded statement of what Work or a Run is intended to accomplish. It is versioned where changes can invalidate plans, claims, or evidence.                                                                                                                                                                  |
| **Work State**                 | Current, Target   | The admitted lifecycle state of Work under its owning lane or domain policy. The generated boundary carries the closed read vocabulary; state labels remain policy data, not executable authority.                                                                                                               |
| **Work Relation**              | Current, Target   | A typed edge between Work objects, such as parent, child, blocks, blocked-by, related, duplicate, or supersedes. The generated read boundary carries these edges; relations do not silently mutate either endpoint.                                                                                              |
| **Child Work**                 | Target            | Independently addressable Work that decomposes another Work object through a parent relation. It retains its own owner, state, Sessions, evidence, and outcome.                                                                                                                                                  |
| **Session**                    | Current, Target   | One live or resumable interaction with Work. Examples include a human review, agent turn, terminal process, background run, and incident-response period. A Session is not the complete Work object.                                                                                                             |
| **Block**                      | Current, Target   | A typed view or control surface inside Work, such as chat, editor, terminal, diff, plan, review, preview, log, metric, artifact, or receipt. It can display state or submit an Intent but owns no authority because it is visible.                                                                               |
| **Host**                       | Current, Target   | The identified placement where a Session or effect can run, including a local machine, remote host, sandbox, Pylon, Agent Computer, CI worker, or production target. Host reachability is not an execution grant.                                                                                                |
| **Intent**                     | Current, Target   | A typed request to act that binds actor, target, generation, idempotency identity, requested effect, and required authority. Admission is not proof that its effect occurred.                                                                                                                                    |
| **Event**                      | Current, Target   | A durable admitted fact about the Work lifecycle with stable order and resume rules. An Event is not necessarily an effect Receipt or complete evidence.                                                                                                                                                         |
| **Receipt**                    | Current, Boundary | A durable record that binds an effect or observation to exact evidence, such as the Intent, Host, generation, result, artifact, or observer. It does not by itself prove verification, acceptance, release, settlement, or a public claim.                                                                       |
| **Work History**               | Target            | The ordered Events, Intents, Receipts, interactions, and explicit gaps associated with Work. A transcript or terminal scrollback is not automatically complete Work History.                                                                                                                                     |
| **Work Projection**            | Current, Target   | A common read model over exact source refs from existing lane authorities. The generated Work summary/snapshot boundary is the first current slice; it is read-only and does not move authority into a new store.                                                                                                |
| **Work Index**                 | Target            | The cross-lane list of Work projected from native threads, agent Sessions, terminal Sessions, Full Auto Runs, Pylon Assignments, managed environments, and Workrooms.                                                                                                                                            |
| **Work Inbox**                 | Target            | The attention-oriented Omega view over the Work Index, organized by active, waiting, blocked, failed, completed, stale, and recoverable Work.                                                                                                                                                                    |
| **Outcome Record**             | Target            | The terminal or current synthesis of effects, changes, artifacts, checks, evidence, verification, delivery, acceptance, and remaining uncertainty for Work. These facts stay individually qualified.                                                                                                             |
| **Accepted Outcome**           | Target, Boundary  | A Work outcome accepted by the authorized party after the required evidence and verification. Generation, process exit, completion, merge, or relay acceptance alone cannot create it.                                                                                                                           |
| **Effective Authority Record** | Target, Boundary  | The user-facing projection of enforced authority for Work: owner, Host, lane, model class, tool profile, file and network scope, approval policy, device grants, generation, and revocation refs.                                                                                                                |
| **Execution Lane**             | Current, Target   | The adapter-backed path that performs a class of Work through an agent, person, job system, service, process, or production operation.                                                                                                                                                                           |
| **Lane Adapter**               | Target            | An extension that connects an agent, job system, service, or automation engine to the common Work model and declares capabilities, actions, events, authority needs, failures, and evidence.                                                                                                                     |
| **Host Adapter**               | Target            | An extension that connects a local, remote, sandbox, CI, managed, or production placement to the Host model.                                                                                                                                                                                                     |
| **Block Adapter**              | Target            | An extension that adds a typed Block and action set for a domain without creating a separate control plane.                                                                                                                                                                                                      |
| **Work API**                   | Target            | The versioned query, command, and subscription surface for listing Work, reading snapshots, resuming from cursors, submitting Intents, answering interactions, controlling Sessions, and fetching bounded outcomes.                                                                                              |
| **Work SDK**                   | Target            | Client libraries over the Work API plus adapter contracts for lanes, Hosts, and Blocks. No SDK client receives more authority than another interface.                                                                                                                                                            |

### 4.2 Common organization and work metadata

| Term               | Status          | Definition                                                                                                                                                                                  |
| ------------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Organization**   | Target          | An administrative scope for people, agents, Teams, policy, integrations, and Work. It is not the Work object or an Omega Workspace.                                                         |
| **Team**           | Target          | A stable group of people and Agent Members with a shared Work scope, workflow policy, and ownership boundary.                                                                               |
| **Priority**       | Target          | The explicit ordering importance of Work. Priority does not override safety, authority, or dependency gates.                                                                                |
| **Label**          | Target          | A scoped classification attached to Work or a domain collection. Labels support discovery and automation but do not grant capabilities.                                                     |
| **Workflow State** | Target          | A configured lifecycle label for an Issue within a Team. The owning Work policy admits state transitions; the display label alone is not authority.                                         |
| **SLA Policy**     | Target          | A policy that defines response or resolution expectations for a class of Work. Timers derived from it are projections over canonical timestamps.                                            |
| **Document**       | Current, Target | Durable authored knowledge with identity, revision, authorship, and links to Work. In the editor, the same word can name the text model behind a Buffer; context must make the layer clear. |
| **Attachment**     | Current, Target | A file or external-resource reference attached to Work or another resource with source, digest, audience, access, retention, and lifecycle facts.                                           |
| **Comment**        | Current, Target | An authored discussion record attached to Work, an Issue, Project, update, Document, or Thread. It does not replace a typed Intent, Event, Decision, or Receipt.                            |
| **Decision**       | Target          | A durable record of a choice, its decision maker, context, alternatives, rationale, date, and affected Work. A discussion Message is not a Decision until recorded as one.                  |
| **Outcome Metric** | Target          | A named measure used to judge Work or a domain collection. It must carry definition, source, time window, and truth limitations.                                                            |
| **Work Pulse**     | Target          | A derived overview of Work flow, outcomes, risk, capacity, cost, quality, domain signals, and outcome metrics. It is a Projection, never a second Work authority.                           |

### 4.3 Planning and portfolio profile

These terms organize Work in any applicable domain. Coding, operations,
incidents, service delivery, research, data, design, and development can use
the same portfolio UI without pretending that all Work is product development.
No Work Domain is required to use every layer.

| Term                        | Status           | Definition                                                                                                                                                                                                                                                                                                                                                |
| --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Portfolio Planning**      | Target           | The optional Organization layer that groups Work into Initiatives, Roadmaps, Projects, Cycles, and Project Milestones across applicable Work Domains.                                                                                                                                                                                                     |
| **Development Work**        | Target           | The software and product-development Work Domain profile. It can use the common portfolio vocabulary, customer context, code, review, and release resources but does not own that vocabulary.                                                                                                                                                             |
| **Initiative**              | Target           | A strategic collection of Projects and Outcome Metrics across applicable Work Domains. It connects Roadmap intent to Work without serving as a Session.                                                                                                                                                                                                   |
| **Roadmap**                 | Current, Target  | An ordered statement of intended outcomes and sequencing. A Roadmap supplies priority context; it does not by itself grant implementation, release, spend, or external-action authority.                                                                                                                                                                  |
| **Project**                 | Target           | A bounded collection of Work toward an outcome, with owner, Teams, scope, dates, Project Milestones, Documents, Updates, and Work refs. It is not the universal Work object or an IDE Project Graph.                                                                                                                                                      |
| **Project Status**          | Target           | A configured lifecycle state for a Project. It is distinct from a Project Update, which is an authored report.                                                                                                                                                                                                                                            |
| **Project Update**          | Target           | A dated authored report about a Project's health, progress, risk, and context. It can cite evidence and Outcome Metrics but is not canonical Work State, verification, or acceptance.                                                                                                                                                                     |
| **Initiative Update**       | Target           | A dated authored report about an Initiative's health, progress, risk, and context. It is distinct from Initiative lifecycle state.                                                                                                                                                                                                                        |
| **Cycle**                   | Target           | An optional time-boxed planning and delivery interval for a Team. Work can join a Cycle without changing its identity.                                                                                                                                                                                                                                    |
| **Project Milestone**       | Target           | A named checkpoint within a Project that groups expected Work completion or outcome evidence. Use this exact term where ambiguity with a release, billing, or verification milestone is possible.                                                                                                                                                         |
| **Release Planning Record** | Target, Boundary | The planning and API projection for an intended product version, including its Release Pipeline, Release Stage, target dates, target commit, Work or Issue refs, Documents, notes, links, and progress. It can adapt a Linear-shaped `Release` resource, but it is not an authorized Release, Release Candidate, deployment, acceptance, or Public Claim. |
| **Release Pipeline**        | Target, Boundary | An ordered planning workflow for Release Planning Records. Its type, stages, or `isProduction` presentation value cannot create production authority, a Deployment Gate, a Release Candidate, or a Release.                                                                                                                                               |
| **Release Stage**           | Target, Boundary | A coarse planning state for a Release Planning Record, such as planned, started, completed, or canceled, with a scoped display name and order. A stage named candidate, verification, published, or completed is not proof that the corresponding artifact or authority gate exists.                                                                      |
| **Release Scope Link**      | Target, Boundary | A typed planning relation between Work or its Issue projection and a Release Planning Record. It means intended inclusion only; the live release contract, gates, artifact identity, and release authority decide what actually ships.                                                                                                                    |
| **Customer**                | Target           | An external or internal recipient or stakeholder record with source, owner, access, status, and retention policy. Customer identity does not create a commitment, grant, or Work State.                                                                                                                                                                   |
| **Customer Need**           | Target           | A typed connection between a Customer and Work, a Project, Comment, Attachment, or other source context. It preserves provenance and access boundaries and does not itself create a commitment.                                                                                                                                                           |
| **Customer Signal**         | Target           | A normalized request, complaint, observation, or opportunity that can produce or support a Customer Need. It preserves source and consent boundaries and is not itself a commitment.                                                                                                                                                                      |

### 4.4 All Work API resource vocabulary

These names provide a familiar generated API and UI without creating another
domain authority. The API resource is a projection or specialization of the
canonical model named in its definition.

| Term                          | Status                    | Definition                                                                                                                                                                                                                                                                                                                   |
| ----------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Node**                      | Target                    | A globally addressable API resource with a stable `id`. In API context, it does not mean a Nostr relay, compute node, Host, or graph-execution node.                                                                                                                                                                         |
| **Entity**                    | Target                    | An API Node with creation, meaningful-update, and optional archive timestamps. It is a structural resource convention, not a universal domain aggregate.                                                                                                                                                                     |
| **User Projection**           | Target, Boundary          | The API and UI projection of a Principal as a person or Agent Member, including display identity, Membership, activity, and capability signals. A Linear-shaped `app` flag or `supportsAgentSessions` value helps presentation and discovery but does not create Agent identity, a Delegation Grant, or execution authority. |
| **Issue**                     | Current, Target           | The concrete planning and tracking projection of Work used by lists, boards, cycles, triage, and the generated API. The current boundary enforces shared `workRef` and revision semantics; it is never a second writable record.                                                                                             |
| **Issue Relation**            | Target                    | The Issue/API projection of a Work Relation. Relation types include parent/child, blocks, blocked-by, duplicate, related, and supersedes under the owning Work policy.                                                                                                                                                       |
| **Issue Label**               | Target                    | A Team- or Organization-scoped Label attached through an Issue projection.                                                                                                                                                                                                                                                   |
| **Assignee**                  | Current, Target, Boundary | The human or explicitly admitted organizational role accountable for an Issue and its underlying Work. The generated boundary keeps it structurally distinct from Agent Delegate. Assignment does not by itself grant execution, release, settlement, or external action.                                                    |
| **Delegate**                  | Target                    | The Agent Member selected to perform bounded Work. Effective authority comes from the Delegation Grant, not the field value.                                                                                                                                                                                                 |
| **Agent Session**             | Current, Target           | The agent-specialized API projection of a Session, bound to Work, an Issue or other context, an agent actor, status, plan, Activities, external refs, generation, and related Run. It is not the Work or Thread.                                                                                                             |
| **Agent Activity**            | Target                    | The agent-specialized projection of Work Activity, such as safe progress, plan, prompt, elicitation, action, response, artifact, or error. It is not hidden reasoning, an effect Receipt, verification, or disposition.                                                                                                      |
| **Agent Skill**               | Current, Target           | The agent-facing API resource for a versioned Skill, including ownership, sharing scope, inheritance, lifecycle, and usage projections.                                                                                                                                                                                      |
| **Favorite**                  | Target                    | A principal-owned ordered navigation reference to a heterogeneous resource or folder. Removing a Favorite does not delete the referenced resource.                                                                                                                                                                           |
| **Notification**              | Current, Target           | A principal-scoped Attention Item with actor, category, grouping, read, snooze, and target facts. It is a Projection, not Work State.                                                                                                                                                                                        |
| **Notification Subscription** | Target                    | A principal-scoped preference to receive Notifications for a named resource, view, or category. It is not a Work trigger unless a separate Loop or Intent is admitted.                                                                                                                                                       |
| **Template**                  | Target                    | Versioned defaults for creating a compatible resource. Applying a Template produces an explicit input revision and cannot inject authority.                                                                                                                                                                                  |
| **Custom View**               | Target                    | A saved filter, grouping, ordering, and display Projection over resources. It never becomes canonical resource state.                                                                                                                                                                                                        |
| **View Preferences**          | Target                    | Principal- or scope-owned presentation settings for a view. They do not change Work, policy, or authority.                                                                                                                                                                                                                   |
| **Integration**               | Current, Target           | A typed connection to an external service within an Organization and optional Team scope. It requires explicit credentials, grants, lifecycle, and receipts.                                                                                                                                                                 |
| **Webhook**                   | Current, Target           | A configured signed HTTP event-delivery boundary with resource scope, endpoint, enabled state, replay/idempotency policy, verification, and failure history. Delivery is not an admitted effect.                                                                                                                             |
| **OAuth Application**         | Current, Target           | An external application principal and grant surface. OAuth identity does not imply Agent Member identity or authority outside the granted scopes.                                                                                                                                                                            |
| **Audit Entry**               | Current, Target           | An administrative activity projection that identifies actor, action class, request facts, metadata, scope, and time. It is not automatically an effect Receipt or complete evidence.                                                                                                                                         |
| **Query**                     | Current, Target           | A read request over authorized resource Projections. Query selection, filter visibility, or possession of an identifier does not grant mutation authority.                                                                                                                                                                   |
| **Connection**                | Target                    | A cursor-paginated resource collection with Nodes and Page Info. OpenAgents adds freshness, truncation, loss, and refetch semantics where the source can be incomplete.                                                                                                                                                      |
| **Edge**                      | Target                    | A cursor-bearing membership of a Node in a Connection. It is an API pagination structure, not a Work Relation.                                                                                                                                                                                                               |
| **Page Info**                 | Target                    | The start/end cursors and forward/backward availability for a Connection, plus OpenAgents completeness and freshness facts where required.                                                                                                                                                                                   |
| **Create Input**              | Target                    | Decoded client-supplied fields for a create command. It remains untrusted until identity, authority, idempotency, revision, and policy admission succeed.                                                                                                                                                                    |
| **Update Input**              | Target                    | Decoded client-supplied changes for an existing resource. Omission, explicit null, clearing, and unchanged state must remain distinct.                                                                                                                                                                                       |
| **Mutation Payload**          | Target                    | The typed result of a mutation, including subject, success or typed failure, accepted revision, event cursor, actor, idempotency, authority decision, and Receipt refs as applicable.                                                                                                                                        |
| **API Error**                 | Target                    | A tagged client-visible failure with class, safe message, operation path, retry posture, request identity, and bounded response metadata. Raw variables, headers, credentials, and private bodies are not public diagnostics.                                                                                                |
| **Rate Limit State**          | Current, Target           | Provider- or service-reported request and complexity limits, remaining capacity, reset times, and retry delay. It is routing evidence, not a guarantee that the next request will run.                                                                                                                                       |

### 4.5 Ownership and collaboration

| Term                                | Status                    | Definition                                                                                                                                                                                                                                                                                                              |
| ----------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Accountable Owner**               | Target, Boundary          | The semantic role for the human or explicitly admitted organizational role answerable for Work, a Project, or an Initiative. The Issue API and UI expose this relation as the Assignee. Delegation does not remove this accountability.                                                                                 |
| **Agent Delegate**                  | Current, Target, Boundary | An Agent Member assigned bounded Work under a Delegation Grant. The generated boundary binds agent, grant, and generation separately from Assignee. It can execute and report only within admitted scope and does not inherit owner authority.                                                                          |
| **Delegation Grant**                | Target, Boundary          | A revocable, scoped authorization that binds a principal, target Work, allowed actions, constraints, issuer, validity, and evidence requirements.                                                                                                                                                                       |
| **Repository Work Claim**           | Current, Boundary         | The cross-session coordination record that names a repository Work scope, holder, owned paths and hot contracts, evidence heartbeat, and explicit release. It prevents collisions but is not an Assignee, Agent Delegate, Lease, Capability Grant, merge authority, or proof that implementation is active or complete. |
| **Participant**                     | Current, Target           | A person, agent, process, or service associated with Work or a Session under a named role and scope. Participation does not imply authority.                                                                                                                                                                            |
| **Agent Member**                    | Current, Target           | An agent represented as a first-class participant in an Organization, Team, or Workroom, with identity, owner relation, capabilities, and explicit grants.                                                                                                                                                              |
| **Work Coalition**                  | Target                    | A temporary, Work-scoped group of people, agents, services, data sources, compute providers, reviewers, or other contributors assembled for one outcome. It is not a durable Team, and every participant retains separate identity, grants, evidence, and attribution.                                                  |
| **Public Agent Surface**            | Boundary                  | A separately admitted public-safe profile, contact, intake, or service surface for an Agent Member. It is not a current standalone Sarah or public-persona product; reachability and advertised capability never grant execution or prove delivery.                                                                     |
| **Service Promise**                 | Current, Target, Boundary | A bounded commitment to deliver a named Service Work outcome for a recipient, with scope, evidence, acceptance, timing, price or payment posture when applicable, and closeout rules. Intake, payment, activity, and completion are not the promised outcome by themselves.                                             |
| **Membership**                      | Current, Target           | A scoped relation between a principal and an Organization, Team, Workroom, or interoperable group. Membership and Role labels do not imply arbitrary command capability.                                                                                                                                                |
| **Role**                            | Current, Target           | A named bundle of expected responsibilities or presentation labels. Effective authority still comes from policy and grants.                                                                                                                                                                                             |
| **Workroom**                        | Current, Target           | A collaboration container that combines members, agents, Threads, Work, Decisions, activity, and optional voice or code Blocks. Its canonical coordinate must identify both OpenAgents scope and any interoperable room.                                                                                                |
| **Community Workroom**              | Current                   | A membership-scoped Workroom for invited people and their attested agents. It separates community coordination from private owner-agent Work.                                                                                                                                                                           |
| **Private Owner Workroom**          | Current, Boundary         | The private Workroom between an owner and owned agents. Private memory, credentials, raw traces, and owner-only controls stay here unless separately disclosed.                                                                                                                                                         |
| **Two-Room Rule**                   | Current, Boundary         | The rule that private owner-agent Work and community collaboration use distinct Workrooms, Membership, disclosure, and evidence paths.                                                                                                                                                                                  |
| **Channel**                         | Target                    | A named topical lane within a Workroom. It organizes Threads but does not create a separate Work or command authority.                                                                                                                                                                                                  |
| **Thread**                          | Current, Target           | A durable ordered conversational or causal context for Messages, Events, Decisions, and Sessions. A Thread can be attached to Work and outlive many Sessions, but it is not the Work object.                                                                                                                            |
| **Work Thread**                     | Target                    | The primary Thread attached to Work. It presents discussion and activity while Work remains the durable lifecycle object.                                                                                                                                                                                               |

| **Candidate Finding**           | Current, Target           | A typed claim that an assessment discovered a possible defect or security issue, with target, source refs, mechanism, severity proposal, assumptions, and evidence boundary. It is neither a confirmed vulnerability nor publication authority.                                                                                                 |
| **Hypothesis**                  | Current, Target           | A falsifiable explanation or risk statement that still requires a named test or observation. It remains distinct from a Candidate Finding and confirmed result.                                                                                                                                                                                 |
| **Finding Verdict**             | Current, Target, Boundary | An independently produced judgment such as `confirmed`, `dismissed` or `refuted`, or `inconclusive` over a Candidate Finding, bound to executed evidence and the exact target. Model agreement alone cannot create it.                                                                                                                          |
| **Model Panel**                 | Target                    | A set of independently instructed model roles that propose, challenge, verify, or analyze a question. Disagreement is a diagnostic signal; agreement is neither necessary nor sufficient for truth.                                                                                                                                             |
| **False Green**                 | Current, Target, Boundary | A passing or healthy-looking result that could not have failed because the required source, environment, oracle, effect, or observation was absent, mocked, mirrored, rounded away, or never executed.                                                                                                                                          |
| **False-Green Class**           | Current, Target           | A named structural cause of False Green, including fixture assertion, API mirror, mocked seam, coverage theater, unexecuted proof, missing dependency, stale projection, and metric round-up.                                                                                                                                                   |
| **Security Invariant**          | Current, Target           | A named safety property that must hold across the relevant source, configuration, build, artifact, runtime, and operational boundaries. It includes its scope, failure consequence, and required witnesses.                                                                                                                                     |
| **Security Invariant Manifest** | Target                    | A versioned set of Security Invariants, target bindings, required evidence, observers, stopping rules, and disclosure policy for Security Work. It does not authorize a scan, remediation, or publication.                                                                                                                                      |
| **Artifact Provenance Witness** | Target                    | A deterministic observer that binds a built or released artifact to the exact source, configuration, dependencies, symbols, or runtime provider properties needed by a Security Invariant.                                                                                                                                                      |
| **Attack-Surface Ranking**      | Target                    | A risk-based ordering of code, configuration, artifacts, and interfaces by exposure, privilege, asset value, and distance from attacker-controlled inputs to security-critical sinks. It allocates review effort; it is not a vulnerability verdict.                                                                                            |
| **Reachability Witness**        | Target                    | Evidence that a named input, dependency, symbol, or implementation can or cannot reach a security-critical effect in the exact configured and built target. Source naming alone is not reachability.                                                                                                                                            |
| **Variant Hunt**                | Target                    | Bounded search for a confirmed defect shape across related targets, revisions, configurations, forks, or dependencies. Each candidate retains its own target evidence and disclosure state.                                                                                                                                                     |
| **Adversary Simulation**        | Target, Boundary          | An isolated, authorized defensive reproduction of an attack path against owned or admitted fixtures and environments. | **Regression Watch**            | Target                    | A recurring check that evaluates new target revisions against confirmed shapes, Security Invariants, witnesses, and the Regression Corpus, with explicit freshness and stopping rules.                                                                                                                                                          |
| **Evidence Ladder**             | Current, Target           | An ordered set of proof rungs from claim or static clue through executable observation, artifact witness, independent reproduction, or stronger evidence. A result is reported only at the highest rung actually reached.                                                                                                                       |
| **Evidence Graph**              | Current, Target           | A typed graph connecting claims, sources, experiments, artifacts, observers, receipts, contradictions, corrections, and public statements. It preserves derivation and missing edges rather than flattening them into prose.                                                                                                                    |
| **Regression Corpus**           | Current, Target           | A versioned collection of historical failures, confirmed shapes, controls, variants, and Fixtures used to prevent recurrence and evaluate new methods. Corpus membership retains provenance and contamination limits.                                                                                                                           |
| **Coverage Ledger**             | Target                    | A security coordination Projection of which targets, revisions, profiles, invariant classes, and evidence rungs have been assessed, remain stale, or have never been covered. Sensitive gaps require scoped visibility.                                                                                                                         |
| **Scan Profile**                | Target                    | A versioned assessment configuration naming target scope, Materialized Source Set rules, model and harness roles, prompts, tools, budgets, exclusions, evidence requirements, and disclosure policy.                                                                                                                                            |
| **Divergence Signal**           | Target                    | A material disagreement across independent Runs, Arms, models, Scan Profiles, or observers that creates review attention. It is a reason to investigate, not an automatic finding.                                                                                                                                                              |
| **Trace**                       | Current                   | An ordered record of runtime, tool, command, and interaction events. A raw Trace can be private; public traces require redaction and explicit publication.                                                                                                                                                                                      |
| **Proof Replay**                | Current, Target           | A deterministic or bounded re-evaluation of recorded inputs, transitions, and evidence used to inspect whether a claim follows. Replay does not re-authorize side effects.                                                                                                                                                                      |
| **After-Action Report**         | Target                    | A durable Incident Work artifact that records timeline, impact, contributing conditions, containment, recovery, evidence, corrected beliefs, corrective Work, owners, and unresolved uncertainty. It is not a substitute for the underlying records.                                                                                            |
| **Responsible Disclosure**      | Target, Boundary          | The controlled process for privately reporting a potential vulnerability to the responsible maintainers, coordinating verification and remediation, setting an embargo, and publishing only through the admitted gate.                                                                                                                          |
| **Disclosure Embargo**          | Current, Target, Boundary | A time- and audience-bounded restriction on sharing sensitive finding details while verification and remediation proceed. Expiry policy does not independently grant publication.                                                                                                                                                               |
| **Finding Commitment**          | Target, Interop           | A digest-bound commitment to a finding or evidence package published before reveal so discovery order can be shown without disclosing the sensitive content. It is not proof that the finding is correct.                                                                                                                                       |
| **Publication Gate**            | Target, Boundary          | The authority, verification, remediation-coordination, redaction, legal, and audience checks required before a security report, trace, model output, or evidence package is disclosed.                                                                                                                                                          |
| **Public-Safe Projection**      | Current, Boundary         | A deliberately redacted projection that contains only fields admitted for public disclosure. Absence from it does not imply absence from private canonical state.                                                                                                                                                                               |

## 19. Authority summary

| Question                                                    | Authority                                                                                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| What Work exists and what state is it in?                   | The existing owning lane today; the target Work Projection composes exact source refs until an admitted authority migration occurs |
| What may an agent do?                                       | Applicable policy plus an explicit Capability Grant or Delegation Grant                                                            |
| What happened during execution?                             | Runtime, Intent, Event, command, Run, Work Activity, and Receipt records from the owning authorities                               |
| Which model or provider account actually ran?               | Provider-reported Effective Model Identity and Model Identity Receipt bound to the exact Turn or Run                               |
| Is a history or result complete?                            | Its Evidence Boundary, Evidence Completeness, Loss Accounting, freshness, and source refs                                          |
| What does the UI show?                                      | Rebuildable Blocks and Projections over canonical and validated interoperable records                                              |
| What did a relay accept?                                    | Relay Receipt only                                                                                                                 |
| What did Git accept?                                        | Git objects and refs under repository policy                                                                                       |
| What proves a ProductSpec criterion?                        | Evidence Receipt plus admitted Verification Receipt                                                                                |
| What does an external source require OpenAgents to build?   | Nothing by itself; FastFollowSpec records Learning Intent, and ordinary authority must separately admit a Work Proposal            |
| What turns a security scan result into a confirmed finding? | An independent Finding Verdict over executed evidence at the required Evidence Ladder rung                                         |
| What may be published about Security Work?                  | Responsible Disclosure and the applicable Publication Gate after verification, coordination, redaction, and authority checks       |
| What did the owner accept?                                  | Owner Disposition                                                                                                                  |
| What is the public state of an OpenAgents capability claim? | The exact Product Promise in the current Promise Registry, with its state, evidence, blockers, and transition receipts             |
| What is released or otherwise publicly claimable?           | The applicable release and Public Claim authority after its gates pass                                                             |
| What qualifies as external demand?                          | Demand Provenance backed by the required external receipts; dogfood, fixtures, credits, and modeled revenue remain separate        |
| Why and where was Work dispatched?                          | The admitted Dispatch Decision, exact Dispatch Policy revision, input refs, Placement, and resulting Receipts                      |
| What is settled?                                            | The designated settlement ledger and authority, never a chat message or relay event alone                                          |
