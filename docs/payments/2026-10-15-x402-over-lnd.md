# x402 over LND, as receiver and as sender (research and build, 2026-10-15)

**Verdict: yes.** Our x402 profile ([NIP-X402](../../nips/openagents/NIP-X402.md),
`exact` scheme, `lnbtc` networks, BOLT11 with a description hash) maps onto
stock LND 0.21 RPCs with no protocol change and no LND patch. The receiver
side is built and staged on the pay front behind a config switch. The sender
side is now built: `openagents x402 fetch --pay-with lnd` pays a challenge from
any LND node over gRPC. What remains is production, not code: a funded
`oa-lnd-1` with inbound liquidity, then flipping one setting on `oa-pay-1`.

Related: [the `lnd-sdk` plan](2026-10-15-lnd-sdk-plan.md) (§3, §4 P0/P1),
[the LND host runbook](lnd-host.md), issues #11751 (P0 SDK), #11752
(`oa-lnd-1`).

A [public signet research run](2026-10-16-lnd-signet.md) now exercises real
HTTP, companion Payment, and MCP purchases through these crates. Signet uses
a separately selected research policy; the standard upstream network set
in the table below is unchanged.

## Our x402 against upstream

Upstream x402 v2 (x402.org, the x402-foundation repo) started on EVM and
Solana: `exact` there means an EIP-3009 `transferWithAuthorization` or an SVM
transfer, signed by the payer and broadcast by a facilitator through
`/verify` and `/settle`. We never use those networks. Upstream has since
merged an `exact` Lightning method (`scheme_exact_lnbtc.md`, pinned in the NIP),
and ours is that method:

| | Upstream EVM `exact` | Ours (`exact`, Lightning) |
| --- | --- | --- |
| Network | `eip155:8453` and others | `lnbtc:<genesis>`, mainnet or testnet only; no regtest or signet |
| Asset, amount | ERC-20 units | `BTC`, a millisatoshi decimal string |
| `payTo` | an address | the receiving node's 33-byte identity key, hex |
| Challenge | price and address | a BOLT11 in `extra.invoice`, signed by `payTo`, whose **description hash** is the request-binding digest (`extra.requestHash`); an inline description is refused |
| Payment proof | signed authorization | the 32-byte **preimage**, which must hash to the invoice's payment hash |
| Facilitator | broadcasts the transfer | only consumes the proof once (replay store); it never sends money; `/verify` is not used (upfront flow) |
| Headers | `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE` | the same |

So anything that can issue a signed BOLT11 with an exact amount and a
description hash, and anything that can pay one and return the preimage, can
play x402. LND can do both.

## Receiver: requirement to LND RPC

| x402 requirement | LND | Where |
| --- | --- | --- |
| Exact-amount invoice, msat precision | `Lightning.AddInvoice{value_msat}` | `lnd_sdk::Client::create_invoice_with_hints` |
| Description hash = request digest, no inline `d` | `AddInvoice{description_hash, memo: ""}`; LND emits tag `h` only | same; it decodes the result and refuses a mismatch |
| `payTo` signs the invoice | LND signs with its node key; we check the recovered payee equals the configured `node_id` | `Wallet::connect_receiver` checks identity and network at connect; the front reads the payee to find the issuing receiver |
| Expiry = `maxTimeoutSeconds` | `AddInvoice{expiry}` | the SDK re-decodes and checks expiry |
| Private channels reachable | `AddInvoice{private: true}` plus explicit hints from `ListChannels` / `GetChanInfo` | `private_route_hints()`; the invoice macaroon has `offchain:read` for this |
| Settlement detection | `LookupInvoice` (state `SETTLED`, `amt_paid_msat >= value_msat`, `settle_index > 0`) when the proof arrives; `SubscribeInvoices{settle_index}` for push consumers | `received_msat`; `settlements()` resumes from the consumer's saved settle index (exactly once if the sink commits effect and index together) |
| Replay protection | none needed from LND | `openagents_x402` replay store, keyed by payment hash; a second proof is `duplicate_settlement` |
| Preimage proof | LND reveals the preimage to the payer only when it settles the HTLC | the facilitator checks `sha256(preimage) == payment_hash` |
| Credential scope | baked macaroon: `info:read`, `invoices:read/write`, `offchain:read` | `Role::Invoice`; it cannot send or open channels |

Built in `crates/openagents-cli/src/pay_lnd.rs` (`LndReceiver` implements
`openagents_x402::server::Receiver`) and `crates/x402/src/front.rs`
(per-resource and default receivers, keeping the old receiver known so its
open invoices still settle after a switch or rollback).

## Sender: requirement to LND RPC

| x402 requirement | LND | Where |
| --- | --- | --- |
| Pay the challenge once | `Router.SendPaymentV2{payment_request, fee_limit_msat, timeout_seconds}`; **no transport retry** | `lnd_sdk::Client::send_payment` |
| Fee cap | `fee_limit_msat` | the x402 policy and `--max-fee-msat` |
| Uncertain outcome | `AlreadyExists` on a second send for the same hash, then `Router.TrackPaymentV2` | the SDK tracks instead of resending; the CLI reports "still in flight" with the hash and never resends |
| Preimage as proof | the `SUCCEEDED` payment's `payment_preimage` | the CLI re-checks `sha256(preimage)`, the amount, and the fee against the invoice before it retries the request |
| Network | GetInfo chain network vs the invoice currency | settings `network` must match the challenge's `lnbtc` network |
| Credential scope | `info:read`, `offchain:read`, `offchain:write` | `Role::Payout`; file must be mode 0600 |

Built in `crates/openagents-cli/src/x402_lnd.rs`: `openagents x402 fetch|call|buy
--pay-with lnd [--lnd FILE]`.

## Blockers checked

- **Inline descriptions.** Our validator refuses any invoice with tag `d`.
  LND emits only `h` when `description_hash` is set and `memo` is empty, which
  the SDK guarantees. The 2026-10-15 regtest run confirmed both directions on
  a real LND signer: the description-hash invoice validates; an `--memo`
  invoice is refused.
- **`payTo` signature.** LND invoices omit the explicit `n` tag; our decoder
  recovers the signer from the signature and requires low-S. Real LND
  signatures pass.
- **Route hints.** `oa-lnd-1` will start with private channels from LSPS1,
  so invoices carry `r` hints; our decoder validates them. Checked on regtest
  with a private channel in both directions.
- **Regtest.** x402 admits only mainnet and testnet. A full HTTP 402 run on
  regtest would be refused by design, so the regtest fixture signs x402 checks
  with an unfunded offline testnet LND, and pays and tracks on regtest. A
  true end-to-end 402 run needs mainnet (or a funded testnet node).
- **Feature bits.** Our decoder refuses unknown required feature bits. The
  regtest check above decoded a real LND 0.21 invoice with its default bits,
  so they pass; recheck after any LND upgrade.

## How to test in production once `oa-lnd-1` has channels

Receiver (on `oa-pay-1`, owner-approved):

1. Stage the binary and credentials: `deploy/lnd/stage-receiver.sh COMMIT BINARY`.
   It writes `/run/openagents-lnd-receive/receive.toml` with `backend = "mdk"`.
2. Copy that `[lnd_receive]` stanza into `/etc/openagents-pay/routes.toml`,
   set `backend = "lnd"`, and restart `openagents-pay-front`. This moves only
   the exact resource `x:openagents-agent-credit` (agent credit) to LND.
3. To move every x402 resource (plugin calls and hosted resources), also set
   `all_resources = true` in the same stanza.
4. Roll back by setting `backend = "mdk"` and restarting; keep the stanza so
   LND invoices already issued still settle.

Sender (any machine):

```toml
# ~/.openagents/x402/lnd.toml, or pass --lnd FILE
endpoint = "https://HOST:10009"
certificate_sha256 = "…"   # openssl x509 -in tls.cert -outform DER | shasum -a 256
node_id = "03…"            # lncli getinfo
macaroon = "pay.macaroon"  # chmod 600; offchain:write
network = "mainnet"
```

```sh
openagents x402 fetch https://api.openagents.com/x/NAME --max-msat 10000 --pay-with lnd --lnd ~/lnd.toml
```

The sender and receiver can be the same node only if it can route to itself
(it cannot pay its own invoice); use a second node or the Spark wallet as the
buyer when the receiver is `oa-lnd-1`.
