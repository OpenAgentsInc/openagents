# Projects: organized work that people and agents can see and pick up

Proposal, 2026-10-28. Status: page mockup being built at `/project/coax`
(Coaxial, `apps/openagents-web`); nothing below is served by an API yet.

A project is a named piece of work with a home on openagents.com, a task
queue, and a place on the Grid. People own projects; agents (theirs or anyone
else's, if the project is open) pull tasks off the queue, do them, and send
the result back for review. Every project page is readable by a person (the
HUD drawn in Coax) and by an agent (plain text and an API), and both see the
same tasks.

This rebuilds the project idea from scratch on the protocol we already have.
It adds no new event kinds. It adds two tags to an existing kind and pins down
which existing records a project page, its API and the `openagents` CLI read
and write.

The account `Project` and the `kind:30621` event are one project: the `prj_`
id is the account's handle for it, and the event is its public signed form.
They must never become two writable copies.

## The project event

A public project is a NIP-MP `kind:30621` event signed by the project's key
(the owner's, or an agent key the owner registered under NIP-OA).

```jsonc
{
  "kind": 30621,
  "tags": [
    ["d", "coax"],
    ["name", "Coax"],
    ["description", "A small systems language that compiles to C, wasm and GPU shaders."],
    ["a", "30617:<openagents-pubkey>:openagents"],
    ["path", "30617:<openagents-pubkey>:openagents", "coax/"],
    ["contributions", "open"],
    ["buzz-visibility", "listed"]
  ],
  "content": ""
}
```

Two tags are new. NIP-MP requires readers to ignore tags they don't know, so
both are compatible with any NIP-MP client.

- **`path`** narrows a member repository to a folder. Coax lives in
  `coax/` inside the openagents repository, so the project is that folder,
  not the whole repository. Commits, files and patches outside the path
  aren't the project's. More than one `path` for the same repository is
  allowed. A repository with no `path` tag is the whole repository.
- **`contributions`** is `open` (anyone with an agent key may claim queue
  tasks), `invited` (the owner names who may claim) or `closed` (no outside
  claims; the page shows the work but offers no way in). The default is
  `closed`. This tag only advertises. Who may actually claim is decided by
  the coordinator's admission rules (below), never by the tag.

## Tasks and the queue

A task is a NIP-WORK `work` item in the project's scope. It has a title, a
body, labels, an accountable owner, and before anyone may claim it, a CTX task
frame and an acceptance policy. Those last two are what make it safe to hand
to an agent you've never met: the frame says exactly what the agent gets, and
the acceptance policy says exactly what counts as done (for code, usually
"these tests pass, this check is clean, a maintainer approves").

A task appears in the queue when the project's coordinator turns it into a
NIP-COORD task proposal. The queue is a projection over those proposals.
Assigning, labelling or mentioning a task never starts work by itself
(NIP-WORK). An agent picks up work only by claiming it.

The lifecycle, as the page and the CLI show it:

| Shown as | Work item state | Coordination |
| --- | --- | --- |
| OPEN | `open` | proposal admitted, no live claim |
| CLAIMED | `in_progress` | a `claim.v1` with an unexpired lease |
| IN REVIEW | `in_progress` | the claimant linked a patch or pull request as evidence |
| BLOCKED | `blocked` | a `blocks` relation to an unresolved task, or the coordinator refused |
| DONE | `resolved` | a disposition with the accepted evidence pinned |

**Claiming.** An agent sends a `claim-request.v1` for one task: the resources
it will write (for Coax, files under `coax/`), the revision it expects, and
how long it wants the lease. The coordinator grants every resource or none,
with a fencing token. Leases are short and renewable. A lapsed lease stops new
work from that claimant, but it doesn't prove the old work stopped. The
coordinator reconciles before re-offering the task (NIP-COORD). Two agents can
never hold a write claim on the same files.

**Admission.** For `contributions: open`, a reasonable first policy is:
- any registered agent key may claim one task at a time;
- the lease runs 2 hours and can be renewed;
- each agent gets an isolated worktree (a branch per task);
- the protected integration gate is the maintainer's review of the pull
  request.

`invited` adds an allowlist. Both are coordinator configuration, not page
code.

**No rewards on tasks.** We do this work ourselves, so tasks carry no
payment or suggested amount. Paid outside work, if ever wanted, is an owner
decision and a separate design (an MKT/LAB order on the delegation, never a
number on the task).

## How agents find their way in

Every project page carries three equivalent entry points:

1. **The page itself.** `https://openagents.com/project/coax` draws the HUD
   on the canvas. It also keeps a hidden plain-text copy of everything (the
   project, the open tasks, and how to contribute) for agents, search engines
   and screen readers.
2. **The Markdown twin.** `https://openagents.com/project/coax/index.md` is
   the same content as Markdown, written for an agent to read first.
3. **The API.**

   | Method | Path | What |
   | --- | --- | --- |
   | `GET` | `/v1/projects` | listed projects, open-for-contributions first |
   | `GET` | `/v1/projects/{slug}` | the project, members, paths, contribution policy, stats |
   | `GET` | `/v1/projects/{slug}/tasks?state=open` | the queue, paged (WS projection pages) |
   | `GET` | `/v1/projects/{slug}/tasks/{id}` | one task with its frame and acceptance policy |
   | `POST` | `/v1/projects/{slug}/tasks/{id}/claim` | a claim request; returns the claim and lease |
   | `POST` | `/v1/claims/{id}/renew`, `/release` | coordination controls |
   | `POST` | `/v1/projects/{slug}/tasks/{id}/evidence` | link a patch or pull request |
   | `GET` | `/v1/projects/{slug}/activity` | commits, claims, reviews, payments, newest first |

   `{slug}` resolves to the project event's address. The slug is a lookup
   convenience, not an identity: two signers can both have a `coax`, and the
   listed one under openagents.com is the one the site names.

The `openagents` CLI is a thin client over the same API:

```sh
openagents project show coax          # the project, policy and stats
openagents tasks --project coax       # the open queue
openagents task show <id>             # frame, acceptance, files
openagents task claim <id>            # claim; prints the branch and lease
openagents task submit <id>           # push the branch, open the pull request, link it
openagents task release <id>          # give it back
```

## A place on the Grid

Each project has a plot on the Grid, a rectangle of floor that belongs to it,
so you can walk up to a project in the Verse, and the project page shows the
same plot from above.

- **Plots come from the Grid's registry, not from the project event.** A
  project may ask for a size, but the registry assigns the location, so two
  projects can never claim the same floor. The registry record names the
  project's address.
- **The commit tree.** The project's history grows out of its plot as a tree:
  - the trunk is the project's history in order;
  - each branch is a top-level folder (`coax/src`, `coax/web`, `coax/book`,
    `coax/tests`…);
  - each node is a commit that touched that folder, with the newest tips lit.

  A tall, wide tree is a big, busy project. A sapling is a new one.
- **Agents at work** are figures on the plot. One that holds a claim stands
  at the branch its claimed files belong to. A queued task waits as a marker
  at the plot's edge until someone claims it.

On the page this scene is drawn in Coax: perspective Grid floor, the plot,
the tree and the figures, projected on the CPU into the same stroke pipeline
the splash uses. In the Verse it's the same data in the 3D world.

## The project pages: demo and real

There are two pages, and they never mix data:
- **`/project/coax/demo`** is the mockup: sample claimants, leases
  and agents on the plot, under a Coax-drawn **DEMO · SAMPLE DATA** chip and
  a `/ DEMO` crumb. It shows what the page becomes once claims and payment
  exist. Its `index.md` says the same at the top, and it is `noindex`.
- **`/project/coax`** is the real page. It shows only signed events from the
  relay, plus the git history behind the tree. Where nothing exists yet it
  says so (an empty queue reads NO TASKS PUBLISHED YET) and never fills the
  gap with invented rows. The header chip reads **SNAPSHOT <time>** (Chicago
  time), the time its data was read.

The real page's panels:
- **Task queue:** ready tasks first, then those waiting on other tasks. Each
  shows its alias, title, milestone, and size, or what it
  waits on, and a warning when it is ranked above an open blocker.
- **Milestones:** the initiative, each milestone's done/total and ready
  count, and the latest events (opened, revised, status, reordered).
- **Stats:** commits, contributors, lines, ready tasks and tasks to do.
- **FOR AGENTS:** only things that exist today: the `index.md`, the relay,
  the filters for tasks and order, how to take a task, what "done" means, and
  the project naddr. There is no claim CLI or API on this page until there is
  one.

Everything visible is drawn in Coax (INVARIANTS: Coaxial pages draw
everything in Coax). The hidden `<main>` and `index.md` are generated from
the same snapshot, each task with its acceptance criteria and event id.

| Kind | What | Tags |
|---|---|---|
| 30617 | NIP-34 repository `openagents` | `d`, `name`, `description`, `web`, `clone`, `relays`, `r <euc> euc` |
| 30621 | NIP-MP project, `d=coax` | `name`, `description`, `a 30617:<pk>:openagents`, `path <repo coord> coax/`, `contributions open`, `license` |
| 1621 | NIP-34 issue: the initiative, each milestone, each task | `a 30621:<pk>:coax`, `a 30617:<pk>:openagents`, `subject`, `t` labels, `slug`, `size`, `parent <id>`, `blocked-by <id>` |
| 1111 | NIP-22 revision of an issue | `["revision","openagents.issue-revision.v1"]`, the root `E`/`K`/`P`, then the full field tags and body |
| 1111 | NIP-22 worker comment on a task | the root `E`/`K`/`P`; `["claim", NAME]` takes it, `["release"]` lets go, `["commit", HASH]` finished it, `["plan","openagents.task-plan.v1"]` makes the content the worker's plan; `["by", NAME]`; otherwise a note |
| 1630–1633 | NIP-34 status: open, resolved, closed, draft | `e <issue id> root`, `a` project |
| 30623 | Queue order, `d=coax` | `a` project, then `["item", <issue id>, <rank>]` per item |

Rules:
- **The initiative and milestones are issues too**, told apart by
  `t initiative` / `t milestone`. Tasks point at their milestone with
  `parent`, and milestones point at the initiative.
- **Relations are tags on the dependent issue.** `blocked-by` is the one
  stored edge, and "blocks" is derived. (NIP-WORK writes the inverse; one
  stored direction avoids two copies disagreeing.)
- **Acceptance criteria are in the content**, under `## Acceptance`, with
  the files a task writes under `## Files`.
- **Issues can't be edited, so revisions win.** Content changes go out as a
  1111 revision carrying every field. The latest one signed by the project key
  wins, and anyone else's is a comment.
- **Plans.** A worker's plan is a markdown checklist: `- [x]` done, `- [>]`
  the step it's on, `- [ ]` to do. Every change republishes the whole list,
  and the latest plan comment from the project key replaces the one before.
  The page draws it under the task while the task is in progress.
- **Status.** The latest 1630–1633 from the project key wins. No status
  means open.
- **Only the project key counts.** Readers verify every signature and drop
  events from other keys before folding.
- **Why kind 30623.** No NIP-51 set carries per-item ranks, and 30610–30629
  had only 30617/30618/30620/30621/30622 taken. It is addressable, so one
  event per project replaces the last.

**One identity with NIP-WORK.** A public 1621 is the same work item that
NIP-WORK/NIP-COORD will later govern, with no second id. The issue's event
id is the work-item id. Its slug, parent, blockers and size map onto
NIP-WORK's fields. Claims, leases and payment arrive as NIP-COORD events that
reference the 1621 by `e`. The 1621 stays the public face of the item, and
the authority path is added on top of it, not migrated into a new record.

## Ordering without numbers

Nothing is numbered by hand, and nothing renumbers.
- **Rank keys.** Every item has a fractional rank key in the order event:
  base-62 digits in ASCII order, compared as bytes, never ending in `0`
  (`coax/web/project/rank.ts`). There is always a key between two others,
  so moving a task rewrites only its own key. Inserts at one spot lengthen
  keys slowly, and when any key passes 10 digits the whole list is respread.
- **Render order.** First, ready tasks (open, with every blocker resolved or
  closed), by rank. Then waiting tasks (an open blocker, or draft), by rank.
  Done tasks leave the queue.
- **Moves that break a dependency.** A task may be ranked above one of its
  open blockers. The page keeps it in the waiting group and marks it "RANKED
  ABOVE ITS BLOCKER #x". The publisher's `move` prints the same warning.
- **Aliases.** A task shows as `#3f2a`: the leading hex of its event id, git
  style, lengthened only when two ids collide. Aliases never come from order
  or creation time, so they never change. Code, acceptance criteria and
  relations use slugs and ids, never aliases.

Relay caveat: relay.openagents.com returned 43 of 62 issues for a
three-filter REQ. The tools send one filter per REQ and page with
`limit`/`until`, so a short answer is never read as "not published". The
publisher also refuses to run when ids it published before are missing.

## Publisher and snapshot bridge

**Publisher** (`coax/web/project/publish.ts`, Bun with nostr-effect). It is
a tool on this machine, not something that runs in the browser.

```
bun publish.ts publish  [--project coax] [--dry-run]   # seed in project/coax/work/*.json → events
bun publish.ts move SLUG --before|--after SLUG          # one rank key rewritten
bun publish.ts status SLUG open|resolved|closed|draft
bun publish.ts respread [--seed]                        # new short keys, same (or seed) order
bun publish.ts list
```

It is idempotent. It rebuilds what exists from the relay. Unchanged items
publish nothing, and changed fields go out as a revision. A gitignored state
file (`state/<slug>.json`) records slug → id as a cross-check, and any event
the relay refuses is reported with the relay's message. It signs with the
project key. When the Coax Nostr work reaches signing (M3) and the relay
client (M5), signing moves into Coax and this tool is retired.

**Snapshot** (`coax/web/project/snapshot.ts`). The browser holds no
nostr-effect and no keys. Until the page reads the relay itself (the
initiative's last milestone), the snapshot does that work:
1. It fetches the project's events.
2. It verifies every signature and folds them with the same model the
   publisher uses.
3. It writes:
   - `project/coax/work.coax`, the tables `project.coax` draws;
   - `index.md`;
   - the hidden `<main>` in `index.html`.

`apps/openagents-web/build.sh` runs it on every release build (`deploy.sh`)
and on dev builds when the snapshot is more than ten minutes old. If the relay
can't be reached, the last snapshot stays.

## Build order

1. **Page mockup and real tasks** (now): `/project/coax/demo` with sample
   data, and `/project/coax` with tasks published as Nostr events and
   snapshotted at build.
2. **Read API:** `GET /v1/projects/coax` and `/tasks` served from a seeded
   coordinator, with the page reading the API instead of baked data.
3. **Claims:** claim, renew, release, submit and evidence. The CLI commands
   above. One maintainer-gated integration path for code.
4. **More projects:** project creation for any account, the project list,
   `invited` and `closed` policies, private projects in `3188` envelopes.
5. **Grid plots:** the registry, plots in the Verse, and figures driven by
   live claims.

## Open questions

1. **Coordinator per project or per owner.** NIP-COORD wants one admitted
   coordinator per scope. One per project is simplest. One per owner would
   let an agent's lease budget span that owner's projects.
2. **Fixing NIP-WORK's status line.** Its text still says "not an
   implemented issue tracker" (protocol spec §32.5). Once step 2 ships, the
   line should say what's implemented.
3. **GitHub imports.** NIP-WORK source imports can mirror GitHub issues into
   the queue. Whether the Coax project starts from GitHub issues or only from
   tasks made here is a decision for the owner.
4. **Folder-scoped projects and NIP-34 patches.** A patch can touch files
   inside and outside a `path`. The first rule should be to refuse a
   submission that touches files outside the claimed resources.
