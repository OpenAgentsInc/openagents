# Laya, and what to do about it

**Status:** a reading of an external project, researched 2026-09-19. Every
substantive claim links to a source. Where something is not stated by the
project, this page says so rather than filling the gap.

**Recommendation up front:** learn from three specific things, do not
benchmark against it yet, and do not prioritise supporting it.

## What it is

[Laya](https://laya.convaiinnovations.com/) is a 421M-parameter
non-autoregressive decision model: a from-scratch decision head on a frozen
ModernBERT-large bidirectional encoder. One state plus a map of typed
questions goes in, typed answers with probabilities come out, and it
generates no text.

It is a genuine member of this category, and it targets our contract
deliberately rather than by coincidence. Its inference entry point is
`system_one(state, questions)`, and the docstring in
[`rl_agent_api.py`](https://huggingface.co/convaiinnovations/laya/raw/main/rl_agent_api.py)
reads:

```python
"""Jev-compatible inference for a saved RL Agent model: system_one(state, questions) -> typed answers."""
```

Same three primitives under the same names — `choice`, `score`, `noul` — and
a confidence computed as `1 - normalized_entropy` under the comment
`"""Jev-style confidence"""`. Three checkpoints ship under Apache-2.0 with
downloadable weights, plus a router that picks between them from Unicode
script detection before the forward pass.

So: the closest open analogue to Kev that exists, and the largest of roughly
a dozen open reproductions that appeared in the same week — see
[awesome-jev](https://github.com/yibie/awesome-jev), which also lists a
`kev` on Qwen2.5-0.5B, `jev-local`, `LitJev`, and several
`POST /v1/systemone` servers.

## What it is not

**It is not a service.** There is no HTTP endpoint upstream: the package is a
Python library, and its dependencies carry no web framework. A community pull
request adding a drop-in `/v1/systemone` server was
[closed rather than merged](https://github.com/NandhaKishorM/laya/issues/1).
So there is nothing to be wire-compatible *with* yet, which is most of why
supporting it is low priority.

**It is not two days of work, but the repository is two days old.** Created
2026-09-18, 49 commits, thirteen PyPI releases in 48 hours, no changelog and
no versioned docs. The model still calls itself `"rl-agent"` in its own
responses and config. Laya is an existing reinforcement-learning project
rebranded onto this contract the week the ecosystem formed.

**Its training data is not released.** The project's own blog criticises
TypeSafe for shipping "with zero open training datasets," while
[issue #4](https://github.com/NandhaKishorM/laya/issues/4), asking for the
training scripts and datasets, is open with no maintainer response. Training
compute was 1.96 hours on one GPU.

## The benchmark table does not support what it is used for

The headline comparison claims Laya beats Jev on typed decisions (0.766
against 0.727), AG News, emotion, and calibration (ECE 0.081 against 0.246).

The project's own `BENCHMARKS.md` is unusually candid and states the central
caveat itself: the Jev figures are *"third-party published, never measured
here — no TypeSafe API access — so sample sizes and prompts differ; treat
them as indicative."* It also volunteers that its base checkpoints score
below the majority-class baseline on typed decisions, that moderation on
held-out data is 0.530, and that ordinal `score` is its weakest primitive.

That candour is real and worth crediting. The headline table still does not
hold up, for four independent reasons:

1. **No paired measurement exists.** Every Jev number is scraped from
   [jev-benchmarks](https://github.com/AbdelStark/jev-benchmarks) (n=100 per
   condition) and
   [decision-model-benchmark](https://github.com/nibzard/decision-model-benchmark).
   Neither of those has evaluated Laya. Nobody has run the two side by side.
2. **The calibration comparison is refit against out-of-box.** Laya's 0.081
   is after post-hoc temperature refitting on its own held-out distribution;
   as shipped it is 0.466. Jev's 0.246 is an out-of-box number on a
   deliberately adversarial forced-uncertainty suite. On the one task where
   both are measured the same way, Jev is better calibrated — 0.144 against
   0.213.
3. **The flagship accuracy is fine-tuned against zero-shot.** Laya's
   typed-decisions checkpoint was trained on that benchmark's own train
   split. Its zero-shot score on the same benchmark is 0.362.
4. **Jev wins where composition matters.** Soft accuracy against the teacher
   distribution is 0.580 against 0.471, and Banking77 is 0.870 against 0.425.

The priority narrative around the release — that this predates TypeSafe's
work — does not survive reading the two papers it cites.
[arXiv:2503.23303](https://arxiv.org/abs/2503.23303) predicts a single scalar
sales-conversion probability; [arXiv:2510.01237](https://arxiv.org/abs/2510.01237)
routes to mitigate hallucination. Neither describes a multi-question typed
schema over a caller-supplied option set. Both are unreviewed preprints.

None of this makes Laya bad work. It makes the comparison unusable, which is
a different claim and the one that matters for us.

## What to learn from it

Two things, in order of value, and one deliberately declined.

### 1. Per-question-type, per-option-count temperature buckets

Calibration is stored as a plain lookup:

```json
"temperature_by_options": {"choice:2":1.906,"choice:3-5":1.760,"choice:6-10":1.000,
                           "choice:11+":0.101,"score:3-5":1.251,"noul:2":1.983}
```

The reasoning — a two-option noul and a twenty-option choice need different
scaling — is obviously right and we are not doing it. Our
`crates/lev/src/calibrate.rs` fits one map per question *family*, where a
family is declared rather than derived from shape. Bucketing by type and
option count instead is cheap and directly portable.

Their `choice:11+` bucket fitted to 0.101 is almost certainly overfit, which
is a reason to keep our admission gate, not a reason to skip the idea.

### 2. Option-order flip rate as a shipped metric

They report permutation flip rate per suite and treat a regression as a
training-data problem. We measure it — Lev flips one greedy answer in eight,
kev-0.5b 7.4%, hosted Jev zero observed — but we do not publish it beside the
accuracy numbers. We should.

### Not taking: the multi-language result

Laya's most striking experiment is a 51-language sweep showing that its
English checkpoint's mean confidence never drops below 0.885 regardless of
accuracy — Khmer reads 0.000 accuracy at 0.952 confidence. Their conclusion
is that confidence gating cannot detect out-of-distribution input, and that
the choice of model has to be made before the forward pass.

**Out of scope by decision.** This repository measures English and only
English. The suites are English, the calibration maps are fitted on English
items, and a record now says so in a `language` field rather than leaving the
scope implied. If non-English ever becomes a priority, this experiment is the
right first thing to run and the finding above is why — but nothing here
waits on it.

## What it validates about Kev

Laya's "single forward pass" is a *batched* pass with one sequence per
question, each carrying its own full copy of the state. A bidirectional
encoder cannot cache a shared prefix, so encoder compute grows as
questions × state tokens. Their own figures show it: 39.5 ms at one question,
158.6 ms at ten, 771 ms at fifty.

Kev's packed prefill with a block-causal mask encodes the state once. The
advertised sevenfold single-question latency win inverts as question count
grows, and the System One design rule that says to ask every question that
shares a state — including speculative ones — is advice Kev can follow and
Laya cannot.

The same architecture produces their Banking77 collapse (0.425 against
0.870): at 512 context with 192 tokens reserved for the head, 77 options do
not fit. They diagnose it correctly as a budget ceiling rather than a
capability gap.

Lev, incidentally, shares Laya's weakness rather than Kev's strength — one
session per question, state re-encoded every time. That is recorded in
`docs/lev/architecture.md` as the price of isolation, and Laya is independent
evidence that the price is real.

## Recommendation

**Learn from:** temperature buckets keyed by type and option count, and
publishing option-order flip rate beside accuracy.

**Benchmark against:** not yet. There is no paired measurement of Laya
against anything, the flagship number is fine-tuned on its own evaluation's
train split, and the calibration headline compares a refit model to an
out-of-box one on a different suite. If we want a number, we should run Laya
ourselves under our protocol — Apache-2.0 weights and a notebook make that
cheap, and it would be the first paired measurement anyone has.

**Support:** low priority, because there is nothing upstream to support. No
`/v1/systemone` server exists there. If Laya-shaped traffic ever matters, the
community forks already implement our endpoint and are the better surface.

**Watch:** whether the training data ships, whether an HTTP server lands, and
whether any third party reproduces the benchmark table.
