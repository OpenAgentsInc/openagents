# Total four-byte load (#092b)

`cb_load_be32` and `cb_load_le32` (`coax/lib/crypto/bytes.coax`) used to load
through the 64-bit `cb_load_word` and then narrow with a checked
`cast(u32)`. That narrowing compiles to a range-checking helper on loaded,
possibly secret, bytes. The corrected secret-source audits refuse that shape.
The two wrappers now call `cb_load_word32`, a fixed four-byte `u32`
accumulator:

```
value = (value << 8) | cast,trunc(u32) data[index];
```

The byte is widened with `cast,trunc`, which emits a plain C conversion. The
shift count is the constant 8, and `<<` discards high bits without a check.
Only the public span check and the public byte order choose control flow and
indices. A refusal still returns `{value = 0, ok = false}`. The C ABI is
unchanged: `CbU32` and `CbU64` keep their layouts, the export signatures are
the same, and `cb_load_word32` is a static helper. The 64-bit loads, the
stores, `cb_mask`, the selects and `cb_ct_equal` are unchanged.

This changes one source shape. It is not a source-audit approval and not a
target timing approval. No signer, ECDH, encryption or production-secret use
follows from it.

**Proofs.** For both byte orders the solver proves five things:

- the old 64-bit four-byte value always fits a `u32`, so the old checked cast
  never trapped;
- the new value equals the low 32 bits of the old one;
- before each shift the accumulator is below 2^24, and the shifted value never
  overlaps the incoming byte, so no bit is lost;
- each byte lands in its own field;
- the starting accumulator value is shifted out entirely, so a successful load
  does not depend on initialization.

The controls are deliberately wrong models, and each must be satisfiable:

- a three-byte accumulator;
- a five-byte `u32` accumulator, which loses bits;
- an uninitialized three-byte accumulator;
- a swapped byte order.

The models are hand-written from source lines that the script pins. The
script refuses to run if any of those lines change. Whether a model matches
its source is a review premise; the solver does not check it. The removed
`cast(u32)` wrappers can no longer be pinned, so the old model rests on review
against the previous source. The z3 models do not cover the refusal path.
The Coax refusal check and mutation cover it.

**Vectors.** The oracle is Python's `int.from_bytes`. The vectors use five
byte patterns. Views are 0–12, 63 and 64 bytes long. Every offset from −2 to
one past the end is tried, plus `±2^63` limits, `2^62`, and malformed extents
(negative, above the 1 MiB bound, and `INT64_MAX`). Each load runs for widths
4 and 8 in both byte orders. Values are compared exactly; 64-bit values pass
through the JS runner as strings. The buffer must be unchanged after each
load. Wasm used clang 21, `wasm-ld` and wasi-libc 27 from nix
(`~/.cache/coax-wasm-toolchain`) under Node WASI. The emitted-C check confirms
that `cb_load_word32` and both wrappers call no checked-cast helper, in either
checked or release builds.

## Independent review

A separate read-only reviewer, with no part in writing the change, checked
these points and found no defect:

- the models correspond to the source, for the old and new paths;
- the headers and C ABI match before and after the change;
- the checks are not vacuous;
- no control flow or index depends on the data.

The reviewer raised these risks, and each is now handled:

- The refusal-path control had been the trivially true `x != 0`. It is
  removed, and the record above says what covers the refusal path instead.
- The 64-bit vectors had been folded into one integer. They are now exact.
- The vectors gained the `INT64_MAX` and above-1 MiB extents.

The reviewer could not run Wasm with the Homebrew defaults on this host. The
Wasm results above come from the nix toolchain.

## Still open

- **Caller target suites.** The SHA-256, ChaCha/XChaCha, Poly1305, PBKDF2,
  scrypt, ECDH and Schnorr Python suites depend on the Mac's `xcrun`, the
  Homebrew LLVM and Wasm toolchain, and a prebuilt fuzz cache. They cannot run
  on this Linux host, so they have not been rerun against this change. Their
  Coax checks pass. No iOS target consumes `coax/lib/crypto` today.
- **Stale pinned proofs.** `ecdh_serialization_proof.py`,
  `field-guards/prove.py` and `ecdh/prove_fused.py` pin `bytes.coax`, but on
  `origin/main` they already refuse for other changed sources (`ecdh.coax`,
  `secp_group32.coax`). Their pins are left as they are.
- **No approval.** This change does not approve any source audit or target
  timing.
