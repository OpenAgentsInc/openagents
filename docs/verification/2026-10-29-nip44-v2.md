# NIP-44 v2 over a supplied conversation key (#4878 nip44-v2, partial)

`coax/lib/nostr/nip44.coax` (`#authority`) has every part of NIP-44 version 2
that takes the conversation key as input:

- `calc_padded_len`, pad and unpad, including the pinned NIP's six-byte prefix
  at 65,536 bytes and above
- message keys from HKDF-expand (76 bytes: ChaCha key, ChaCha nonce, HMAC key)
- encrypt and decrypt with base64 framing and the version byte
- HMAC-SHA256 over nonce||ciphertext, compared in constant time with
  `cb_ct_equal`

Decrypt checks the MAC before it decrypts anything. The caller's `out` is
written only after the padding is valid, and every refusal leaves `out`
unchanged.

`nip44_conversation_key_checked` is HKDF-extract with salt `nip44-v2` over a
raw 32-byte shared x that the caller supplies. To wire task #71e7
(crypto-ecdh-xonly), pass that task's raw x output to this function.
`coax/lib/nostr/nip44-memory.coax` holds the `#export_c` wrappers. They only
compute the overlap facts, following the pattern of `chacha20-memory.coax` and
`hmac-memory.coax`.

## Profiles

The two pinned sources disagree. The 2023 vector corpus lists 65,536 and
100,000 bytes under `invalid.encrypt_msg_lengths`. The pinned NIP text, which
is newer, makes those lengths valid with the six-byte prefix. Each source is
honored by a named profile:

| Profile | Plaintext | Largest payload | Larger input |
| --- | --- | --- | --- |
| `NIP44_COMPAT` | 1..65,535 | 87,472 characters | `NIP44_CAPACITY`, refused before base64 decoding |
| `NIP44_EXTENDED` | 1..917,504 | 1,223,436 characters | `NIP44_CAPACITY` |

`NIP44_COMPAT` matches the corpus and deployed 2-byte readers such as
nostr-effect. A compat reader never misdecodes an extended payload.

The 917,504-byte limit comes from local limits. The next padding bucket
(1,048,576) would push the HMAC input (nonce plus a 6-byte prefix plus the
padded plaintext) past the 1 MiB `CB_MAX_BYTES` limit that SHA-256, HMAC and
ChaCha20 share. A check asserts that the HMAC, ChaCha20 and base64 admission
functions all accept the advertised maximum and refuse the next bucket.

Following the spec pseudocode, unpad checks the prefix and the exact padded
length. It does not check that the padding bytes are zero. Encrypt always
writes zero padding.

The pinned NIP's extended-prefix table (65,535/65,536/65,537) gives matching
plaintext and payload SHA-256 in the interpreter. A compat reader refuses the
65,536-byte payload as capacity.

Interoperability: there are 11 throwaway-key rows (1 to 300 bytes) from
nostr-effect 0.0.13, which uses @noble/ciphers, @noble/hashes and
@scure/base. Coax's encrypt is byte-identical to nostr-effect's payload, and
Coax decrypts nostr-effect's payload. Encryption is deterministic for a given
nonce, so the two implementations interoperate in both directions. No
production key is used. The oracles were the packages already installed for
the board tool. Nothing was downloaded.

## Not done

- **ECDH (#71e7):** raw-x secp256k1 ECDH, `get_conversation_key(sec, pub)`
  from keys, and the 8 `invalid.get_conversation_key` vectors (scalar out of
  range, invalid or twist points). These wait on crypto-ecdh-xonly.
- **Event boundary:** encrypting into a signed event, reading it back, and
  checking that event payload limits agree with these maximums. This needs the
  event write/read path. Verifying the outer event is the integration
  boundary's job.
- **Other targets and erasure:** no Wasm or iOS runs. There is no erasure
  guarantee for work buffers or derived keys, and no claim about target timing.
- **Fresh nonces:** the caller must supply a fresh CSPRNG nonce from
  `entropy.coax` for each message. Nonce reuse is not detected.
