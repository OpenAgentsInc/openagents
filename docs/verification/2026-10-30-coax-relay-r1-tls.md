# wss:// on the Coax relay's server side (R1)

This record closes the TLS bullet of
[the R1 record](2026-10-29-coax-relay-r1.md) ("TLS. None. ws:// only").
It is part of phase R1 in coax/nostr.md section 17. It reuses the client TLS
layer's file and policy ([2026-10-29-nostr-relay-tls.md](2026-10-29-nostr-relay-tls.md))
and is covered by the same owner exception (AGENTS.md, Rules: the C host may
link one TLS library for the handshake, certificate verification and record
encryption only). Recorded 2026-10-30.

## What landed

| File | What |
| --- | --- |
| `coax/platform/tls-native.{h,c}` | Adds a server mode beside the client, so there is still one TLS path. These functions are for C hosts only, are not `#foreign`, and take pointers: `cxtls_server_load(cert, key)`, `_new(fd)`, `_handshake`, `_want`, `_read`, `_pending`, `_write`, `_free`. The policy is fixed, with no switch: TLS 1.2 minimum (1.3 preferred), no compression, no renegotiation, no client certificates. The private key is opened with `O_NOFOLLOW` and checked on the open descriptor, so there is no window between the check and the read. It must be a regular file owned by the effective user with no group or other bits (0600 or 0400). Otherwise the load returns `CXTLS_KEY_MODE` (-13) and nothing is loaded. A key that is unreadable or doesn't match the certificate is `CXTLS_KEY` (-14), and an unreadable chain is `CXTLS_CERT` (-15). No error path prints or keeps OpenSSL error text, so no key material can reach a log. Every call returns at once. The handshake is `SSL_do_handshake` on a nonblocking socket and reports 0 while it waits for the peer. On Apple every server function is a stub that returns `CXTLS_UNSUPPORTED` |
| `coax/platform/socket-server-native.{h,c}` | `cxsrv_set_tls(1)` makes every accepted connection TLS. The `cxsrv_*` contract that Coax sees doesn't change: reads and writes are plaintext. The handshake is stepped inside `cxsrv_read`, which returns 0 while it waits. A handshake failure (the client isn't TLS, offers nothing at TLS 1.2 or above, or gives up) returns `CXSRV_ERROR` on that handle only. So does a handshake that isn't finished within `CXSRV_TLS_HANDSHAKE_MS` (10 s). `cxsrv_poll` waits for what OpenSSL wants (POLLIN or POLLOUT), wakes in time for a handshake deadline, and returns at once while decrypted bytes wait inside TLS (`SSL_has_pending`) |
| `coax/relay/relay-host.c` | `--tls-cert CHAIN.pem --tls-key KEY.pem`, both or neither. Load failures print a fixed sentence and exit 2. `ry_host_tls()` tells Coax that TLS is on |
| `coax/relay/relay.coax` | Two changes only. The default NIP-42 relay URL is `wss://ADDRESS:PORT` when TLS is on. A `--url` whose scheme disagrees with the transport is refused at start: `ws://` on a TLS relay, or `wss://` on a plain one. Everything above the socket (HTTP, RFC 6455, NIP-01, NIP-11, NIP-42) is the same Coax code over the same bytes |
| `coax/relay/build.sh` | Sources `coax/platform/tls-env.sh` and links `tls-native.c` and `socket-native.c` against OpenSSL 3 from Nix. The host C is now built with `-Wall -Wextra -Werror` |
| `coax/tests/nostr/relay_session.py` | `--tls [--client EXE]`: every session runs over `wss://` (NIP-11 over `https://`), and the TLS cases below are added. The test CA, a rogue CA, the leaf (SAN `DNS:localhost`, `IP:127.0.0.1`) and a second key are generated by `openssl` into the run's temp dir. They are valid for one day and none is committed. Plain `python3 coax/tests/nostr/relay_session.py` is unchanged and still runs over ws:// |
| `coax/tests/net/relay_tls_client.coax` | The Coax client transport, `relay_conn.coax`, against the TLS relay. It opens `wss://localhost:PORT` with the chain and the name verified, reads the NIP-42 challenge, sends a REQ for kind 1, counts events until EOSE, and closes with 1000 |
| `coax/tests/net/tls.sh` | Also builds `relay_tls_client` (ASan/UBSan, `-DCXTLS_TEST_TRUST`) and runs `relay_session.py --tls --client` on it |

## What ran

These ran on 2026-10-30 on Linux 6.18.49 (NixOS), with gcc 15.2.0, OpenSSL
3.6.3 (from Nix, through tls-env.sh), Python 3.13 `ssl`, and the compiler
coax0 from the main checkout's `coax/bin/coax`. The relay and the client
driver were built with ASan and UBSan.

- **`coax/tests/net/tls.sh`: all local checks pass.** The 17 existing client
  cases are unchanged and pass, and the script now runs
  `relay_session.py --tls --client`, which gave **85 of 85**:
  - **The 72 existing sessions over wss://.** NIP-11 is served over
    https://. Every NIP-42 answer names `wss://127.0.0.1:PORT`, including
    the one in another case with a slash (`WSS://127.0.0.1:PORT/`). The
    sessions also cover publish and OK, REQ, EOSE and live events, CLOSE,
    replacement, expiration, the limits, ping, the 1009 close, and a
    restart with `--store` that brings back the same 11 events.
  - **13 TLS cases.** Five are refused at start, with exit 2 or no listener,
    and none of their output contains key text: a 0644 key, a key path that
    is a symbolic link, a key that isn't the certificate's, `--tls-cert`
    without `--tls-key`, and `--url ws://` on a TLS relay. A Python client
    that trusts a rogue CA gets `SSLCertVerificationError`, and so does one
    that expects `other.test`. A plaintext WebSocket upgrade sent to the
    TLS port is closed with no reply. With two stalled handshakes open (one
    silent, one that sent 10 bytes of a ClientHello), another client still
    completed TLS, got its challenge and finished REQ to EOSE in 0.01 s. The
    two stalled handshakes were closed after 10.0 s. After all that the
    relay still served the same events. The Coax client transport
    (`relay_conn`, in `relay_tls_client.coax`) connected to
    `wss://localhost:PORT` with the chain and the name verified, got the
    challenge and the 3 stored kind 1 events, saw EOSE, and finished the
    1000 closing handshake. With `CXTLS_TEST_CA` pointing at the rogue CA,
    it refused the relay.
  - No sanitizer report from the relay or the client driver, and no leaks
    from the driver (LSan on).
- **`python3 coax/tests/nostr/relay_session.py` (ws://, unchanged mode):
  72 of 72** under ASan/UBSan. The plain path behaves as before.
- **`-Wall -Wextra -Werror` is clean** for `tls-native.c` (with and without
  `-DCXTLS_TEST_TRUST`), `socket-server-native.c`, `relay-host.c` (the
  relay build now uses these flags for the host C) and `store-file-native.c`.
- **One fix on the way.** The first full tls.sh run failed one session,
  "a 131074-byte frame: close 1009". The relay refuses that frame on its
  header and closes. The Python client was still writing the rest of the
  131 KiB, and over TLS that write sometimes hit the reset (EPIPE). The
  check now sends the header and 1 KiB, then reads the close. It passed
  over both ws:// and wss:// after the change. That a refusal on the header
  alone is enough is now part of what the check proves.
- **Mutation: none needed.** No `#authority` file changed. `relay.coax`
  isn't `#authority`; its change is the URL scheme default and agreement
  check, exercised by the sessions. `relay_route.coax`, `nip42.coax`,
  `relay_uri.coax` and the store are unchanged, so their earlier mutation
  results stand.

## Missing (not claimed)

1. **The Apple server branch.** A Network.framework `nw_listener` is not
   written. On Apple, `--tls-cert` fails at start with "TLS server mode is
   not available on this platform". The stubs sit after the
   `tls-apple.inc` include, which needs Apple's headers, so they were not
   compiled here or on a Mac.
2. **Certificate reload.** The chain and key are read once at start. Rotating
   a certificate (for example, Let's Encrypt renewal) needs a restart. There
   is no SIGHUP reload.
3. **No SNI-based multiple certificates and no ALPN.** One chain serves every
   name.
4. **Slot pressure from stalled handshakes.** A stalled handshake doesn't
   block other connections, but it holds one of the relay's 16 connection
   slots for up to 10 s. Plain ws:// has the same exposure through a slow
   HTTP head, which has no idle limit. Per-IP connection limits are R2.
5. **A TLS 1.1-only client** is refused by the fixed minimum. That is tested
   on the client side (tls.sh's `--max 1.1` server), but this run had no
   TLS 1.1 client against the relay.
6. **The tailnet and public deployment.** The certificate for a real name
   (tailnet `*.ts.net` from `tailscale cert`, or a public name), and pointing
   the Pylon at `wss://`, belong to the tailnet and flood work.
7. The relay binary now always links OpenSSL, even when it serves only
   ws://.
