# Chapter 15: Mammoth CPU verification, 2026-10-29

The original-weight run used coax0 0.22.0 built from `origin/main` in a fresh worktree on
`coderos-4080` (Linux x86-64, i7-14700K, 125 GB RAM; the RTX 4080 was not
used) and GCC 15.2.0. The target is the pinned `baselabs/mammoth-1`
revision `61cec44c281c693992e3d6ebeb44dd3402dfa186`.

## Psionic run

`psionic/tests/run_mammoth.sh` prepared the typed choice `Water is wet.` /
`Is the water wet?` / `yes`, `no` to 86 tokens (49 prefix, 37 suffix), equal to
the pinned chapter 10 token stream; both models pin the same tokenizer. Every
buffer was sized by `ps_plan(1,86,86,49)`: 2,640,384 parameter floats (twice,
for staging), 62,176 layer-work floats, 42,041,344 state floats and
218,486,272 workspace floats, about 1.05 GiB of caller allocations.

| Phase | Wall clock |
| --- | --- |
| Session open: SHA-256 of all files, inventory, index, layer binding | 234.5 s |
| Answer: prefix and suffix through 64 layers and the full vocabulary | 9,113.0 s |
| Harness process total | 9,347.6 s |
| Script total, including Coax-to-C compilation | 2 h 36 min 4 s |

The run is one thread at 97 to 100 percent of a core. The host was shared with
other work at a load average near 35 on 28 hardware threads, so these times
are an observation under contention, not a benchmark. Peak resident set size
was 53,949,460 KiB (51.4 GiB). Almost all of it is the read-only mapping of the
two shards, whose pages were all touched by hashing; the private allocations
are the 1.05 GiB above plus the tokenizer table and inventory. Pages of a
private read-only file mapping can be reclaimed by the kernel, so this is not
a lower bound on the memory the run needs, and it is not an admission rule.

Result: `yes`, `p_yes=0.94461191`, `p_no=0.0553880904`, slot mass
`0.472741322`, confidence `0.889223819`.

## Independent reference

A float32 copy of Mammoth is about 108 GB, so the chapter 14 approach (the
whole model loaded by Transformers in float32) does not fit on this host next
to the mapped checkpoint. [`mammoth_reference.py`](../../psionic/tests/mammoth_reference.py)
keeps the same arithmetic and changes only residency: it builds one
Transformers 5.19.0 `Qwen3_5DecoderLayer` at a time (PyTorch 2.14.1+cpu, eight
threads), loads that layer's original BF16 tensors converted to float32 with
`load_state_dict(strict=True)`, runs all 86 tokens through it and frees it.
Full-attention layers use eager attention and an additive mask in which prefix
rows cannot see suffix columns and everything else is visible; linear layers
get no mask, as in an unpadded forward, and use the Transformers PyTorch paths
(the script refuses to run if `fla`, `causal_conv1d` or `kernels` is
installed). Embedding rows, the final RMS norm and every head row are float32;
the Hugging Face hub was kept offline.

To check the method, the same script was run on the authenticated Elephant
original. It gave `p_yes=0.757196486` and slot mass `0.228232756`, against the
chapter 14 whole-model reference `0.757196248` and `0.228232533`: differences
below 0.0000003.

On Mammoth the reference took 148 s wall clock with a 50.9 GB peak resident set
(mostly mapped safetensors pages) and returned slot logits 10.928954, 8.092546,
`p_yes=0.944611788`, `p_no=0.0553881899` and slot mass `0.472741485`. The
captured values are in
[`transformers-reference.json`](../../psionic/fixtures/models/mammoth/transformers-reference.json).

| Statistic | Psionic | Reference | Absolute difference |
| --- | --- | --- | --- |
| `p_yes` | 0.94461191 | 0.944611788 | 1.2e-7 |
| `p_no` | 0.0553880904 | 0.0553881899 | 1.0e-7 |
| slot mass | 0.472741322 | 0.472741485 | 1.6e-7 |
| confidence | 0.889223819 | 0.889223598 | 2.2e-7 |

The harness enforces 0.0005 absolute on each statistic, the chapter 14
tolerance, fixed in the fixture checker before the Mammoth run. The observed
differences are about 2,000 times smaller. Unlike chapter 14, this record has
no intermediate-layer comparison for Mammoth: the Psionic public path exposes
only the answer. These are numerical comparisons, not bitwise identity.

## Checks

The original-weight run, the reference and the first checks used coax0 0.22.0.
After rebasing on `origin/main`, the changed units were checked again with
coax0 0.24.0 using `psionic/check.sh --jobs 16 --only decision-session
decision-plan`: all oracles and fixtures (including the Mammoth fixture and
captured Psionic output), Coax debug and release checks (273 and 283 checks),
and mutation of `decision-session.coax`, 6,333 mutants with no survivors.

`decision-plan.coax` (`#authority`) passed its debug and release checks, and
`coax mutate` killed all 6,513 mutants with no survivors under 0.22.0; the file
is unchanged since. Its native harness and the extended session harness, which
now refuses Mammoth requests with the wrong file or tensor count, passed debug
and release, plain and ASan/UBSan, with GCC 15.2.0. `psionic/tests/book.py`
passed on the rebased tree.

Not done: a complete `psionic/check.sh` run. One was started and stopped after
26 of its units' mutation runs, all with zero survivors, because a full run
takes many hours; units this chapter does not touch were not rerun.
The `--only` run hit its 15-minute limit while mutating `decision-plan.coax`
under 0.24.0, so that mutation and the `--only` native step were not repeated
with 0.24.0; the 0.22.0 results above stand for them.

## Limits

This covers one text request at temperature one on one CPU profile. It does
not establish accuracy on other requests, calibration or quality under
chapter 16 for Mammoth, image input, or a serving speed: the CPU reference
path takes over two hours for 86 tokens. `ps_plan` sizes caller buffers; it
does not check host memory or schedule resources.
